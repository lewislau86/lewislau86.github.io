## 问题：很多请求同时来

到目前为止，每个请求都是单独处理的。[第 28 章](./inference-efficiency.md)算过，单请求 decode 每生成一个 token，都要把全部权重读一遍，却只做一行矩阵乘；那一章的屋顶线图也说了，要几百个 token 一起算，GPU 的算力才用得满。

真实的服务同时有很多请求。把它们放进同一次前向，权重读一遍，所有请求共用，这就是**批处理**。难的不是“要不要批”，而是请求长短不一、到达时间不一：提示词有长有短，有的要写 8 个字，有的要写 40 个；有的刚到，有的已经写了一半。这一章回答三个问题：长短不同的请求怎样拼进一次前向而结果不变；调度器每一步该放谁进来；批开多大才合适。

## 1. 研究对象：第 12 章的基线模型

模型与第 28～31 章相同：d=128、4 层、4 个头、词表 4096、上下文 64，训练 300 步，种子 0。批处理不改变模型，只改变“一次前向里放谁”。为了在拼批时复用同一套计算，把一层 Block 拆成两半：`attn_inputs` 算出加了 RoPE 的 Q、K、V，`finish` 接上注意力的输出，做完残差和前馈层。两半中间的注意力怎么算，正是拼批要动的地方。

## 2. 拼成矩形：padding、掩码和位置

最直接的批法是把几个提示词拼成一个 [B, T] 的矩形，短的用 `<pad>` 补齐。补在左边（left padding），每一行的最后一个位置都是真 token，下一个 token 的 logits 都在最后一列。要做对两件事：

- **掩码**：真 token 不能看见 pad，注意力里要把 pad 所在的列遮掉；
- **位置**：位置从这一行第一个真 token 开始数，也就是 `mask.cumsum(-1) - 1`，而不是矩形里的列号。

4 个长度不同的提示词（6、12、24、40 个 token），按四种写法拼批，和单独跑的结果比较最后一个位置的 logits：

<<< @/public/tinyllm/code/batching.py#padded

```text
左补齐，位置和掩码都对    与单独跑的最大差 1.9e-06  下一个 token 相同 4/4
左补齐，位置用列号      与单独跑的最大差 2.4e-06  下一个 token 相同 4/4
左补齐，不遮 pad     与单独跑的最大差 3.0e+00  下一个 token 相同 3/4
右补齐，取最后一列      与单独跑的最大差 1.2e+01  下一个 token 相同 2/4
提示词长度 [6, 12, 24, 40]：矩形里真 token 只占 51%，其余位置是白算的 pad
```

逐行看：

- 位置和掩码都对时，差别在 $10^{-6}$ 量级，是浮点舍入。
- “位置用列号”的结果也对，这有点出乎意料。原因是 RoPE 只看两个位置的**相对距离**：同一行的真 token 都向右平移了同样的格数，两两之间的距离不变。换成 GPT-2 那样按绝对位置查表的位置编码，这样写就错了；而且列号可能超出训练时见过的长度。所以 transformers 仍然按 `cumsum` 算位置（见章末“在真实模型里”）。
- 不遮 pad：真 token 的注意力分了一部分给 pad，logits 差到 3，4 个里有 1 个下一个 token 变了。
- 右补齐还取最后一列：短的那几行最后一列是 pad，拿到的是 pad 位置的输出，只有最长的那一行（以及碰巧一样的一行）是对的。右补齐也能做对，要按每行的真实长度去取，但生成时新 token 会接在 pad 后面，所以批量生成一般用左补齐。

最后一行是矩形批的代价：4 个提示词共 82 个真 token，矩形却有 160 个位置，一半是白算的。

![同样 4 个提示词的两种拼法：上面拼成 4×40 的矩形并左补齐，160 个位置里 78 个是 pad；下面首尾相接排成一行，共 82 个位置，没有 pad，线性层对整行一起算，注意力按段分开](/tinyllm/figures/batch-layouts.svg)

怎么读这张图：上面每行一个请求，灰格是 pad。下面是本章引擎的做法：所有请求的新 token 首尾相接排成一行，不补齐；线性层和前馈层对这一整行一起算（权重只读一遍），只有注意力按段分开，每段只看自己的 K、V。

## 3. 一个最小的连续批处理引擎

矩形批除了补齐，还要整批一起开始、一起结束。换一种组织方式：

- 每个请求占一个**槽位**，槽位里放它自己的 KV cache 和已有长度，长短互不影响；
- 一次前向的输入是一个列表 `[(槽位, 这次要送的 token), ...]`：在 decode 的请求送 1 个，刚来的请求送整段（或一段）提示词；
- 所有新 token **首尾相接排成一行**，线性层、前馈层对这一行一起算；
- 注意力按请求分开算，每个请求只看自己槽位里的 K、V。

这就是 [Orca](https://www.usenix.org/conference/osdi22/presentation/yu) 提出的“选择性批处理”（selective batching）：有权重的算子一起算，注意力按请求分开；今天推理框架里的“变长（varlen）批”也是这个思路，只是注意力换成了一次处理所有段的内核。

## 4. 为什么要批：一次前向带多少个请求

有了引擎，就能量批处理的收益了。缓存里每个请求已有 16 个位置，一次前向给 B 个请求各算一个新 token；再量一个请求一次送进 N 个 token：

<<< @/public/tinyllm/code/batching.py#batch-cost

```text
一次前向带  1 个请求：权重读一遍 5.00 MiB，摊到每个 token 5.00 MiB
一次前向带  8 个请求：权重读一遍 5.00 MiB，摊到每个 token 0.63 MiB
一次前向带 32 个请求：权重读一遍 5.00 MiB，摊到每个 token 0.16 MiB
```

上面三行和硬件无关：权重只读一遍，摊到每个 token 上的读取量和 B 成反比。在本站的运行环境（4 核 aarch64 CPU）上，一次前向带 1 个请求约 1.0 ms，带 8 个约 1.7 ms，带 32 个约 3.8 ms：前向慢了不到 4 倍，摊到每个 token 却便宜了约 9 倍。一个请求一次送进 1 到 48 个 token，耗时从约 1.05 ms 涨到约 1.5 ms。在这台机器上，多带的请求比多送的 token 更贵，很可能主要因为引擎的注意力是逐个请求用 Python 循环算的，每多一个请求就多 4 层的注意力调用；GPU 上的变长注意力内核一次处理所有段，没有这笔开销。

这两组数有同一个形状：一次前向有一笔固定开销，在它之内多带一些几乎不要钱，超过以后才按工作量线性变长。这就是[第 28 章](./inference-efficiency.md)屋顶线的形状。

## 5. 请求流和成本模型

调度要在同一份请求流上比较。请求流由单独的随机数生成器预先排好（和第 12 章的 batch 计划同一个思路）：到达时间是泊松过程；四分之三是短提示词（一首诗的第一句），要生成 8～40 个 token；四分之一是长提示词（一首诗的前 40 个 token），只生成 4～12 个。三种随机种子各一份。

墙钟时间和机器有关，噪声也大，所以调度实验的时间用一个写明了的**成本模型**来算：一次前向花 $\max(1, N/K)$ 个单位，N 是这次前向里新 token 的总数（早结束、还占着位置的行也算 1 个），K=16。意思是：一次前向至少花 1 个单位（读一遍权重），新 token 不超过 K 个时几乎不多花，超过以后按 token 数线性变长。真实 GPU 上拐点在几百个 token，这里按本章提示词的长度把它缩小到 16。第 8 节会换几个 K 再看结论变不变。

## 6. 三种批法，同一份请求流

调度器每次做一个决定：这一次前向里放谁、各送几个 token。三种批法：

- **静态批**：凑够 B 个请求再一起开始（流的末尾凑不够，就等最后一个到），整批一起结束。早结束的请求不离开，它的位置照算（矩形批就是这样处理的），记作“白算”。为了公平，这里的静态批也用首尾相接的引擎送提示词，不算 pad 的代价，这对它是偏宽的。
- **动态批**：引擎空闲时，从队首请求到达算起最多等 W 个单位，到时有多少收多少（最多 B 个），之后同样整批一起结束。
- **连续批**：每次前向之后，结束的请求立刻离开，等待的请求立刻补进空槽位，它的整段提示词和别人的 decode 放在同一次前向里。这就是 Orca 的“按迭代调度”（iteration-level scheduling）。

每格是 3 份请求流的平均，方括号是范围。

- **重负载下，连续批的 TTFT 中位数只有静态批的约五分之一**（13.7 对 66.2），吞吐高约一半（5.64 对 3.67），3 份请求流上都是如此。静态批有两笔浪费：约三分之一的位置是早结束的请求在“陪跑”；新来的请求必须等整批结束才能进来，排队越来越长。
- **静态批的 TPOT 反而最好**（1.00）。它把所有提示词放在整批的第一次前向里，之后每一步只有 decode，不超过 8 个 token，按成本模型每步正好 1 个单位。连续批把新请求的提示词塞进别人的 decode 步，那一步变长，正在生成的请求就慢了一点（1.15）。这个代价第 7 节来解决。
- **动态批在轻负载下才有用。** 每 8 个单位才来一个请求时，静态批要等凑够 8 个，TTFT 37；动态批从队首请求到达算起最多等 4 个单位就开跑，TTFT 降到 20。可是一开跑就要整批跑完，中途来的请求还得等，所以它还是远不如连续批（1.6）。重负载下队首请求往往已经等够了，动态批常常不等满就开跑，批更小，比静态批略差。
- 轻负载下三种批法的吞吐差不多（2.16～2.27）：这时吞吐由请求来得多快决定，不由调度决定。

## 7. 长提示词卡住别人：分块 prefill

连续批里，一个 40 个 token 的提示词进来时，它和所有正在 decode 的请求在同一次前向里。按成本模型，这次前向要花 $\max(1, (40+7)/16)\approx 2.9$ 个单位，正在 decode 的 7 个请求这一步都要等这么久，用户看到的是输出卡了一下。

**分块 prefill**（chunked prefill）把每次前向的新 token 限制在 K=16 个以内：先给在 decode 的请求各 1 个，剩下的额度按到达顺序分给提示词，没送完的下一次接着送。分块不改变数学结果，[第 28 章](./inference-efficiency.md)已经证明过一次算完和分块逐元素相同；这里的 `assert` 也再检查了一遍。

<<< @/public/tinyllm/code/batching.py#chunked

```text
连续批          最长卡顿 4.02 [3.31, 5.38]  TPOT P90 1.34 [1.19, 1.49]  TTFT 中位 13.71 [8.43, 19.98]  P90 26.93 [20.61, 32.31]  吞吐 5.64 [5.47, 5.75]
连续批 + 分块 prefill 最长卡顿 1.00 [1.00, 1.00]  TPOT P90 1.00 [1.00, 1.00]  TTFT 中位 11.03 [6.03, 18.20]  P90 21.06 [16.88, 23.30]  吞吐 6.16 [5.85, 6.45]
逐份请求流的 TTFT 中位：种子 0 12.7 → 6.0  种子 1 8.4 → 8.9  种子 2 20.0 → 18.2
```

最长卡顿从约 4 个单位降到 1，TPOT 的 P90 也降到 1，3 份请求流都是如此。卡顿降到 1 是成本模型的直接结果：每次前向不超过 K 个新 token，就不超过 1 个单位，这正是分块的设计目标，让每次前向都停在拐点以内。

吞吐在 3 份请求流上都变好了（平均 6.16 对 5.64）；TTFT 中位平均也更好（11.0 对 13.7），但逐份看是 2 份变好、1 份略差（8.4 → 8.9）。吞吐的提高来自成本模型的一个假设：不到 K 个 token 的前向也要花 1 个单位，只有 decode 的那些步留着空余的额度。分块把提示词切开，填进这些空余里（7 个 decode 加 9 个提示词 token 正好 16 个），decode 就“搭了便车”；不分块时，40 个提示词 token 加 7 个 decode 一次花 2.9 个单位，等于把一部分本可以白搭的 decode 挤成了额外的时间。成本模型没有给分块记任何额外开销（比如每一块都要重读前面块的 K、V），所以这里的收益是偏乐观的。这正是 [Sarathi-Serve](https://arxiv.org/abs/2403.02310) 的思路：把提示词切成块，和 decode 拼在一起，不让 decode 停下来（stall-free）。

![连续批下每个请求相邻两个 token 的间隔：上面不分块，长提示词到达（橙色竖线）后间隔跳到 1.1 到 5.4 个单位；下面分块后所有间隔都是 1](/tinyllm/figures/batch-chunked.svg)

怎么读这张图：每个点是某个请求相邻两个 token 之间隔了多久，横轴是时间。上图大部分点在 1，但长提示词（橙色竖线）进来以后会冒出几个高点，那是所有正在生成的请求一起被卡住；下图的点全部贴在 1 上。

## 8. 批开多大：吞吐和延迟的交换

槽位数 B 决定最多多少个请求同时在跑。为了让大的 B 真的被用满，这里把到达压到每个单位 1 个请求（过载），用不分块的连续批，把 B 从 1 调到 32。再加一个时延目标（SLO）：TTFT 不超过 20 个单位、TPOT 不超过 1.5 个单位，两个都满足的请求，它的 token 才算进 **goodput**（[第 28 章](./inference-efficiency.md)讲过这个指标）：

```text
B= 1：吞吐 0.98  goodput 0.05 [0.04, 0.06]（达标 1.3/40 个请求）  TTFT 中位  398.5  TPOT 中位 1.00  P90 1.00
B= 2：吞吐 1.91  goodput 0.16 [0.13, 0.21]（达标 3.0/40 个请求）  TTFT 中位  192.0  TPOT 中位 1.00  P90 1.06
B= 4：吞吐 3.48  goodput 0.64 [0.59, 0.74]（达标 6.3/40 个请求）  TTFT 中位   85.8  TPOT 中位 1.01  P90 1.16
```

吞吐一直在涨，从 0.98 到 8.32；但 B 越大，每次前向的 token 越容易超过拐点（十几个 decode 再加上新来的提示词），每一步都变长，TPOT 中位从 1.15（B=8）涨到 1.53（B=16）、2.27（B=32）。goodput 在 B=8 和 16 时最高：B=16 的平均略高（2.02 对 1.94），但 3 份请求流之间从 0.76 到 3.90 波动很大，B=8 在 1.47 到 2.27 之间，更稳，达标的请求也更多（12.7 对 11.3）。B=32 时掉到 1.10：吞吐是多了，可大部分请求的 TPOT 超了目标，不算数。B 小的时候 goodput 也低，原因相反：请求排队太久，TTFT 超了目标。

成本模型的拐点 K=16 是本章定的。换成 8 和 32，再比一次重负载下四种策略的 TTFT 中位数：

```text
K= 8：TTFT 中位  静态   86.6  动态   89.9  连续  33.7  连续 + 分块  38.3
K=16：TTFT 中位  静态   66.2  动态   71.4  连续  13.7  连续 + 分块  11.0
```

注意 `serve` 里 K 同时是成本模型的拐点和分块的额度，这三行把两样一起改了。“连续批远好于静态批和动态批”在三个 K 下都成立。分块 prefill 的 TTFT 却不总是更好：K=8 时，7 个请求在 decode 就占掉 7 个 token 的额度，正在送提示词的请求每次只能送 1 个，40 个 token 的提示词要送 40 次，TTFT 反而变差（38.3 对 33.7）。所以分块的额度要明显大于同时在 decode 的请求数；真实框架里每次前向的 token 额度（几千个）比最大并发请求数（几百个）大得多，也是这个原因。

## 9. 真实系统里还有什么

本章的引擎只有几十行，真实的推理服务在同样的骨架上多做了几件事：

- **显存才是真正的上限。** 本章的引擎给每个槽位预留了 64 个位置的 KV cache，不管用没用到。真实服务里同时在跑的请求数，往往先被 KV cache 卡住，而不是被算力卡住。KV 怎样按需分配、怎样在请求之间共享，是[第 33 章](./kv-memory.md)的内容。
- **prefill 和 decode 分到不同的机器。** 分块 prefill 让两者共用一批 GPU、互相少干扰；[DistServe](https://arxiv.org/abs/2401.09670) 走另一条路，把 prefill 和 decode 放在不同的 GPU 上，各自按 TTFT 和 TPOT 的目标配资源，代价是要把 KV cache 从 prefill 的机器传到 decode 的机器。
- **投机解码要重新算账。** [第 31 章](./speculative-decoding.md)的收益来自“多验证几个位置几乎不要钱”，这只在一次前向远没到拐点时成立；批大了以后，每个请求多验证 γ 个位置，就是实打实地多算。
- **请求不只按到达顺序排。** 本章全部按先来先服务；真实系统还要处理优先级、超时取消、显存不够时把请求换出去再换回来（transformers 的调度器里能看到这些分支）。

## 动手实验

1. **静态批也能少浪费。** 改写 `serve` 的静态批：早结束的请求立刻离开、不再“陪跑”，但新请求仍要等整批结束才能进来。白算的比例降到多少？TTFT 有多大改善？和连续批比还差多少？
2. **最短的先来。** 连续批里，等待队列现在按到达顺序。改成“要生成的 token 少的先进”（假设能提前知道长度），比较 TTFT 的中位数和 P90。为什么 P90 可能变差？
3. **分块额度。** 在第 7 节把分块的额度从 16 改成 24、32（同时保持成本模型的 K=16），最长卡顿和 TTFT 怎样变化？额度和 K 不一样时，“每次前向不超过拐点”还成立吗？

## 本章结论：TinyLLM 的选择 {#tinyllm-choice}

TinyLLM 的推理服务用本章的<strong>连续批 + 分块 prefill</strong>：每个请求一个槽位，新 token 首尾相接排成一行，有权重的算子一起算、注意力按请求分开；每次前向先给所有在 decode 的请求各 1 个 token，剩下的额度按到达顺序分给提示词。分块额度要明显大于最大并发请求数。批大小 B 不按“吞吐最大”选，而是按目标 SLO 下的 goodput 选。离线评估一批固定的提示词时，左补齐的矩形批更简单，位置按 `cumsum` 算、pad 的列遮掉即可。

为什么：在同一份请求流（3 个种子）上，重负载下连续批的 TTFT 中位数是静态批的约五分之一、吞吐高约一半，静态批约三分之一的位置在陪跑；分块 prefill 把最长卡顿从约 4 个单位降到 1，吞吐也略好（TTFT 3 份里 2 份变好）；过载时 goodput 在 B=8～16 之间最高，B=8 在 3 份请求流上更稳，B=32 吞吐更高、goodput 却掉了约一半。所有调度下每个请求的输出都和单独跑逐 token 相同。

实验边界：时间用的是成本模型，不是 GPU 实测，而且它没有给分块记重读 K、V 的开销；每份请求流只有 40 个请求，结果里包含了开头“暖机”和结尾“收尾”的阶段，不是长时间稳定运行的数字；拐点 K 换成 8、16、32，“连续批远好于静态和动态批”都成立，但分块额度太小时（K=8）TTFT 反而变差。请求长度是预先定好的，不靠 `<eos>` 停止；KV cache 按最大长度给每个槽位预留，没有考虑显存不够的情况。什么情况下要换：显存成为瓶颈时，先换[第 33 章](./kv-memory.md)的分页缓存；prefill 和 decode 互相干扰严重、而且有多台机器时，考虑把两者分开部署。

::: warning 常见误区
- **批处理会改变输出。** 只要掩码、位置和每个请求的 KV cache 都处理对，拼批前后每个请求的输出逐 token 相同（浮点舍入在 $10^{-6}$ 量级）。本章对所有调度都做了 `assert`。
- **左补齐只要遮掉 pad 就行，位置无所谓。** 对 RoPE 恰好无所谓，对按绝对位置查表的位置编码就错了；按 `cumsum` 算位置在两种情况下都对。
- **静态批的 TPOT 最好，所以它最好。** 它的 TPOT 好，是因为新请求根本进不来；TTFT 和吞吐都差得多。延迟要把 TTFT 和 TPOT 一起看。
- **批越大越好。** 吞吐一直涨，但过了拐点每一步都变长，TPOT 超标的请求越来越多，goodput 反而下降。
- **分块 prefill 一定更快。** 它消除的是卡顿；额度太小时，提示词送得太慢，TTFT 会变差。
:::

## 检查理解

1. 4 个提示词长度分别是 10、20、30、100，拼成左补齐的矩形批，白算的位置占多少？换成首尾相接呢？

   <details><summary>参考答案</summary>

   矩形是 $4 \times 100 = 400$ 个位置，真 token $10+20+30+100 = 160$ 个，白算 $240/400 = 60\%$。首尾相接排成 160 个位置，没有白算的 pad；代价是注意力要按段分开算，需要支持变长的注意力实现。

   </details>

2. 连续批里，一个新请求的 40 个 token 提示词和 7 个 decode 放在同一次前向。按本章的成本模型，这一步花多少个单位？分块额度 16 时，同样的提示词分几次送完？这几次一共出了多少个 decode token？

   <details><summary>参考答案</summary>

   不分块：$N = 47$，花 $47/16 \approx 2.9$ 个单位，出 7 个 decode token 和新请求的第一个 token。分块：每次先给 7 个 decode，剩下 9 个额度给提示词，40 个 token 要送 5 次（9、9、9、9、4），每次 1 个单位，共 5 个单位，出 $5 \times 7 = 35$ 个 decode token，最后一次还出了新请求的第一个 token。拿同样的 5 个单位比：不分块时第一步 2.9 个单位之后，剩下约 2 个单位再走 2 步、每步 8 个，一共约 $7 + 1 + 16 = 24$ 个。分块让新请求的第一个 token 晚了约 2 个单位，但其他请求一步也没有卡住，总产出也更多。

   </details>

3. 为什么静态批“白算”的比例在两档负载下都是约三分之一，而连续批是 0？

   <details><summary>参考答案</summary>

   静态批里，一批请求一起开始、一起结束，早结束的请求要陪着最长的那个跑完。白算的比例只取决于同一批里输出长度差多少（本章是 8～40 个 token，长提示词的请求只要 4～12 个），和请求来得快慢无关。连续批里请求结束就离开，空出的槽位马上给别人，没有陪跑。

   </details>

4. 第 8 节过载时，B=32 的吞吐比 B=16 高，goodput 却低了将近一半。如果把 TPOT 的目标从 1.5 放宽到 2.5，你预期最好的 B 会怎样变？

   <details><summary>参考答案</summary>

   B=32 时 TPOT 中位约 2.27、P90 约 3.4，放宽到 2.5 以后，有相当一部分请求能满足 TPOT 目标，goodput 会明显回升，最好的 B 会往 16～32 移；但 TTFT 的目标还在，而且 B=32 的 TPOT 中位已经接近 2.5，3 份请求流里不一定都是 32 更好，要实测。一般规律是：目标越松，越能用大批换吞吐；目标越紧，越要用小批保延迟。

   </details>
