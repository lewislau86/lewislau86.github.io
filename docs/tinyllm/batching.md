# 第 30 章：批处理与调度

[课程总览](./index.md) · [上一章](./speculative-decoding.md) · [下一章](./kv-memory.md)

::: info 本章状态：规划中
正文与 notebook 尚未完成。到目前为止每个请求都是单独处理的，本章处理第一个真正的服务问题：多个请求同时到达。预计覆盖：

- **为什么要批。** decode 每一步都要把全部权重从显存读一遍，读一次给一个请求用和给 16 个请求用，读的量一样。批量把这份开销摊薄。
- **三种批法。** 静态批处理要等够固定数量、且整批一起结束；动态批处理改成按时间窗口收；连续批处理按 token 步调度，哪个请求生成了停止符就立刻换上下一个。
- **等长之外的问题。** 变长序列靠 padding 拼成矩形，短序列的填充位置照样占算力；记录一批里多少位置是白算的。
- **chunked prefill。** 一个长提示词的 prefill 会占住整个前向，让所有正在解码的请求停一下；把它切块和 decode 拼在同一批里，能在 prefill 没做完时也让其他请求继续出字。
- **用什么衡量。** 首字延迟（TTFT）、每 token 延迟（TPOT）、吞吐，以及只有满足时延目标才算数的 goodput；[第 26 章](./inference-efficiency.md)的指标在这里第一次被用来比较调度策略。
:::

## 本章主线选择（待实验验证）

主线写一个最小的推理循环：请求带到达时间和目标输出长度，由固定的随机数生成器预先排好一批请求流（和[第 12 章](./tinyllm-model.md)的 batch 计划同一个思路），然后依次换成静态、动态、连续三种调度，在同一份请求流上比较每个请求的等待时间与总步数。指标以<strong>步数和白算的位置数</strong>为主，墙钟时间放在第二位并标清环境。

chunked prefill 单独做一组：同一个长提示词，一次 prefill 与切成 2、4 块并且和 decode 拼批，比较每一步的 prefill token 数与正在解码的请求能否继续出字。分块不改变数学结果，这一点用 KV cache 的等价性直接验证（[第 26 章](./inference-efficiency.md)已经用过同样的做法）。

批处理本身不解决显存：把更多请求同时放进来，KV cache 会先撑不住。下一章讲显存里的 KV 怎样分配和复用。
