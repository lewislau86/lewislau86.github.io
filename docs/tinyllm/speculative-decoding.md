## 问题：一次前向只换来一个 token

[第 28 章](./inference-efficiency.md)说过，单请求 decode 每生成一个 token，都要把全部权重读一遍，而矩阵乘只有一行。[第 30 章](./quantization.md)把权重变小，读一遍更快了，可还是“一次前向，一个 token”。

既然读一遍权重的代价已经付了，能不能让这一遍多算几个位置？难处在于自回归：第 $t+1$ 个 token 要等第 $t$ 个生成出来才能算。**投机解码**（speculative decoding）的办法是先猜：让一个便宜得多的**草稿模型**连续猜 γ 个 token，再让**目标模型**（就是我们真正想用的那个模型）把这 γ 个位置一次前向算完，逐个核对。猜对的直接收下，第一处猜错的地方换成目标模型自己的选择。猜得准，一次前向能前进好几个 token；猜不准，每轮也至少前进一个。

这一章用第 12 章的基线当目标模型，回答三个问题：贪心解码时，输出能不能保证一个字都不变；采样时，怎样才不改变输出的分布；在什么条件下真的能变快。

## 1. 可以回滚的 KV cache

目标模型就是第 12 章的基线：d=128、4 层、4 个头，训练 300 步，种子 0，和第 30 章种子 0 的模型完全相同。结构不变，只多了两件事：宽度、层数、头数可以设置（草稿模型要更小）；前向时可以带一个 KV cache，而且这个缓存要能**回滚**。

为什么要回滚？验证时，γ 个草稿 token 全部送进了目标模型，它们的 K、V 也就写进了缓存。被拒的那几个是错的，必须删掉，下一轮从正确的前缀接着算。第 28 章的缓存只会往后追加，这里加一个 `crop(n)`，只保留前 n 个位置：

<<< @/public/tinyllm/code/speculative-decoding.py#kv-cache

一次送进 T 个新 token、缓存里已有 `past` 个位置时，第 i 个新位置能看到缓存里的全部位置，以及它自己和它前面的新位置，所以掩码是一个向右平移了 `past` 格的下三角（`tril(diagonal=past)`）。只送一个 token 时，这个掩码全是 True，就是第 28 章的 decode。

先猜一下，8 个位置要多花多少时间？在本站的运行环境（4 核 aarch64 CPU）上，一次送进 1、2、4、8 个位置分别约 0.92、0.95、0.96、0.97 ms：计算量涨了 8 倍，时间只多了约 5%。这么小的模型，每次前向的时间主要花在“调用一次”本身：几十个小算子各启动一次、权重读一遍，真正做乘法的时间很少。GPU 上单请求 decode 也是这个形状，只是原因换成了显存带宽。

所以验证 γ 个草稿，和普通 decode 一步差不多贵。剩下的问题是：这几个位置上该放什么 token。

### 一轮：起草、验证、接受

<<< @/public/tinyllm/code/speculative-decoding.py#spec-greedy

逐行看：

- 目标模型的输入是 `seq[start:] + draft`。上一轮最后新增的那个 token 是目标模型自己的输出，还没送进过它，这一轮和草稿一起送。第一轮 `start=0`，整个提示词一起送，prefill 和第一轮验证合成了一次前向。
- 第 i 个位置的输出 `choice[i]` 是目标模型在“当前文本 + 前 i 个草稿”之后会选的 token，和草稿 `draft[i]` 比较。比到第一处不同就停：后面的草稿是接着一个错的 token 往下猜的，已经没有意义。
- 不管接受了几个，最后都加上 `choice[k]`：γ 个草稿全对（k=γ）时，它是最后一个位置白送的第 γ+1 个 token；第 k+1 个草稿不对时，它就是正确答案。所以每轮至少前进 1 个，最多 γ+1 个。
- `rollback(len(seq) - 1)` 删掉被拒草稿的 K、V。刚加上的最后一个 token 还没进缓存，下一轮再送。

为什么输出一定不变？接受的每个草稿 token 都等于目标模型在同一个前缀下的 argmax，补上的那一个也是 argmax，所以每个位置上的 token 都和普通贪心相同。唯一可能出岔子的是浮点误差：一次送 5 个位置和一次送 1 个位置，矩阵乘的分块方式可能不同，logits 的末几位会有差别，两个候选几乎打平时 argmax 有可能翻转。所以下面不靠推理，直接用 `assert out == ref` 检查。

先训一个小草稿：d=64、2 层、2 个头，参数约是目标的四分之一，按同样的 300 个 batch 训练。它必须和目标模型用同一个分词器，否则 token 编号对不上，没法逐个比较。用验证集里 12 首诗的第一句当提示词（训练时没见过），每个提示词生成 32 个 token：

## 4. 草稿要像目标，而不是写得好

α 只有 0.38。直觉是把草稿训得更好，但草稿被接受靠的不是“写得好”，而是“和目标想得一样”。按语料训练的草稿学的是语料，目标模型自己的偏好，包括它的错误，草稿并不知道。

换一个训练目标：让草稿去拟合目标模型在同样输入上的整个输出分布，用目标的 softmax 当软标签做交叉熵，等价于最小化 $\mathrm{KL}(p\,\Vert\,q)$。这就是**蒸馏**（[第 40 章](./distillation.md)会系统地讲），专门为投机解码蒸馏草稿的做法见 [DistillSpec](https://arxiv.org/abs/2310.08461)。训练函数多一个 `teacher` 参数，结构、步数、batch 都不变；3 个种子按同一组 batch 同步训练，老师的输出每个 batch 只算一次：

## 5. 起草多长

γ 越大，一轮可能前进得越多，但越往后的草稿越容易白猜。如果每个草稿被接受的概率都是 α、彼此独立，一轮前进的 token 数的期望是

$$
\tau = 1 + \alpha + \alpha^2 + \dots + \alpha^\gamma = \frac{1-\alpha^{\gamma+1}}{1-\alpha}
$$

（[Leviathan 等，2023](https://arxiv.org/abs/2211.17192)）。γ 趋于无穷时，τ 的上限是 $1/(1-\alpha)$。用蒸馏草稿扫一遍 γ，3 个种子，公式里的 α 取 γ=1 时测到的接受率：

γ=1 时每轮只有一个草稿，τ 就是 $1+\alpha$，和公式完全相同。γ 从 3 开始，实测比公式高：公式假设每个位置被接受的概率一样、彼此独立，实际文本里有的地方好猜（句末的“。”、`<eos>` 和下一首的开头往往连在一起），有的地方几乎猜不中，接受是一段一段成串出现的，第一个猜中以后，后面跟着猜中的机会更大。γ 超过 4 以后，τ 和目标前向次数都几乎不再变化。

前向次数省了，时间省了没有？每轮的代价是 γ 次草稿前向加 1 次目标前向。记草稿一次前向的耗时是目标的 c 倍，一轮验证又和一次普通 decode 差不多贵（第 2 节），那么相对普通 decode 的加速比约为

$$
\text{加速比} \approx \frac{\tau}{1 + \gamma c}.
$$

上面每一遍投机生成都记了墙钟时间，和同一批提示词上普通贪心的时间比：

<<< @/public/tinyllm/code/speculative-decoding.py#wallclock

在本站的运行环境上，草稿一次前向约是目标的 0.5 倍，实测加速比从 γ=1 的约 0.86 倍降到 γ=8 的约 0.32 倍：<strong>全都比普通贪心慢。</strong>代进公式，γ=4 时 $1.81/(1+4\times0.49)\approx 0.61$，实测约 0.52。差距一部分来自每段最后一轮多出来、又被截掉的 token：按实际用掉的前向算，平均 233 次前向产出 384 个 token，折合每次 1.65 个，代进公式是 0.56；剩下的大概是起草、比较这些 Python 代码本身的时间。

问题出在 c。草稿的参数只有目标的 27%，一次前向的时间却是目标的一半：两层也要启动一整套算子，输出层（64 × 4096）和嵌入表也省不了多少，第 2 节说过这么小的模型时间主要花在调用本身。真实系统里 c 是按时间算的，不是按参数：DeepMind 给 700 亿参数的 Chinchilla 配了一个 40 亿参数的草稿，参数比约 6%，但草稿只有 8 层（目标 80 层），每个 token 1.8 ms，目标 14.1 ms，c 约 0.13（[Chen 等，2023](https://arxiv.org/abs/2302.01318)）。决定 c 的是层数这类必须串行的部分。

## 6. 不用训练的草稿

草稿不一定是另一个模型。两种不用额外训练的做法：

- **只走目标模型的前几层**（自投机，self-speculative）：前 2 层的输出直接接最后的 RMSNorm 和输出层当草稿。
- **在已有文本里查**（prompt lookup）：找最近一次出现的“最后 2 个 token”，把它后面紧跟的几个 token 当草稿。查不到就不起草，这一轮退化成普通的一步 decode。


这一组只用了种子 0 的草稿，单个种子，只看大小关系。

- **前 2 层**每轮前进的 token 数是四种里最多的（2.04），α 也只比“文本里查”低：它本来就是目标模型的一部分，想法最接近。但它的成本 c 约 0.57，本机上和蒸馏草稿一样慢（约 0.56 倍）。真实的自投机方法如 [LayerSkip](https://arxiv.org/abs/2404.16710) 会在训练时加“早退”损失，让浅层的输出直接可用，而且起草和验证共用前几层的计算和 KV cache；这里没有训练、缓存也是分开的，只是一个未经训练的简陋对照。
- **文本里查**一旦查到，草稿的 α 最高（0.58），可是 339 轮里只有 49 轮查到了，每轮平均只前进 1.16 个 token。但它几乎不花时间，是四种里唯一比普通贪心快的，本机单次计时约快 1.1 倍。它适合输出大段重复输入的任务：改代码、引用原文的摘要、根据检索资料回答。在这里能查到，靠的是生成的诗里有重复的字词和句式（[第 30 章](./quantization.md)的生成样例里就有整句重复）。

## 7. 采样时：拒绝采样

贪心时“相同就接受”天经地义。采样时，草稿按自己的分布 q 抽出 x，目标的分布是 p；如果直接接受，输出就是从 q 采样，分布变了。[Leviathan 等（2023）](https://arxiv.org/abs/2211.17192)和 [Chen 等（2023）](https://arxiv.org/abs/2302.01318)给出的修正分两步：

1. 以 $\min\big(1, p(x)/q(x)\big)$ 的概率接受 x：目标比草稿更想要 x 时一定接受，没那么想要时按比例接受；
2. 被拒时，从 $\max(0, p-q)$ 归一化后的分布里重新抽一个：只在“目标想要、草稿给少了”的地方补。

为什么这样输出的分布恰好是 p？输出 x 有两条路：草稿抽中 x 并被接受，概率是 $q(x)\min(1, p(x)/q(x)) = \min\big(p(x), q(x)\big)$；或者被拒后重抽到 x。被拒的总概率是 $1-\sum_y \min(p(y), q(y)) = \sum_y \max(0, p(y)-q(y))$，正好是重抽分布的归一化常数，所以第二条路的概率是 $\max\big(0, p(x)-q(x)\big)$。两条路加起来，$\min(p, q) + \max(0, p-q) = p$。顺带得到：草稿被接受的概率是 $\sum_x \min(p(x), q(x))$，两个分布重叠得越多越好。

## 8. 收益的账

把加速比公式算一遍：给定接受率 α 和草稿成本 c，最好的 γ 是多少，最多能快多少。这里假设一轮验证和一次普通 decode 一样贵，没有算两个模型来回切换的开销，是上限：

<<< @/public/tinyllm/code/speculative-decoding.py#budget

```text
c=0.02  α=0.5: γ= 4 1.79×   α=0.7: γ= 8 2.76×   α=0.9: γ=19 6.37×
c=0.1   α=0.5: γ= 2 1.46×   α=0.7: γ= 4 1.98×   α=0.9: γ=10 3.43×
c=0.5   α=0.5: γ= 1 1.00×   α=0.7: γ= 1 1.13×   α=0.9: γ= 3 1.38×
```

- **c 和 α 一样重要。** c=0.5 时，即使 α=0.9 也只能快 1.38 倍；本章的草稿就在这一行。c=0.02 时，α=0.5 也能快 1.8 倍。
- **α 越大、c 越小，最好的 γ 越大。** 草稿又准又便宜时值得多猜几个；草稿贵时只猜一两个。
- **“验证几乎不要钱”有前提。** 这只在 decode 卡在带宽时成立，也就是单请求或小批量。批量大了，GPU 本来就算满了，每个请求多验证 γ 个位置就是实打实多算 γ 倍，收益变小甚至变成负的。EAGLE-3 的作者报告，批大小 64 时吞吐只提高 1.38 倍（[Li 等，2025](https://arxiv.org/abs/2503.01840)）。投机解码要放到[第 32 章](./batching.md)的批处理场景里重新算账。

真实系统里的草稿大多不是单独的小模型，而是想办法把 c 压到很小、把 α 提高：

| 草稿从哪来 | 做法 | 公开报告的结果 |
| --- | --- | --- |
| 单独的小模型 | 同一分词器的小模型，最好按目标蒸馏过 | Chinchilla 70B 配 4B 草稿，快 2～2.5 倍（[Chen 等，2023](https://arxiv.org/abs/2302.01318)） |
| 目标的前几层 | 训练时加早退损失，浅层直接出 token，起草和验证共用前几层 | 摘要任务最多快 2.16 倍（[LayerSkip](https://arxiv.org/abs/2404.16710)） |
| 额外的预测头 | 在最后一层的隐藏状态上加几个头，分别猜后面第 2、3…个 token，组成候选树一起验证 | Medusa-1 约 2.2 倍，Medusa-2 约 2.3～2.8 倍（[Cai 等，2024](https://arxiv.org/abs/2401.10774)） |
| 特征级草稿 | 一个小的 Transformer 层，输入目标模型的隐藏状态，自回归地猜 | EAGLE-3 报告 3.0～6.5 倍（[Li 等，2025](https://arxiv.org/abs/2503.01840)；前作 [EAGLE](https://arxiv.org/abs/2401.15077)） |
| MTP 模块 | 预训练时就训好的“多 token 预测”模块，推理时拿来起草 | DeepSeek-V3：第 2 个 token 的接受率 85%～90%，每秒 token 数 1.8 倍（[DeepSeek-AI，2024](https://arxiv.org/abs/2412.19437)） |
| 在已有文本里查 | 在提示词和已生成的文本里找相同的 n-gram | 不用训练，收益取决于输出和输入重合多少（[prompt lookup decoding](https://github.com/apoorvumang/prompt-lookup-decoding)） |

这些数字来自各自论文的设置（模型、硬件、批大小、任务都不同），不能直接互相比较；共同点是 c 都很小（一层或几个头），并且用目标模型的隐藏状态或蒸馏把 α 拉高。

| --- | --- | --- |

## 本章结论：TinyLLM 的选择 {#tinyllm-choice}

TinyLLM 的默认生成不开投机解码，但保留三样东西：<strong>可以回滚的 KV cache</strong>（`crop`），<strong>“起草 → 一次前向验证 → 接受到第一处不同”的循环</strong>，以及<strong>“输出必须和普通贪心逐 token 相同”的断言</strong>。后面任何改动生成路径的优化，都先过这条断言。

为什么默认不开：在本章的条件下（第 12 章基线当目标，CPU，单请求），模型草稿的成本 c 约 0.5，即使是蒸馏过的草稿（贪心 α≈0.45，采样 α≈0.77），贪心实测也比普通 decode 慢，采样时最多快 1.06 倍。唯一变快的是“在已有文本里查”（单个种子、本机单次计时约 1.1 倍），它不用训练、几乎不花时间，可以作为零成本的选项打开。

什么情况下要换：模型放到 GPU 上、单请求或小批量的 decode 卡在带宽，并且能拿到 c 在 0.1 以下的草稿（蒸馏过的小模型、一层的特征级草稿、模型自带的 MTP 模块）时，先在自己的任务上测 α，用 $\tau/(1+\gamma c)$ 选 γ，再实测墙钟时间；批量大了以后，到[第 32 章](./batching.md)的场景里重新算账。

::: warning 常见误区
- **投机解码是一种近似，会降低质量。** 贪心时输出和原来逐 token 相同（本章用 `assert` 检查了 12 段）；采样时用拒绝采样，输出的分布和目标模型相同。草稿只影响速度。
- **草稿越强越好。** 要的是“和目标想得一样”。蒸馏草稿和按语料训练的草稿结构完全相同，α 从 0.37 提到 0.45。另外草稿还得便宜，否则省下的目标前向会被草稿的前向吃掉。
- **目标模型的前向次数少了，就一定更快。** 本章用蒸馏草稿贪心解码、γ=4 时，目标前向从 384 次降到平均 233 次，墙钟时间却是原来的近两倍，因为每轮还要跑 4 次草稿，c 约 0.5。
- **γ 越大越好。** τ 很快就饱和了（本章 γ 超过 4 以后几乎不变），草稿的成本却随 γ 线性增加。
- **采样时直接接受草稿，或者被拒后从 p 重抽。** 前者等于从 q 采样，后者把草稿给多了的 token 算了两遍，两种都会改变输出的分布。
- **批量大时一样有效。** “验证几个位置和验证一个差不多贵”只在 decode 卡在带宽时成立。
:::

## 检查理解

1. 接受率 α=0.8、γ=4，每轮前进的 token 数期望是多少？草稿成本 c=0.05 时加速比的上限是多少？c=0.5 呢？

   <details><summary>参考答案</summary>

   $\tau = (1-0.8^5)/(1-0.8) = (1-0.32768)/0.2 \approx 3.36$。c=0.05 时加速比 $3.36/(1+4\times0.05) = 3.36/1.2 \approx 2.8$；c=0.5 时 $3.36/(1+2) \approx 1.12$。同样的接受率，草稿贵了，收益几乎全没了。

   </details>

2. 草稿全部被接受时，为什么还能多得一个 token？这个 token 要多花一次前向吗？

   <details><summary>参考答案</summary>

   目标模型这一轮的输入是“上一轮留下的 token + γ 个草稿”，共 γ+1 个位置，每个位置都输出一个下一个 token 的分布。最后一个位置（第 γ 个草稿）的输出就是第 γ+1 个 token 的预测。草稿全对时，这个预测的前缀全部正确，可以直接用。它是同一次前向顺带算出来的，不多花前向。

   </details>

3. 采样时，某个 token x 的草稿概率 $q(x)=0$，目标概率 $p(x)>0$。草稿永远抽不到 x，那输出里还会出现 x 吗？出现的概率对吗？

   <details><summary>参考答案</summary>

   会。x 只能通过“被拒后重抽”这条路出现：被拒的总概率是 $\sum_y \max(0, p(y)-q(y))$，重抽到 x 的条件概率是 $\max(0, p(x)-0)$ 除以这个总和，两者相乘正好是 $p(x)$。这也说明了为什么重抽分布必须是 $\max(0, p-q)$：它专门补草稿给少了（包括完全没给）的那部分。

   </details>

4. 第 3 节的验证循环里，为什么回滚到 `len(seq) - 1`，而不是 `len(seq)`？

   <details><summary>参考答案</summary>

   每轮最后加上的那个 token（`choice[k]`）是目标模型这一轮的输出，它本身还没有作为输入送进目标模型，缓存里没有它的 K、V。缓存里有效的只有前 `len(seq) - 1` 个位置：旧文本、上一轮留下的 token、以及被接受的 k 个草稿。下一轮把它和新草稿一起送进去。

   </details>
