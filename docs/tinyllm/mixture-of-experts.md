[第 3 章](./architecture-evolution.md)讲架构演进时说过，今天最大的那些模型，几乎都把前馈层换成了**稀疏专家**（Mixture of Experts，MoE）：DeepSeek-V3 有 6710 亿参数，每个 token 只用其中 370 亿；Kimi K3（2.8 万亿参数、每个 token 激活 1040 亿，[Kimi Team，2026](https://arxiv.org/abs/2607.24653)）、Qwen3 的大尺寸、小米的 MiMo-V2 系列，旗舰模型都是 MoE。

这一章是第五部分的最后一章，也是一个特殊的专题。前半部分在 TinyLLM 上把 MoE 搭起来，看清路由、负载均衡、专家分工这几件事；后半部分回答三个更实际的问题：

1. **MoE 是训练时就要决定的吗？** 已经训练好的稠密模型，能不能改成 MoE？
2. **MoE 和稠密模型用起来有什么不同？** 显存、速度、并发、微调。
3. **为什么越来越多的厂商选择 MoE？** 以小米的 MiMo 系列为例。

## 1. MoE 层长什么样

一个 MoE 层由两部分组成：

- **一组专家**：每个专家就是一个普通的 SwiGLU 前馈层，和主线模型里的那个一模一样。
- **一个路由器**：一个线性层，给每个 token 对每个专家打一个分，选分数最高的 `top_k` 个。

每个 token 只经过被选中的几个专家，它们的输出按分数加权相加：

<<< @/public/tinyllm/code/mixture-of-experts.py#moe

![左：稠密前馈层，每个 token 都经过同一个 SwiGLU。右：MoE 层，路由器给 8 个专家打分，每个 token 只选分数最高的 2 个专家，两个专家的输出按归一化后的分数加权相加；没被选中的专家不参与这次计算](/tinyllm/figures/moe-structure.svg)

怎么读这张图：左右两边的输入、输出形状一样，区别在中间。左边每个 token 都经过同一个前馈层；右边先由路由器给 8 个专家各打一个分，只有分数最高的 2 个专家（深色）参与计算，它们的输出按分数加权相加。所以 MoE 的参数是 8 份，每个 token 的计算只有 2 份。

`forward` 里的循环是“按专家分组”：先找出选了第 $e$ 个专家的那些 token，把它们一起送进这个专家，再把结果按权重加回各自的位置。真实的实现也是这个思路，只是用专门的 GPU 内核把分组、计算、写回做得更快。负载均衡的那几行，第 3 节再讲。

本章的 MoE：每层 8 个专家，每个和主线的前馈层一样大（中间宽度 170），每个 token 选 2 个，和 Mixtral 8x7B 是同一种做法。为了公平比较，再准备三个稠密模型：

<<< @/public/tinyllm/code/mixture-of-experts.py#configs

```text
稠密（主线）       总参数 163,904   每个 token 用到 163,904（100%）
稠密，激活参数相同    总参数 229,184   每个 token 用到 229,184（100%）
稠密，总参数相同     总参数 620,864   每个 token 用到 620,864（100%）
MoE 8 选 2    总参数 621,888   每个 token 用到 230,208（37%）
```

MoE 的**总参数**和第三个稠密模型几乎一样（62 万），可每个 token 只用到其中 23 万，和第二个稠密模型一样。这两个数决定了不同的东西：

- **总参数**决定模型能装多少东西，也决定要占多少显存（每个专家都得放在显存里，随时可能被选中）。
- **激活参数**决定每个 token 要算多少，也就是训练和推理的速度。

MoE 的全部吸引力就在这里：**用激活参数的计算量，换总参数的容量**。

先说结论：**在这个尺度上，MoE 没有赢。** 除了主线稠密模型稍差一点，其余几种的范围都互相重叠：MoE 和“激活参数相同”的稠密模型差不多，也没有达到“总参数相同”的稠密模型的水平。

这和大模型上的经验并不矛盾，而是说明 MoE 的好处需要条件：

- **每个专家只看到一部分数据。** 8 个专家选 2 个，平均每个专家只训练了四分之一的 token。240 步、约 25 万 token 的训练，对每个专家来说太少了。MoE 的优势在“数据多、训练长”的时候才显现。
- **模型太小。** 宽度只有 64，路由器能用来区分 token 的信息很少；专家也很小。

大规模的结果是另一番景象：Switch Transformer 在相同的计算量下，比对应的稠密模型训练快了好几倍（[Fedus 等，2021](https://arxiv.org/abs/2101.03961)）；DeepSeek-V3 每个 token 只用 370 亿参数，能力却和更大的稠密模型相当（[DeepSeek-AI，2024](https://arxiv.org/abs/2412.19437)）。所以本章的小模型实验用来看清 MoE 的**机制**，而“MoE 在大规模上更划算”这个结论，来自这些大规模的实验。

## 3. 负载均衡：为什么要让专家“雨露均沾”

上面的输出里，“不均衡”的 MoE 最忙的专家拿走了 43%、40%、44% 的选择，理想情况是每个专家 1/8，即 12.5%。

路由器是一起训练的。训练初期，哪个专家碰巧好一点，路由器就多选它，它被训练得更多，就更好，于是被选得更多……这是一个自我强化的过程，最后可能只有少数几个专家在干活，其余的形同虚设，叫作**路由崩塌**。

对质量来说，这在小模型上未必有害（“不均衡”的验证损失和别的差不多）。真正的问题出在**硬件**上。大模型训练时，不同的专家放在不同的卡上（专家并行）。一个 batch 里，最忙的那个专家决定了这一步要等多久：它拿走 44% 的选择，是平均值 12.5% 的 3.5 倍，它所在的那张卡就要算 3.5 倍的活，其余的卡都在等它。所以 MoE 必须做负载均衡。常见的做法有两种：

- **辅助损失**（[Switch Transformer](https://arxiv.org/abs/2101.03961)、[GShard](https://arxiv.org/abs/2006.16668)）：在损失里加一项“每个专家分到的比例 × 路由器给它的平均概率”的和（代码里的 `self.aux`），专家越不均衡，这一项越大。它能把最忙的专家压到 18%～19%，代价是它和语言模型损失“抢梯度”：系数大了，会伤害模型质量；系数小了，又压不住。
- **无辅助损失的偏置**（[Wang 等，2024](https://arxiv.org/abs/2408.15664)，DeepSeek-V3 采用）：给每个专家一个偏置，只加在“选谁”的分数上，**不参与输出的加权**，也不通过梯度学习。每一步看负载：太忙的专家，偏置减一点；太闲的，加一点（代码里的 `self.bias += self.gamma * sign(...)`）。它不碰损失函数，所以不和语言模型损失抢梯度。本章它把三个种子的最忙专家都压到了 14%，是三种方法里最均衡的。

在这个小模型上，三种方式的质量差别都在种子噪声以内；DeepSeek-V3 的技术报告在大规模上比较过，无辅助损失的方法在保持均衡的同时质量更好。本章其余部分的 MoE 都用偏置均衡。

![专家并行：8 个专家分在 4 张卡上，token 经第一次 all-to-all 发到专家所在的卡，算完后第二次 all-to-all 送回原来的卡；一层的时间由收到 token 最多的那张卡决定](/tinyllm/figures/expert-parallel.svg)

怎么读这张图：从上往下是一层 MoE 在 4 张卡上的执行顺序。每张卡上的 token 先由路由器选好专家（小框里的 E 几），第一次 all-to-all 把它们发到专家所在的卡，各卡算完，第二次 all-to-all 再送回去。中间一行写着每张卡收到多少 token：所有卡要一起等最忙的那张，这就是负载均衡要解决的问题。

还有一种更激进的做法是给每个专家设“容量上限”：一个 batch 里，每个专家最多接收多少个 token，超出的 token 直接跳过这个专家（Switch Transformer 的 capacity factor）。这能严格控制每张卡的计算量，代价是有些 token 没被处理。

分工非常清楚：**标点各有自己的专家**。第 0 层里，逗号全部交给专家 2，句号全部交给专家 7，`<eos>` 全部交给专家 6；汉字分散在各个专家上。第 1 层同样如此，句号和逗号共用专家 7，`<eos>` 交给专家 3，而专家 7 几乎不接汉字（1%）。

没有人告诉模型“标点要单独处理”，这是路由器自己学出来的：标点之后的下一个 token 很有规律（逗号后接下一句的第一个字，句号后接下一句或 `<eos>`），一个专门的专家就能把它处理好。大模型上的专家分工往往没有这么“可解释”，研究发现很多专家按词性、语法角色或输入的语言分工，而不是按“数学”“历史”这样的主题分工（[Jiang 等，2024](https://arxiv.org/abs/2401.04088) 对 Mixtral 的分析）。所以“专家”这个名字容易让人误解：它们不是各管一个学科的“专家”，而是路由器为了降低损失自己找到的一种分工。

## 5. 专题一：MoE 必须一开始就决定吗？

不一定。把稠密模型改成 MoE，有几条路。

### 稀疏升级：复制前馈层，接着训练

最直接的办法叫**稀疏升级**（sparse upcycling，[Komatsuzaki 等，2022](https://arxiv.org/abs/2212.05055)）：拿一个训练好的稠密模型，把每层的前馈层复制成 $N$ 份，作为 $N$ 个专家；新加一个路由器；然后接着训练。

在 TinyLLM 上试一下。第 2 节训练主线稠密模型时，在第 120 步存了一份参数和优化器状态。从这里升级：

<<< @/public/tinyllm/code/mixture-of-experts.py#upcycle

```text
升级前后，同一段输入的 logits 最大差 3.3e-06；验证损失 稠密 5.1219，升级后 5.1219
继续训练到第 240 步：稀疏升级 4.742（4.737～4.751）   稠密（主线） 4.748   从头训练的 MoE（偏置均衡） 4.721
专家之间的相似度：稀疏升级 0.484，从头训练 -0.000（1 表示完全相同，0 表示毫无关系）
```

![稠密模型训练到第 120 步后，每层的前馈层复制成 8 个一模一样的专家，新加一个路由器，Adam 的状态也一起复制，然后作为 MoE 接着训练到第 240 步。升级那一刻输出和稠密模型完全相同](/tinyllm/figures/moe-upcycle.svg)

- **升级那一刻，模型什么都没“忘”。** 8 个专家一模一样，不管路由器选哪 2 个、权重怎么分（两个权重加起来是 1），加权和都等于原来的前馈层。所以输出和稠密模型只差浮点误差（$3.3\times10^{-6}$），验证损失完全相同（5.1219）。之前的训练一点没浪费。
- **优化器状态也要复制。** 每个专家都拿到原来前馈层的 Adam 状态（$m$、$v$），路由器从零开始。[第 21 章](./training-loop.md)看到过，丢掉优化器状态会让训练跳一下。
- **之后的效果和从头训练差不多。** 在这个小模型上，稀疏升级（4.742）、稠密接着训练（4.748）、从头训练的 MoE（4.721）都在噪声范围内。
- **专家分化得慢。** 训练完以后，稀疏升级的 8 个专家之间平均相似度还有 0.48；从头训练的专家之间是 0，毫无关系。8 个专家从同一个起点出发，路由器要花很长时间才能让它们各自走开。[Drop-Upcycling](https://arxiv.org/abs/2502.19261) 发现，稀疏升级开头占优，但长期会被从头训练的 MoE 追上；它的改进是升级时把每个专家的一部分权重重新随机初始化，人为制造差异。

真实的例子：阿里的 Qwen1.5-MoE-A2.7B 就是从稠密的 Qwen-1.8B 升级而来的。官方的说法是，他们的初步实验发现从头训练 MoE 效率不高，难以达到预期的效果，于是从 Qwen-1.8B 出发初始化专家，再继续预训练；它用的是更细的专家，每层 64 个，其中 4 个是每个 token 都经过的共享专家（[Qwen 团队，2024](https://qwen.ai/blog?id=qwen-moe)）。具体怎样把一个前馈层切分、复制成这些专家，官方没有完全公开。

### 其他几条路

- **直接拆分，不复制**（[MoEfication](https://arxiv.org/abs/2110.01786)）：前馈层的中间神经元，对每个输入只有一小部分真正被激活。把这些神经元按“经常一起激活”分组，每组当一个专家，再训练一个路由器。它不增加参数，目的是**省推理计算**：论文里只用 10%～30% 的前馈层参数，就保持了 95% 以上的效果。
- **分头训练再合并**（[Branch-Train-MiX](https://arxiv.org/abs/2403.07816)）：从同一个稠密模型复制出几份，分别在代码、数学、百科等数据上继续训练，再把它们的前馈层合成一个 MoE 层（其余参数取平均），最后整体微调学路由。分头训练的那一步不需要卡之间通信，可以完全并行。
- **反过来，MoE 变稠密**：可以，但难得多。专家的知识要么蒸馏到一个稠密模型里，要么合并成一个前馈层，都会损失效果。

所以，MoE 不是“只能在训练开始时决定”的。但不管哪条路，**都需要继续训练**：路由器必须学，专家必须分化。没有“推理时一键切换成 MoE”这回事。

（“每 token 计算”按 $2\times$ 激活参数估算，“每 token 读权重”是批量为 1 时要从显存读出的权重字节数；两者都只是粗略的量级，没算注意力的 KV cache。）

对照 Qwen3-30B-A3B 和稠密的 Qwen3-32B，这两个模型要占的显存差不多（61 GB 对 66 GB），用起来却很不一样：

| 方面 | 稠密模型 | MoE 模型 |
| --- | --- | --- |
| **能不能装下** | 由参数量决定 | 由**总参数**决定；同样的速度，MoE 要多得多的显存 |
| **一个人用时生成快不快** | 每个 token 读全部权重（Qwen3-32B 约 66 GB） | 只读被选中的专家（Qwen3-30B-A3B 约 6.6 GB），在显存带宽受限的设备上快得多 |
| **很多人同时用时** | 吞吐随批量稳定增长 | 批量一大，几乎所有专家都要读（批量 64 时 98%），带宽上的优势基本消失；计算上的优势还在 |
| **部署** | 单卡或张量并行，较简单 | 大模型要专家并行，卡之间用 all-to-all 交换 token，还要处理负载不均 |
| **同样显存下的能力** | 通常更强 | 每个 token 用的参数少，同样显存下往往不如稠密模型 |
| **同样速度下的能力** | 较弱 | 通常更强：用激活参数的速度，换总参数的容量 |
| **微调** | 熟悉、稳定 | 全参微调要放下全部专家的参数和优化器状态；数据少时路由容易偏，常见做法是冻结路由器，或只用 LoRA 微调 |

几点补充：

- **个人电脑上跑 MoE**：本地推理通常一次只处理一个请求，正是 MoE 最占便宜的场景。只要内存装得下，像 Qwen3-30B-A3B 这样的模型生成速度接近一个 3B 的稠密模型。内存装不下时，有的推理框架支持把一部分专家放在 CPU 内存里，每个 token 只搬用到的那几个，速度会慢一些，但能跑起来。
- **云服务上的 MoE**：批量大的时候，带宽优势消失，但每个 token 的计算量仍然只按激活参数算，所以同样的硬件每秒能处理的 token 更多，单价也就更低。代价是部署更复杂，需要很多张卡一起放下全部专家。
- **结果的稳定性**：在设了专家容量上限的实现里（第 3 节），一个 token 会不会被某个专家丢掉，取决于同一批里还有哪些别的请求；同一个提示词，在不同的并发情况下，输出可能有细微差别。用户偶尔会感觉到“同样的问题，回答不完全一样”，这是原因之一（采样的随机性是另一个，[第 26 章](./generation.md)）。

一句话总结：**同样的显存，选稠密；同样的速度或同样的计算预算，选 MoE。** 手机、单卡这类显存紧张的场景，稠密模型往往更合适；云端大规模服务、追求单位成本的场景，MoE 更合适。

## 7. 专题三：为什么越来越多的厂商选择 MoE

先看事实。小米 MiMo 系列最早的模型 MiMo-7B（2025 年 5 月）是**稠密**模型，主打推理能力，从头预训练了 25 万亿 token（[小米 LLM-Core 团队，2025](https://arxiv.org/abs/2505.07608)）。2026 年 1 月的 MiMo-V2-Flash 换成了 **MoE**：总参数 3090 亿，每个 token 激活 150 亿；技术报告把它的目标描述为“快速、强推理和 agent 能力”，并说它的能力可以和 DeepSeek-V3.2、Kimi-K2 相比，总参数却只有它们的 1/2 和 1/3；推理时再用多 token 预测做投机解码（[第 30 章](./speculative-decoding.md)），解码速度最高提升 2.6 倍（[小米 LLM-Core 团队，2026](https://arxiv.org/abs/2601.02780)）。2026 年 3 月的 MiMo-V2-Pro 总参数 1 万亿、每个 token 激活 420 亿，也是 MoE，注意力按 1:7 混合全局注意力和滑动窗口注意力，上下文 100 万 token；4 月的 V2.5-Pro 沿用这一规模，9 月又发布了同为万亿参数级的 V2.6 系列（[小米 MiMo 模型更新日志](https://mimo.mi.com/docs/en-US/updates/model)）。DeepSeek、Qwen、Kimi 的旗舰模型同样都是 MoE。

技术报告没有专门解释“为什么选 MoE”。下面是从前几节的账出发的**分析**，不是小米的官方说法：

1. **训练的账。** 训练的计算量大致正比于“激活参数 × 训练 token 数”，模型能装下多少知识则更多取决于总参数。同样的算力预算，MoE 可以有大得多的总参数。当训练数据多达几十万亿 token 时，稠密模型的参数往往不够“装”，MoE 用同样的计算换来更大的容量。第 2 节的小模型实验看不到这一点，是因为数据量差了八九个数量级。
2. **推理的账。** 每个 token 的推理成本也正比于激活参数。推理模型和 agent 要生成很长的输出（思考过程、多轮工具调用），生成阶段的成本占了大头；激活参数少，每个 token 就便宜、就快。MiMo-V2-Flash 的定位“快速、强推理和 agent 能力”，正好对上这一点。
3. **部署的账。** MoE 要很多张卡才能放下，但在云端，这些卡同时服务成千上万的用户，显存的成本被摊薄了；剩下的就是每个 token 的计算成本，而这正是 MoE 省的。

反过来，MoE 也不是处处都好。显存紧张的场景（手机、个人电脑、单卡），总参数是硬门槛，稠密模型或者很小的 MoE 更合适；训练也更复杂，要处理负载均衡、专家并行通信、路由不稳定这些稠密模型没有的问题。MiMo 系列从稠密的 7B 起步、旗舰换成 MoE，和整个行业“小模型稠密、大模型 MoE”的分工是一致的。

## 8. TinyLLM 什么时候该用 MoE

把本章的实验和专题合起来：

- **TinyLLM 的主线保持稠密。** 在 16 万参数、几十万 token 的规模上，MoE 和激活参数相同的稠密模型打平，还多了负载均衡、更大的方差和更复杂的代码。
- **模型放大到参数或推理成本成为瓶颈时，再换 MoE。** 用偏置均衡；每个专家和原来的前馈层一样大、选 2 个是最简单的起点，更大的模型通常改用更多、更小的专家，再加共享专家（[DeepSeekMoE](https://arxiv.org/abs/2401.06066)）。
- **已经有训练好的稠密模型时，先试稀疏升级。** 它从稠密模型的效果出发，不浪费之前的训练；长期训练时考虑部分重新初始化，帮专家分化。

## 动手实验

1. **加长训练。** 把 `STEPS` 改成 720（约 3 分钟），重做第 2 节的稠密与 MoE 对照。MoE 和“激活参数相同”的稠密模型之间的差距变大了吗？
2. **细粒度专家。** 改成 16 个专家、每个中间宽度 85、每个 token 选 4 个（激活参数不变）。分工图有什么不同？
3. **加一个共享专家。** 在 MoE 层里加一个每个 token 都经过的 SwiGLU（中间宽度 170），路由专家改成选 1 个。逗号、句号还需要专门的专家吗？
4. **部分重新初始化的稀疏升级。** 升级时把每个专家一半的中间神经元重新随机初始化（对应的 `gate`、`up` 的行和 `down` 的列），专家之间的相似度和继续训练后的验证损失怎样变化？

## 本章结论：TinyLLM 的选择 {#tinyllm-choice}

TinyLLM 的主线保持**稠密**。MoE 作为对照变体：每个 Block 的前馈层换成路由器加若干个 SwiGLU 专家，每个 token 选 `top_k` 个，输出按归一化的分数加权求和；负载均衡用**无辅助损失的偏置**。模型放大、参数容量或推理成本成为瓶颈时再切换；已经有训练好的稠密模型时，先用**稀疏升级**，从稠密模型的效果出发接着训练。

理由来自本章的实验（代理模型、240 步、3 个种子）：MoE（8 个专家选 2 个）的验证损失和激活参数相同的稠密模型在同一个范围里，没有达到总参数相同的稠密模型的水平；不加均衡时最忙的专家拿走 40%～44% 的选择，偏置均衡把它压到 14%，辅助损失压到 18%～19%，三者的质量差别在噪声以内。路由器自己学会了让标点各用一个专家。稀疏升级时，输出和稠密模型只差 $3.3\times10^{-6}$，之后和从头训练的 MoE 打平，但专家之间的相似度还有 0.48，分化得慢。

这些选择在什么情况下要换：训练数据和模型都很大时，MoE 用同样的计算换来更大的容量，是更划算的选择；推理服务追求单位成本、并发很高时，MoE 每个 token 的计算更省；显存紧张、单卡或端侧部署时，稠密模型更合适。

::: warning 常见误区
- **MoE 是一群各管一个学科的专家。** 专家的分工是路由器为降低损失自己学出来的，往往按词性、标点、语法角色分，而不是按“数学”“历史”分。
- **MoE 一定比稠密模型好。** 本章的小模型上它没有赢；它的优势要在数据多、模型大时才显现。同样的显存，稠密模型通常更强。
- **MoE 省显存。** 它省的是计算；所有专家都要放在显存里，显存按总参数算。
- **MoE 在高并发时也只读一小部分权重。** 批量一大，几乎所有专家都会被某个 token 选中；带宽上的优势只在小批量时明显。
- **负载均衡是为了让模型更好。** 它主要是为硬件服务：最忙的专家决定了专家并行时的速度。本章不均衡的 MoE 质量并不差，但最忙的专家要算 3.5 倍的活。
- **MoE 只能在训练开始时决定。** 稀疏升级可以把训练好的稠密模型无损地改成 MoE，接着训练；Qwen1.5-MoE 就是这样来的。
:::

## 检查理解

1. MoE 的“总参数”和“激活参数”各决定什么？Qwen3-30B-A3B 和 Qwen3-32B 显存差不多，为什么前者一个人用时生成快得多？

   <details><summary>参考答案</summary>

   总参数决定模型能装多少东西和要占多少显存，所有专家都要放在显存里；激活参数决定每个 token 要算多少、读多少权重，也就是速度。Qwen3-30B-A3B 的总参数是 305 亿，和 Qwen3-32B 的 328 亿差不多，所以显存差不多；但它每个 token 只激活 33 亿参数，批量为 1 时每生成一个 token 只要读约 6.6 GB 的权重，Qwen3-32B 要读约 66 GB。生成阶段通常受显存带宽限制，读得少就快。

   </details>

2. 稀疏升级时，为什么升级那一刻模型的输出和原来的稠密模型完全一样？如果每个 token 只选 1 个专家、权重直接用路由器给的概率（不归一化），还一样吗？

   <details><summary>参考答案</summary>

   8 个专家都是同一个前馈层的复制，输出完全相同。每个 token 选 2 个专家，权重归一化后加起来是 1，加权和就等于这个前馈层本身的输出，所以和稠密模型一样。如果只选 1 个专家、权重直接用 softmax 概率（比如 0.15），输出就变成原来的 0.15 倍，和稠密模型不一样了；路由器刚初始化时概率接近 1/8，输出会被缩小很多，升级那一刻效果就会变差。所以稀疏升级时，要保证选中专家的权重加起来是 1。

   </details>

3. 不做负载均衡时，本章 MoE 的质量并不比做了均衡的差，为什么真实的大模型训练还一定要做？

   <details><summary>参考答案</summary>

   负载均衡主要是为硬件服务的。大模型训练用专家并行，不同的专家在不同的卡上；一步训练要等所有卡算完，最忙的专家所在的卡决定了这一步的时间。本章不均衡时最忙的专家拿走 44% 的选择，是均匀情况（12.5%）的 3.5 倍，那张卡要算 3.5 倍的活，其余的卡都在等。另外，路由崩塌时，大部分专家几乎不被训练，等于浪费了它们的参数。

   </details>

4. 一个团队要做手机上运行的端侧模型，另一个团队要做面向大量用户的云端 API。各自更适合稠密还是 MoE？为什么？

   <details><summary>参考答案</summary>

   端侧更适合稠密（或很小的 MoE）：手机内存小，模型的总参数是硬门槛；同样的内存，稠密模型的能力通常更强；单用户、小批量的场景下，MoE 读得少的优势也只体现在速度上，而端侧往往先受限于“装不装得下”。云端 API 更适合 MoE：成千上万的用户摊薄了“放下全部专家”的显存成本，剩下的主要是每个 token 的计算成本，而 MoE 只按激活参数计算；同样的预算能提供更大容量、更强的模型，或者同样的能力更低的单价。代价是部署要专家并行、处理负载均衡，更复杂。

   </details>
