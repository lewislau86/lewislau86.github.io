## 问题：训练时只见过 64 个位置

TinyLLM 的上下文是 64 个 token。[第 7 章](./position-encoding.md)第 6 节试过直接把长度加到 2 倍、4 倍：RoPE 对任何位置都算得出角度，模型能跑，但位置任务的准确率从 100% 掉到约 46%，连背过的唐诗损失也变高了。

大模型也有同样的问题，只是数字大得多。预训练绝大部分时间用较短的序列（注意力的计算量随长度平方增长），最后再扩展到长上下文：

- [Llama 3](https://arxiv.org/abs/2407.21783)从 8K 开始，分六个阶段逐步扩到 128K，长上下文这一段用了约 8000 亿个 token；每个阶段都要等两件事达标再进入下一个：短上下文的评测完全恢复，“大海捞针”（needle in a haystack）在当前长度上全部答对（第 3.4.2 节）。RoPE 的 base 从一开始就调到 500,000（第 3.2 节）。
- [Qwen3](https://arxiv.org/abs/2505.09388)预训练的第三阶段用几千亿个 token 把序列长度从 4096 扩到 32768，同时把 RoPE 的 base 从 10,000 调到 1,000,000；推理时再用 YaRN 等方法把能处理的长度提高到 4 倍（第 3.2 节）。

这些做法都在改同一个东西：RoPE 的旋转角度。这一章在第 17 章的代理模型上，把上下文从 64 扩到 256，比较四种做法：直接外推、位置插值、调大 base、YaRN，每种都看“不训练”和“用长序列训一小段”。除了按位置看验证损失，还用一个检索任务检查模型是不是真的用到了远处的信息，因为后面会看到，**验证损失看不出这一点**。

## 1. 实验对象，以及一个检索任务

模型是第 17 章的代理模型：词表 1024、宽度 64、2 层、4 个头（每个头 16 维，RoPE 有 8 对维度），上下文 64。这一章要训 3 个基线和二十几段扩展，用第 12 章的原尺寸太慢；损失的绝对值只在本章内部比较。

<<< @/public/tinyllm/code/long-context.py#proxy

只看验证损失，有一个问题：验证集是一串互不相干的诗拼起来的，远处的诗对预测下一个字几乎没用。模型就算完全不看 64 个位置以外的内容，损失也不会差多少；反过来，损失没崩，也说明不了它会用远处的信息。所以另加一个检索任务，和大模型常用的 passkey retrieval、“大海捞针”同一个思路：

![检索任务：一行唐诗文本里，某个位置换成字母 k，倒数第二个位置换成 bos，模型要在 bos 后面预测出 k；字母和 bos 之间隔 d 个位置](/tinyllm/figures/lc-task.svg)

怎么读这张图：橙色格子是字母，蓝色格子是查询；模型要在查询后面写出那个字母，注意力必须跨过 d 个位置找到它。字母从 a～p 里选，唐诗语料里从来不出现，靠蒙只有 1/16 的机会猜对。

<<< @/public/tinyllm/code/long-context.py#data

```text
训练流 296,250 个 token，验证流 15,892 个 token；检索用的字母 16 个，语料里一次也没出现过
```

训练时，四分之一的行带检索任务，有两种放法：

- **基线**（`far_first=False`）：放一个字母，之后在 max_dist 个位置以内随机插几处查询。一行有好几个目标，基线才学得会（只插一处的话，一行只有一个目标，信号太弱，基线学不会）；后面的查询可以从前面的查询抄，所以真正跨过的距离多数比 max_dist 短。
- **扩展**（`far_first=True`）：第一处查询离字母正好 d 个位置，d 在 3 到 max_dist 之间均匀，其余查询都排在它后面。这样，max_dist=254 时，每行都有一个目标真的要跨过 d 个位置，d 有一半以上超过 112。

测试时每行只放一个字母、一处查询，查询固定在倒数第二个位置，距离 d 取 16、48、112、176、240，每个距离测 96 行。

## 3. 四种改法：改的都是旋转角度

[第 7 章](./position-encoding.md)的 RoPE 把每个头的维度两两配对，第 i 对按速度 $\theta_i = \text{base}^{-2i/d_\text{head}}$ 旋转，位置 m 转过 $m\theta_i$。第 0 对转得最快，最后一对最慢。先看一个数：**训练时每一对维度最多转了几圈**。

<<< @/public/tinyllm/code/long-context.py#rope-variants

```text
每一对维度最多转几圈（最后一个位置的角度 ÷ 2π）；第 0 对转得最快
训练（64 个位置）    10.03   3.17   1.00   0.32   0.10   0.03   0.01   0.00
直接外推（256）     40.58  12.83   4.06   1.28   0.41   0.13   0.04   0.01
位置插值（256）     10.15   3.21   1.01   0.32   0.10   0.03   0.01   0.00
调大 base（256）  40.58  10.53   2.73   0.71   0.18   0.05   0.01   0.00
YaRN（256）     19.17   3.90   1.02   0.32   0.10   0.03   0.01   0.00
```

![四种方案下每一对维度转过的圈数：训练时第 0 对转了约 10 圈，第 3 对以后不到 1 圈；直接外推每一对都转到 4 倍，位置插值和训练时一样，调大 base 只有第 0 对不变、慢的几对变慢，YaRN 保留第 0 对的一部分，其余和位置插值相同](/tinyllm/figures/lc-turns.svg)

怎么读这张图：灰色柱和虚线是训练时转到过的最大角度；彩色柱高过虚线，就说明这一维在 256 个位置里会转到训练时没见过的角度。纵轴是对数坐标。

这张表解释了直接外推为什么会失败，也解释了另外三种改法各在做什么：

- **训练时转满一圈以上的维度不怕外推。** 第 0 对在 64 个位置里已经转了 10 圈，0 到 2π 的每个角度都见过很多次，位置再往后，角度只是绕回来，没有新东西。第 1、2 对也至少转满了一圈。
- **没转满一圈的维度才是问题。** 第 3 对在训练时只转了 0.32 圈，角度只覆盖了 0 到 2π 的三分之一。直接外推到 256，它转到 1.28 圈，大半角度从来没见过，这些维度上 q、k 的点积是没被训练约束过的值。第 4～7 对也一样。第 7 章说“没见过的距离抢走注意力权重”，具体就发生在这几维上。
- **位置插值（PI）**：把位置除以 s=4，256 个位置压回训练时的角度范围，每一维都不超出。代价是分辨率：相邻两个 token 的角度差只剩原来的四分之一，最快的那几维本来靠大角度差分清“紧挨着的是谁”，现在分不清了。
- **调大 base**：把 base 换成 $\text{base}\cdot s^{d_\text{head}/(d_\text{head}-2)}$（NTK-aware 的公式）。指数的取法让最慢的一维正好变慢 s 倍、第 0 对完全不变，中间按几何级数过渡。代价有两头：第 1、2 对也变慢了，同样的距离对应的角度变了，近处的位置关系也要重新适应；第 3～5 对仍然超出训练时的范围（0.71 对 0.32 圈、0.18 对 0.10 圈、0.05 对 0.03 圈）。
- **YaRN**：按“训练长度内转了几圈”分段处理：转了 β 圈以上的维度不动，不到 α 圈的维度做插值，中间线性过渡；另外把注意力分数乘一个温度 $(0.1\ln s + 1)^2$（q、k 各乘一次 $0.1\ln s+1$）。论文对 Llama 推荐 α=1、β=32。这里有一个缩小规模才看得到的问题：训练长度只有 64，最快的一维也只转了 10 圈，不到 β=32，所以第 0 对只保留了约 30%，其余几乎都和位置插值一样。YaRN 的作者也写了，α、β 要按模型逐个调（第 3.2 节）。

![四种方案在 256 个位置上的表现：上排是按位置的验证损失，下排是检索准确率随距离的变化；左列不训练，右列在长度 256 上训 150 步](/tinyllm/figures/lc-results.svg)

怎么读这张图：上排是损失，下排是检索，灰底是训练长度以内；左列是这一节，右列是第 5 节。每个点是 3 个种子的平均。

- **直接外推**：位置 0–63 的损失是 4.461，就是基线本来的水平；64–127 升到 4.744，128 以后升到 6.1 以上。检索在 48 的距离上就只剩 0.41，再远接近瞎猜（1/16 约是 0.06，这里 0.1～0.26）。距离 48 本身在训练长度以内，可查询前面有 254 个位置，大部分距离训练时没见过，它们的分数抢走了注意力。
- **调大 base**：损失撑到 191 才明显升（5.078 → 5.503），和上一节的表一致：超出的维度超得没有直接外推多，要到更远的位置才转到没见过的角度。但 0–63 的损失也从 4.461 升到 5.085：第 1、2 对变慢了，近处的位置关系也变了。检索越远越差。
- **位置插值**：损失在所有位置都约 5.9，连 0–63 也从 4.461 变成 5.851：位置分辨率降到四分之一，近处的词序乱了。检索在 112 以内还有 0.86 以上，到 240 是 0.57：找一个唐诗里不出现的字母，主要靠内容匹配，对位置精度要求不高。
- **YaRN**：损失和位置插值差不多（它在这里几乎就是位置插值），检索却好得多，240 的距离上 0.93。去掉温度以后，检索掉到 0.53，和位置插值几乎一样（0.57）：在这个设定下，YaRN 的检索优势几乎全来自温度。上下文长了 4 倍，softmax 要分给更多的位置，分数乘一个大于 1 的系数，让注意力重新集中到匹配的那个位置上。

所以不训练的时候，没有一种方法两头都好：直接外推保住了近处的语言能力、丢了远处；插值类保住了远处的检索、丢了近处的语言能力。

## 5. 用长序列训一小段

每种方案都从基线出发，在长度 256 上再训 150 步。每个 batch 4 行，看的 token 数和基线的一个 batch 相同；学习率 warmup 10 步到 3e-3，再线性降到 0。四分之一的行带检索任务，用第 1 节的“扩展”放法，第一处查询离字母 3～254 个位置。

150 步就把所有方案拉回来了（上一张图的右列）：

- **检索四种方案都是全对。** 训练数据里有足够多真正跨越远距离的检索目标，没见过的角度很快就学会了。
- **损失是不压缩位置的两种更低。** 192–255 位置：调大 base 4.377、直接外推 4.395，YaRN 4.458、位置插值 4.509。插值类把近处的分辨率压缩了，150 步还没完全补回来。
- 四组位置里 0–63 最高，是因为这一组包含每段开头那些几乎没有上文的位置；后三组之间相差不到 0.05。

在这个规模上（s=4、2 层模型），直接外推加一段有远距离依赖的训练，效果并不差。[位置插值的论文](https://arxiv.org/abs/2306.15595)在 LLaMA 上看到的情况不同：直接外推的模型训了一万步，passkey 检索的有效长度只从 2048 涨到 2560，位置插值 200 步就能在整个扩展后的长度上检索（表 4）。那里的扩展倍数和模型都大得多，本章的实验复现不出这个差别。下一节看的是另一个条件：训练数据本身。

## 6. 损失看不出训练数据里有没有远距离依赖

上一节扩展用的数据里，每一行检索都有一个真正跨越远距离的目标。如果长序列虽然长，依赖却都在近处呢？真实数据里很常见：把很多短网页拼成一条长序列，长度够了，可远处的内容和当前位置没关系。把扩展时检索的 max_dist 限制在 60（和基线训练时一样），对直接外推和 YaRN 各做一次：

怎么读这张图：左图是位置 192–255 的验证损失，每种方案两根柱子，分别是扩展数据里有远距离依赖和只有近处依赖；右图是检索准确率随距离的变化，实线是有远距离依赖，虚线是只有近处依赖。

两点：

- **只看损失，两种数据完全分不出来。** 直接外推在两种数据下，四组位置的损失几乎一模一样（192–255 都是 4.395）；112 以上距离的检索却从全对掉到 0.81～0.95。损失衡量的是“平均来说预测得好不好”，远距离的依赖在验证集里本来就很少，影响不了平均数。所以评估长上下文一定要单独测检索：Llama 3 用“大海捞针”判断每个阶段是否达标，就是这个原因。
- **插值类方法能把近处学会的能力搬到远处。** YaRN 在只有近处依赖时，240 的距离上仍有 0.97：它把远处压回了见过的角度，基线在 60 以内学会的检索直接就能用。直接外推要靠数据里的远距离例子去学那些没见过的角度，例子少了就学不全。这是插值类方法省数据的一个原因，[YaRN](https://arxiv.org/abs/2309.00071)报告它比之前的方法少用 10 倍的 token、2.5 倍的训练步数。

真实的长上下文训练因此有两条对数据的要求：长样本里要有真正的远距离依赖（整本书、整个代码仓库、长对话，而不只是把短文档拼起来）；拼接短文档时用第 14 章的文档掩码，免得模型学会“远处都是无关内容”。Llama 3 说文档掩码在普通预训练里影响不大，在很长序列的继续预训练里很重要（第 3.2 节）。本章的实验没有加文档掩码。

最后看一下训得更久会怎样。从基线重新开始，把扩展训练加长到 450 步（学习率按 450 步重排），对直接外推和 YaRN 各做一次：

```text
直接外推+450 步     损失（位置 0-63 / 64-127 / 128-191 / 192-255） 4.386 4.327 4.290 4.316   检索准确率（距离 16/48/112/176/240） 1.00 1.00 1.00 1.00 1.00
YaRN+450 步     损失（位置 0-63 / 64-127 / 128-191 / 192-255） 4.417 4.345 4.315 4.340   检索准确率（距离 16/48/112/176/240） 1.00 1.00 1.00 1.00 1.00
```

## 7. 代价：上下文长 4 倍，要多花多少

<<< @/public/tinyllm/code/long-context.py#cost

```text
长度   64：KV cache     64 KiB/条  每 token 计算量 稠密 163,584 + 注意力 8,192（注意力占 5%）
长度  256：KV cache    256 KiB/条  每 token 计算量 稠密 163,584 + 注意力 32,768（注意力占 17%）
长度 1024：KV cache   1024 KiB/条  每 token 计算量 稠密 163,584 + 注意力 131,072（注意力占 44%）
[计时，本机] 1024 个 token 切成长   64 的段，一次前向 2.3 ms
[计时，本机] 1024 个 token 切成长  256 的段，一次前向 3.2 ms
[计时，本机] 1024 个 token 切成长 1024 的段，一次前向 5.1 ms
```

两件事：

- **KV cache 跟着长度线性涨。** 每条序列要存每一层、每个位置的 K 和 V（第 28 章），长度 4 倍，显存就是 4 倍；推理时能同时服务的请求数相应变少（第 32、33 章）。
- **注意力的计算量占比随长度上升。** 每个 token 要和前面所有位置算分数、加权求和，每个 token 的注意力计算量和长度成正比，整条序列就是平方。同样 1024 个 token，切成长 1024 的段比切成长 64 的段，一次前向在本机慢了约一倍。每层稠密部分约 $12d^2$，注意力约 $T\cdot d$，两者之比约 $T/(12d)$：TinyLLM 的 d 只有 64，256 个位置时注意力就不能忽略；d=4096 的模型要到几万个位置才和稠密部分相当。这也是长上下文放在预训练最后、分阶段扩的原因（Llama 3 第 3.4.2 节），注意力内核（第 29 章）在长序列上更要紧。

## 动手实验

1. **温度取多大。** 在 `rope_angles` 里把 YaRN 的温度系数从 $0.1\ln s+1$ 换成 $0.05\ln s+1$ 和 $0.2\ln s+1$，重做第 4 节。检索和损失各往哪边变？
2. **按规模调 α、β。** 把 YaRN 的 β 从 32 改成 4（训练长度只有 64，最快的一维转 10 圈），让第 0 对完整保留、第 1 对大部分保留。不训练时位置 0–63 的损失能不能更接近直接外推的 4.461？检索会不会变差？
3. **完全不放检索行。** 把 `extend` 里调用 `make_batch` 时的 0.25 改成 0，扩展时只用拼接起来的唐诗训练。距离 16 的检索还剩多少？和[第 37 章](./continued-pretraining.md)的遗忘有什么关系？
4. **更大的倍数。** 把目标长度改成 1024（s=16），扩展训练仍然 150 步。直接外推还能在 1000 左右的距离上全对吗？训练 150 步时，长度 1024 的一行要多少时间？

## 在真实模型里

transformers 把几种上下文扩展都写成“换一组 `inv_freq`”：配置里 `rope_parameters` 的 `rope_type` 选方法，`factor` 是本章的 s，模型代码一行不改。下表的链接都指向 Hugging Face transformers 的固定版本 `v5.21`，精确到行。读代码时可以先跳过缓存、掩码、并行这些工程细节，只看和本章对应的那几行。

| --- | --- | --- |
| 位置插值 | [`_compute_linear_scaling_rope_parameters`](https://github.com/huggingface/transformers/blob/v5.21/src/transformers/modeling_rope_utils.py#L133-L190) | `inv_freq /= factor`：把每一维的旋转速度除以 s，等价于本章把位置除以 s |
| 调大 base（动态） | [`_compute_dynamic_ntk_parameters`](https://github.com/huggingface/transformers/blob/v5.21/src/transformers/modeling_rope_utils.py#L269-L342) | `base * ((factor * seq_len / max_position_embeddings) - (factor - 1)) ** (dim / (dim - 2))`：随当前长度调 base，不超过训练长度时不变；`factor=1`、长度为 4 倍时就是本章的 base·4^(d/(d−2)) |
| YaRN | [`_compute_yarn_parameters`](https://github.com/huggingface/transformers/blob/v5.21/src/transformers/modeling_rope_utils.py#L345-L483) | `beta_fast=32`、`beta_slow=1` 按“训练长度内转几圈”划出不动、插值和过渡三段，和本章相同；过渡段按维度序号线性（论文按圈数线性），边界取整；`attention_factor = 0.1 * ln(factor) + 1` |

## 本章结论：TinyLLM 的选择 {#tinyllm-choice}

TinyLLM 扩展上下文用<strong>本章的选择</strong>：YaRN（带温度），s 取目标长度 ÷ 训练长度，α、β 按训练长度调（训练长度很短时，β 要相应调小）；扩展后在目标长度上训一小段，学习率从较小的峰值线性降到 0，训练数据里要有真正跨越远距离的依赖，拼接的短文档加文档掩码；评估时同时看按位置的验证损失和不同距离上的检索准确率，两者都达标才算扩展成功，并检查短上下文的表现没有掉。

为什么：在第 17 章的代理模型上（3 个种子），不训练时直接外推在 128 以后损失升到 6.1 以上，检索在 48 的距离就只剩 0.41；位置插值和 YaRN 的损失在所有位置都约 5.9～6.0，但 YaRN 的检索在 240 的距离上仍有 0.93，去掉温度只有 0.53。用含远距离依赖的数据训 150 步后，四种方案的检索都是全对，直接外推和调大 base 的损失比插值类低 0.06～0.13，训到 450 步时 YaRN 和直接外推的差距缩小到 0.024。扩展数据里只有近处依赖时，两种方案的损失和有远距离依赖时几乎一样，但直接外推在 112 以上距离的检索掉到 0.81～0.95，YaRN 仍在 0.97 以上。选 YaRN，是因为它在不训练时最能用、对扩展数据里远距离例子的多少最不敏感；代价是训练初期的损失略高。

实验边界：模型只有 2 层、每头 16 维，只有 8 对 RoPE 维度，从 64 扩到 256（s=4），和大模型从 4K、8K 扩到 128K 差得很远，PI 论文里直接外推训练很慢的现象这里没有复现；YaRN 用的是论文为 Llama 推荐的 α、β，没有按本章的规模调；检索任务是合成的（找一个语料里不出现的字母），比真实的长文档问答简单得多，只能说明注意力能不能跨过这段距离，每个距离只测 96 行、3 个种子，相差几个百分点的不能当真；验证集是互不相干的诗拼起来的，几乎没有远距离依赖，所以按位置的损失只能说明“没崩”；扩展训练只有 150～450 步、峰值学习率只试了 3e-3，没有试分阶段扩展。什么情况下要换：能保证扩展数据里有大量真正的长距离依赖、又在意语言建模损失时，调大 base 或直接外推加训练在本章里损失最低；能从头预训练时，一开始就用较大的 base（Llama 3 的 500,000），后面扩展要改的就少。

::: warning 常见误区
- **RoPE 能算任意位置，所以模型能处理任意长度。** 能算不等于算得对；训练时没转满一圈的维度，在更远的位置会转到没见过的角度。
- **验证损失没崩就说明长上下文能用。** 本章扩展数据里只有近处依赖时，损失和有远距离依赖时一模一样，远距离检索却掉了；要用检索类的任务单独检查。
- **只要把序列拼长就是长上下文数据。** 依赖都在近处的长序列，教不全模型用远处的信息；直接外推对这一点最敏感。
- **位置插值不需要训练。** 它不训练时远距离检索还行，可近处的分辨率丢了，语言建模的损失从 4.5 升到 5.9；要配一小段训练。
- **YaRN 只是“分段的插值”。** 本章不训练时，去掉温度的 YaRN 检索和位置插值差不多，温度才是它在远处检索好得多的主要原因。
- **YaRN 的 α、β 照抄论文就行。** 它们是按 Llama 的训练长度和 head 维度挑的；本章训练长度只有 64，照抄后 YaRN 的插值部分几乎退化成位置插值。
- **上下文长 4 倍，开销也是 4 倍。** KV cache 是线性的，注意力的计算量是平方的；短的时候不明显，越长越占大头。
:::

## 检查理解

1. 本章的模型每个头 16 维、base 10000，训练长度 64。为什么第 0 对维度外推到 256 个位置没问题，第 3 对却有问题？

   <details><summary>参考答案</summary>

   第 0 对每个位置转 1 弧度，64 个位置转了约 10 圈，0 到 2π 的每个角度都见过很多次，位置再往后只是重复这些角度。第 3 对的速度是 $10000^{-6/16}\approx 0.032$ 弧度，64 个位置只转了 0.32 圈；外推到 256 时转到 1.28 圈，大半角度训练时从未出现，这些维度上的注意力分数没有被约束过。

   </details>

2. 不训练时，位置插值在 112 的距离上检索有 0.86，可位置 0–63 的损失从 4.461 变成了 5.851。为什么它能找回远处的字母，却连近处的诗都写不好？

   <details><summary>参考答案</summary>

   位置插值把每个位置除以 4，相邻两个 token 的角度差只剩原来的四分之一，靠快速旋转的维度分辨“紧挨着的是哪个字”的能力被削弱了，近处的词序乱了，语言建模变差。找字母主要靠内容：字母在唐诗里从不出现，查询只要找到“和别的 token 都不一样的那个”，不需要精确知道它在哪，所以压缩后的位置大体够用。

   </details>

3. 一个团队把模型从 8K 扩到 32K，训练数据是把大量几百个 token 的网页拼成 32K 长的序列，不加文档掩码，用直接外推。验证损失看起来很正常。按本章的结果，你预计会出什么问题？怎么改？

   <details><summary>参考答案</summary>

   远距离的检索（大海捞针）很可能不行：数据里几乎没有跨越几千个 token 的依赖，直接外推又要靠这样的例子去学没见过的角度；验证损失看不出这一点（本章两种数据的损失一模一样）。不加文档掩码还会让模型习惯“远处都是无关内容”。改法：换成插值类方法（YaRN 或按波长分段）；数据里加入真正的长文档（书、代码仓库、长对话），短网页拼接时加文档掩码；评估加上不同距离的检索测试。

   </details>

4. 模型宽度 d=4096、32 层，FP16 存 KV cache（不考虑 GQA）。上下文从 8K 扩到 128K，每条序列的 KV cache 从多少变成多少？

   <details><summary>参考答案</summary>

   每个位置每层存 K、V 各 4096 个数，2 字节一个：2 × 32 × 4096 × 2 = 512 KiB。8K 个位置是 4 GiB，128K 是 64 GiB。所以真实的大模型都会用 GQA（第 6 章）减少 K、V 的头数，再配合第 33 章的分页管理。

   </details>
