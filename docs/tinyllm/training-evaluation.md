前面几章，每次训练完我们都看同一个数：验证损失。它降下来了，就说模型学到了东西；两个设置比较，谁的验证损失低，谁就更好。

这个习惯有两个隐含的前提。第一，**代码是对的**：损失降下来，是因为模型学会了写诗，而不是因为某个 bug 让它找到了捷径。第二，**这个数是准的**：验证集换一批诗，结论不会变。本章分别检验这两个前提，最后再问一个问题：验证损失低，模型写出来的诗就好吗？

## 1. 一条“好看”的曲线

先看一个例子。下面两份代码只差一个参数：第二份的注意力漏了因果掩码，每个位置都能看到它后面的 token。各训练 240 步：


漏了因果掩码的那份，验证损失是 0.111，比正确的代码低了 40 多倍。如果只看这个数，它是一个惊人的突破。让两个模型各写几行：

正确的代码写得还不通顺，但已经有了五言诗的样子；“突破”的那份只会重复同一个字。

原因不难想通。训练时，第 $t$ 个位置要预测的正是第 $t+1$ 个 token，而没有因果掩码，第 $t$ 个位置能直接看到第 $t+1$ 个 token，抄过来就行。一段 64 个 token 里，63 个位置都能看到答案，只有最后一个位置看不到（答案在这段之外）。乱猜的损失是 $\ln 1024 = 6.93$，平均到 64 个位置上，约 $6.93/64 \approx 0.11$，和测到的 0.111 几乎一样。生成时就没有答案可抄了，模型从没学过真正的预测，只能胡写。

这个例子说明：**损失低得不合理，往往不是好消息。** 下面系统地看一遍。先剧透一张图：后面要埋的几个 bug 里，有两个的曲线都比正确的代码“好看”。

![正确的代码训练 240 步，验证损失 4.733。漏了因果掩码时训练、验证损失都降到 0.11，标签没错位时降到 0.003，看起来比正确的代码好得多；每步同一个 batch 时训练损失降到接近 0，验证损失却是 8.65](/tinyllm/figures/eval-pretty-curves.svg)

怎么读这张图：每种颜色是一份代码，曲线是训练损失，右侧的菱形是最终的验证损失，灰色虚线是均匀乱猜的 ln V。正确的代码最后验证损失 4.733；降得更低、看起来更好的那几条，全是有 bug 的。“损失降得越低越好”这个直觉在这里完全失效，下一节逐个拆开看。

## 2. 六个常见的 bug

除了漏因果掩码，再埋五个同样常见的 bug。每个都只是一行之差：

<<< @/public/tinyllm/code/training-evaluation.py#bugs

| bug | 错在哪里 | 真实代码里常见的样子 |
| --- | --- | --- |
| 漏了因果掩码 | 注意力能看到后面的 token | 自己写注意力时忘了加掩码；或者调用时漏了 `is_causal=True` |
| 标签没错位 | 目标用了 `x` 而不是 `y` | 自己构造标签时没有错开一位；或者在模型里又错位了一次 |
| 双重 softmax | 把概率当成 logits 传给 `cross_entropy` | 模型输出已经过了 softmax，又交给内部会做 `log_softmax` 的损失函数（[第 15 章](./language-model-loss.md)） |
| 忘了清梯度 | 每步没有 `zero_grad` | 重构训练循环时漏掉了一行 |
| 每步同一个 batch | 取 batch 时写成了第 0 行 | 索引写错；数据迭代器每步都被重新创建 |
| 初始化放大 10 倍 | 词嵌入的标准差多乘了 10 | 初始化函数被调用了两次；或者换了初始化方案没有核对尺度 |

## 3. 六项检查

下面这六项检查，每一项都很便宜，都能给出“通过 / 不通过”：

<<< @/public/tinyllm/code/training-evaluation.py#checks

一项一项看它们检查的是什么：

**① 初始损失。** 随机初始化的模型对下一个 token 应该几乎没有偏好，损失接近均匀乱猜的 $\ln V$（这里是 $\ln 1024 = 6.93$）。明显高于它，说明初始的 logits 太大、太自信；明显低于它，说明模型还没训练就“知道”了什么，这在正常情况下是不可能的。阈值取 $\pm 1$，是因为 TinyLLM 的输入嵌入和输出层共享权重（[第 5 章](./embeddings-and-output.md)），一开始就略偏向“预测输入的那个 token 自己”，正确的代码初始损失是 7.43，比 $\ln V$ 高 0.5。

**② 单 batch 过拟合。** 拿一个 batch 反复训练 100 步。16 万参数的模型背下 1024 个 token 毫不费力，损失应该降到接近 0。降不下去，说明前向、损失、反向、更新这条链上有一环断了。这是最常被推荐的检查（[Karpathy，2019](https://karpathy.github.io/2019/04/25/recipe/)），它只要几秒钟，而且必须用和正式训练**同一份**训练代码，否则测的不是你要用的代码。

**③ 因果性。** 改掉第 40 个 token，前 40 个位置的输出应该**完全**不变，因为它们不应该看到第 40 个 token。这项检查连训练都不用。

![示意图（为了看得清，只画一段短输入）：把第 6 个 token 换掉，比较前后两次的输出。有因果掩码时，第 6 个之前各位置的输出完全不变；漏了因果掩码时，前面的位置也变了，说明模型能看到后面的 token](/tinyllm/figures/eval-causality.svg)

怎么读这张图：上下两组各是一份代码。每组的“输入”一行里写着“改”的是被换掉的 token，“输出”一行标出每个位置的输出变没变。有因果掩码时，它前面的位置都“不变”；漏了掩码时，前面的位置也“变了”，说明它们“看见”了后面的 token。脚本里实际换的是第 40 个 token，道理相同。

**④ 训练、验证曲线。** 训练 240 步后，验证损失应该比初始明显下降（超过 1），而且和训练损失相差不大（这里不到 0.5，[第 18 章](./regularization.md)：差距大是在背书）。

**⑤ 生成样例。** 让模型写 32 首，按逗号句号切开，五个字的句子应该占一半以上。阈值是按这个代理模型训练 240 步的水平定的；换了模型和训练时长，要重新定。

**⑥ 梯度范数。** 裁剪前的全局梯度范数，中位数应在 0.05～5 之间，最大值不超过 10（[第 20 章](./gradient-stability.md)）。太小说明梯度消失、学不动了；太大说明数值有问题。

一行一行看：

- **漏了因果掩码**：只有③因果性能精确地指出问题。曲线（④）好看极了；生成样例（⑤）不及格，但它只能说明“有问题”，说不出是什么问题。
- **标签没错位**：①初始损失 4.53，比乱猜还低。原因和正确代码的初始损失偏高是同一个：共享权重让模型一开始就偏向“预测输入的 token 自己”，正确的代码里这是错的答案，这里却恰好是“答案”（目标就是输入本身）。之后模型只需学会抄写，训练和验证损失都降到 0.003。⑥ 梯度范数中位数只有 0.0039，也是因为损失已经接近 0。
- **双重 softmax**：初始损失恰好等于 $\ln V$，看起来非常“标准”，①通过了。可是②单 batch 怎么也过拟合不下去：概率都在 0 到 1 之间，当成 logits 再做一次 softmax，最大的那个比最小的最多大 $e$ 倍，正确答案的概率最高也只有 $e/(e+1023)$，损失最低约 5.93，模型根本没法“自信”。梯度范数中位数只有 $6.9\times10^{-5}$，几乎学不动。
- **忘了清梯度**：最隐蔽的一个。①②③④⑥全部通过，只有⑤生成样例不及格。它的验证损失 5.66，比正确的代码差了 0.9，但如果手上没有一个“正常情况下应该是多少”的参照，单看这一条曲线，什么异常也看不出来：损失在降，训练和验证贴在一起，梯度范数也正常。它能学到一点东西，是因为裁剪会就地修改 `.grad`，累积下来的梯度每步都被压回 1 以内，相当于一个衰减得很慢的动量。
- **每步同一个 batch**：④一眼就能看出来，验证损失 8.65，比乱猜还差，而验证减训练的差是 8.64，训练损失几乎为 0：模型把那一个 batch 背了下来，典型的背书（第 18 章）。
- **初始化放大 10 倍**：①初始损失 77.9，比 $\ln V$ 大十倍以上；⑥梯度范数最大 23.8。模型最终也学到了一些东西（验证 5.35），但比正确的代码差得多。

从这张矩阵里能读出几条规律：

1. **没有一项检查能抓住所有 bug，每个 bug 都至少被一项抓住。** 所以要几项一起做。
2. **最便宜的三项（①②③）不用正式训练，几秒钟就能跑完**，能抓住六个里的四个。正式训练之前先跑它们。
3. **⑤生成样例抓住了全部六个，但不够具体。** 它只告诉你“有问题”，说不出是哪里的问题；训练不足的模型同样过不了这一项。它适合当最后一道关，不适合用来定位。
4. **有些 bug 只会让结果变差，不会出现明显的异常**，比如忘了清梯度。抓它们要靠参照：同样的设置，以前跑出过多少？这正是本课一直保留第 12 章基线、第 17 章代理模型数字的原因。
5. **曲线好得不合理时，先怀疑代码。** 漏因果掩码和标签没错位的曲线，都比正确的代码“好”得多。

## 5. 验证损失本身有多准

现在假设代码是对的。下一个问题是：验证损失这个数本身有多准？

验证集只有 291 首诗。换一批诗，验证损失会变吗？当然会。变多少，可以用 **bootstrap** 来估：从这些诗里有放回地重新抽 291 首（有的诗被抽到两次，有的一次也没抽到），重新算一次验证损失；重复 1000 次，看这些数散布得多宽（[Efron，1979](https://projecteuclid.org/journals/annals-of-statistics/volume-7/issue-1/Bootstrap-Methods-Another-Look-at-the-Jackknife/10.1214/aos/1176344552.full)）。重抽的单位是“诗”而不是“token”，因为同一首诗里的 token 不是互相独立的。

拿同一次训练里第 230 步和第 240 步的检查点比较：

<<< @/public/tinyllm/code/training-evaluation.py#bootstrap

```text
290 首完整的验证诗
第 230 步      4.7509   95% 区间 4.7319～4.7693（宽 0.0374）
第 240 步      4.7333   95% 区间 4.7145～4.7516（宽 0.0370）
差（230 − 240） 0.0176   95% 区间 0.0149～0.0199（宽 0.0049）
```

（验证流末尾的最后一首诗被窗口截断了，所以这里是 290 首。）

![左：对验证诗有放回地重抽 1000 次，第 230 步和第 240 步检查点的验证损失各自的 95% 区间互相重叠。右：每次重抽时两个检查点用同一批诗，算它们的差，95% 区间宽度只有各自区间的约八分之一，而且不含 0](/tinyllm/figures/eval-bootstrap.svg)

- **每个检查点自己的区间宽约 0.037。** 也就是说，换一批同样多的诗，验证损失可能上下浮动约 0.02。两个检查点的区间是重叠的：如果分别看，会觉得“差别在误差以内”。
- **配对以后，差的区间只有 0.005 宽，而且不含 0。** 每次重抽时，两个检查点用的是**同一批**诗，算它们的差。有些诗本来就难，两个模型在上面的损失都高；有些本来就容易，都低。这部分“诗本身的难易”对两个模型是一样的，相减就抵消了，剩下的才是模型之间的差别。所以第 240 步确实比第 230 步好，好约 0.018。

这给了比较两个模型的正确做法：**在同一个验证集上比，算差，再对差做 bootstrap**（机器翻译评测里叫配对 bootstrap，[Koehn，2004](https://aclanthology.org/W04-3250/)）。分别算两个区间再看重不重叠，会把很多真实的差别误判成“在误差以内”。

注意这里估的只是**换一批验证诗**带来的误差。换一个随机种子重新训练，模型本身也会变：[第 17 章](./learning-rate.md)、[第 18 章](./regularization.md)用 3 个种子报告范围，量的是这一部分。两种误差都要考虑；下一章讲调参时，会把它们合起来当作“噪声底线”。

![同一次训练的 5 个检查点。验证损失从 6.05 降到 4.73；五字句占比从 7% 升到 79%，乱码字符从 32% 降到 0.4%；照抄训练集的句子始终是 0。两者方向一致，但不成比例](/tinyllm/figures/eval-quality.svg)

- **方向一致。** 验证损失越低，格式越好，乱码越少。在这个阶段，验证损失是生成质量的一个可靠的总体指标。
- **但不成比例。** 第 60 步到第 120 步，验证损失降了 0.44，乱码从 5.1% 降到 1.8%；第 180 步到第 240 步，验证损失只降了 0.16，五字句占比却从 59% 升到 79%。验证损失是对所有 token 的平均，而格式只取决于少数几个关键位置（逗号、句号、第五个字之后）；这些位置学会的时机，和平均损失下降的节奏并不同步。
- **照抄训练集的句子一直是 0。** 用全部 5419 首诗只训练了一遍，模型还没开始背书，这和[第 12 章](./tinyllm-model.md)的观察一致。

本章的三个指标都很粗：它们能发现“格式不对”“满是乱码”“在背书”，却判断不了“诗写得好不好”。语言模型的生成质量怎么评，是一个大问题，常见的做法是在一组固定的任务上考试（下游任务评测）、请人打分，或者请一个更强的模型打分；这些在后训练的几章（[第 38 章](./instruction-finetuning.md)起）会再碰到。对预训练阶段，验证损失仍然是最稳定、最便宜的主指标，生成样例和简单的结构指标用来补它看不到的地方。

## 7. 诊断清单

![诊断清单的四个阶段：训练前做初始损失、因果性和单 batch 过拟合检查；训练中记录损失、梯度范数、学习率和非有限值；训练后看生成样例和结构指标；比较模型时用配对 bootstrap 和多个种子](/tinyllm/figures/eval-checklist-flow.svg)

怎么读这张图：从左往右是时间顺序，每一栏下面是这个阶段要做的检查。越靠左越便宜、越早能发现问题；越靠右越接近“模型到底好不好”。下面的清单按同样的顺序写成可以照着做的表。

把本章的检查按“什么时候做”整理一下：

| 时机 | 检查 | 能抓住什么 | 代价 |
| --- | --- | --- | --- |
| 写完模型，训练之前 | 初始损失 ≈ $\ln V$ | 初始化尺度、标签泄漏 | 一次前向 |
| | 因果性测试 | 掩码遗漏 | 两次前向 |
| | 单 batch 过拟合 | 损失函数、反向、更新链路 | 几秒 |
| 训练中 | 训练/验证曲线 | 背书、学不动 | 每隔一段测一次验证 |
| | 梯度范数、学习率（[第 20 章](./gradient-stability.md)） | 数值问题、调度错误 | 几乎为 0 |
| 训练后 | 生成样例与结构指标 | 各种问题的最后一道关 | 生成几十首 |
| | 和已知基线比较 | 只让结果变差的 bug | 需要保留参照 |
| 比较两个模型 | 配对 bootstrap，多个种子 | 把噪声当成改进 | 重抽 1000 次 |

最后一行要单独强调：本章的检查都是针对“代码对不对”的。代码对了以后，两个设置哪个更好，要按配对比较和多种子的口径来判断。

## 动手实验

1. **埋一个新 bug。** 把 RoPE 的位置编号写反（`torch.arange(context)` 换成倒序），六项检查里哪几项能抓住它？
2. **因果性测试的盲区。** 只在第 1 层漏掉因果掩码，第 0 层保持正确，③因果性还能抓住吗？④的验证损失会低到什么程度？
3. **验证集要多大。** 只用前 50 首验证诗重复第 5 节，单个检查点的区间宽多少？配对的差的区间呢？
4. **换一个生成指标。** 加一个“押韵率”：律诗的第 2、4、6、8 句末字是否同韵（可以先用末字的拼音韵母近似）。它和验证损失的关系，与五字句占比一样吗？

## 本章结论：TinyLLM 的选择 {#tinyllm-choice}

TinyLLM 每次改动训练代码以后，正式训练之前先跑三项检查：**初始损失接近 $\ln V$、因果性测试、单 batch 过拟合**（用和正式训练同一份训练代码）。训练中记录训练损失、验证损失、梯度范数和学习率；训练后用**固定提示词、固定随机种子**的生成样例，和五字句占比、乱码占比、照抄训练集比例这几个简单指标，补验证损失看不到的地方。比较两个模型时，在同一个验证集上**配对比较**，按诗做 bootstrap 估区间，并结合多个随机种子。

理由来自本章的实验（代理模型、单个种子）：六个常见的 bug 里，没有一项检查能抓住全部，但每个都至少被一项抓住；训练前的三项检查只要几秒，就能抓住其中四个。漏因果掩码、标签没错位让验证损失低到 0.111 和 0.003，比正确的代码“好”得多；忘了清梯度则六项里只有生成样例不及格，要靠和已知基线比较才能发现。验证损失每个检查点自己的 95% 区间宽约 0.037，配对以后差的区间只有 0.005 宽。

这些选择在什么情况下要换：模型和训练时长变了，生成样例、梯度范数的阈值要重新定；验证集更大时，抽样误差更小，但随机种子带来的差别不会因此变小；进入后训练阶段，要加上任务评测，验证损失不再够用。

::: warning 常见误区
- **损失越低越好。** 低得不合理时，先怀疑信息泄漏：漏了因果掩码、标签没错位，验证损失都比正确的代码低几十倍。
- **单 batch 过拟合用一个单独写的小循环测。** 那样测的不是你要用的训练代码；“忘了清梯度”这类 bug 就漏掉了。
- **初始损失接近 $\ln V$，就说明代码没问题。** 双重 softmax 的初始损失恰好等于 $\ln V$，可它根本训练不下去。
- **曲线正常，就说明代码没问题。** 忘了清梯度时，曲线、梯度都正常，结果却差了 0.9；要和已知的基线比。
- **两个模型的区间重叠，差别就不可信。** 在同一个验证集上配对比较，区间会窄得多；本章两个检查点的区间重叠，配对的差却明确大于 0。
- **验证损失降了多少，生成质量就好了多少。** 两者方向一致，但不成比例；格式可能在损失变化不大的阶段大幅改善。
:::

## 检查理解

1. 漏了因果掩码时，验证损失为什么恰好是 0.11 左右，而不是 0？

   <details><summary>参考答案</summary>

   每段 64 个 token 里，第 $t$ 个位置要预测第 $t+1$ 个 token。没有因果掩码时，前 63 个位置都能直接看到自己要预测的那个 token，损失几乎为 0；只有最后一个位置的答案在这一段之外，看不到，只能乱猜，损失约 $\ln 1024 = 6.93$。64 个位置平均，约 $6.93/64 \approx 0.11$。

   </details>

2. 双重 softmax 时，初始损失为什么恰好等于 $\ln V$？为什么单 batch 怎么也过拟合不下去？

   <details><summary>参考答案</summary>

   随机初始化的模型输出的概率都很小（约 $1/V$），当成 logits 再做一次 softmax，几乎是均匀分布，所以损失恰好是 $\ln V$。之后，作为“logits”的概率都在 0 到 1 之间，相差最多 1，再 softmax 以后，最大的概率也只有 $e/(e + V - 1)$，$V = 1024$ 时约 0.0027，对应的损失最低约 5.93。模型无论怎么学都不可能变得自信，单 batch 过拟合时损失卡在 6.87；而且梯度极小（中位数 $6.9\times10^{-5}$），几乎学不动。

   </details>

3. 有人说：“我的新模型验证损失 4.71，旧模型 4.73，两者的 95% 区间都约 ±0.02，重叠了，所以差别不可信。”这个推理有什么问题？应该怎么比？

   <details><summary>参考答案</summary>

   分别估区间再看重不重叠，没有利用“两个模型是在同一批验证诗上测的”这一点。很多诗本身难或容易，对两个模型的影响是一样的，分开估时这部分波动被算了两遍。正确的做法是配对：每次 bootstrap 重抽同一批诗，算两个模型损失的差，看差的区间是否包含 0。本章两个检查点各自的区间宽约 0.037、互相重叠，配对后差的区间只有 0.005 宽、不含 0。另外，还要用多个随机种子重新训练，确认这个差别不是某一个种子的偶然结果。

   </details>

4. 为什么单 batch 过拟合检查必须用和正式训练同一份训练代码？举本章的一个例子。

   <details><summary>参考答案</summary>

   检查的目的是确认“要用的那份训练代码”的前向、损失、反向、更新链路是通的。如果另写一个小循环，测的就是另一份代码，正式代码里的 bug 不会出现在检查里。本章“忘了清梯度”的 bug 就在训练循环里：如果单 batch 过拟合另写一个带 `zero_grad` 的循环，这个 bug 根本不会被执行。本章的 `check_overfit_one_batch` 调用的是同一个 `train` 函数，只是把数据换成固定的一个 batch。

   </details>
