## 问题：小模型的训练信号从哪里来

预训练用的是人写的文本，每个位置的“正确答案”只有一个：真实的下一个字。可这个答案信息量很少：“春眠不觉晓”后面，真实的是“处”，但“夜”“花”“鸟”也都说得通，各有几分可能。一个训好的大模型知道这些，它给出的整个概率分布比一个“正确答案”包含多得多的信息。

[Hinton 等（2015）](https://arxiv.org/abs/1503.02531)把这叫**知识蒸馏**：让小模型（学生）去拟合大模型（老师）输出的分布，这个分布叫**软标签**。在语言模型上，常见的有三种做法：

- **序列级蒸馏**（[Kim 与 Rush，2016](https://arxiv.org/abs/1606.07947)）：老师先写出一批文本，学生把它们当成普通数据训练。只需要老师能生成文本，所以闭源的大模型也能当老师；今天大量的“合成数据”就是这么来的。
- **软标签蒸馏**：在同一份文本上，学生每个位置都去拟合老师的整个分布。需要拿到老师的 logits。
- **on-policy 蒸馏**（[Agarwal 等，2023](https://arxiv.org/abs/2306.13649)）：学生自己写，老师在学生写的每个位置上给出分布，学生朝它靠拢。学生在自己会走到的地方得到纠正，而不是只在老师走过的路上学。

[Qwen3](https://arxiv.org/abs/2505.09388)的 0.6B～14B 和 30B-A3B 都没有单独走完整的四阶段后训练，而是从 Qwen3-32B 或 Qwen3-235B-A22B 蒸馏：先用老师在思考、不思考两种模式下的回答做离线蒸馏，再做 on-policy 蒸馏，拟合老师的 logits（第 4.5 节）。他们在 Qwen3-8B 上比较过：从同一个检查点出发，on-policy 蒸馏用 1800 个 GPU 小时，比用 17920 个 GPU 小时的强化学习效果还好（AIME'24 74.4 对 67.6，表 21）。

这一章在预训练的层面把前两种做一遍：老师是第 38 章的基座，学生是一个更小的模型。

## 3. 三种训法

![三种训学生的办法：从头训和序列级蒸馏每个位置只有一个正确答案，软标签蒸馏每个位置的目标是老师的整个分布](/tinyllm/figures/kd-methods.svg)

怎么读这张图：每一行是一种训法，右边的小柱状图是某一个位置上学生要拟合的目标：前两行只有一根柱子（一个正确答案），第三行是老师给出的整个分布。

软标签的损失是每个位置上的 KL(老师 ‖ 学生) 再平均。这是**前向 KL**：老师认为有可能的 token，学生都必须给出概率，否则损失很大，所以学生会尽量“覆盖”老师的分布。`kd_loss` 还带两个工程选项：温度，以及只保留老师前 k 个 token 的概率（第 5 节）。

<<< @/public/tinyllm/code/distillation.py#distill

三种训法用同样的模型、步数（600 步，每步 8 行 × 128 个 token）、学习率（WSD，峰值 1e-2），各 3 个种子：

<<< @/public/tinyllm/code/distillation.py#compare

```text
[计时，本机] 3 种训法 × 3 个种子，各 600 步，共 41.9 秒
从头训     验证损失 第 200/400/600 步 4.998 4.800 4.675  │ 最终 [4.631, 4.701]  离老师的 KL 0.558
序列级蒸馏   验证损失 第 200/400/600 步 5.038 4.880 4.761  │ 最终 [4.739, 4.800]  离老师的 KL 0.553
软标签蒸馏   验证损失 第 200/400/600 步 4.767 4.567 4.471  │ 最终 [4.444, 4.506]  离老师的 KL 0.253
老师自己的验证损失 4.305
```

![蒸馏的结果：左图是三种训法的验证损失随步数变化，软标签一直最低；中图是软标签的三个变体；右图是训到 1800 步时从头训和软标签的比较](/tinyllm/figures/kd-results.svg)

怎么读这张图：三张图的纵轴都是真实验证集上的损失，越低越好。左图 600 步处的竖条是 3 个种子的范围；中图的虚线是从头训（种子 0），红柱被截断了，实际是 6.33。

- **软标签蒸馏在每个时刻都最好。** 600 步时 4.471，从头训 4.675，差 0.2，比种子之间的范围（约 0.06～0.07）大得多。第 400 步时软标签（4.567）已经比从头训 600 步（4.675）好。学生离老师的 KL 也只有从头训的一半（0.253 对 0.558）。每个位置拿到的是一整个分布，同样的数据，学生学到的东西多得多。还要说明一点：“同样的数据”指的是学生直接见到的数据。老师是在全部约 30 万个 token 的预训练数据上训出来的，学生只见过其中的 10 万个，老师的分布里也带着另外那 20 万个 token 的信息。这正是蒸馏的用处，但差距不全是“分布比答案信息多”带来的。
- **序列级蒸馏比从头训还差一点。** 600 步时 4.761 对 4.675，离老师的 KL 和从头训差不多（0.553）。老师写的诗不如真实的诗好，而学生学的是这些样本本身，不是老师的分布；10 万个 token 的样本里，老师分布的细节大部分没体现出来。老师比学生强得多时（比如用 GPT-4 级的模型写数据），这种做法才划算；本章的老师只比学生大三倍，写出来的诗质量有限。

## 4. 训得更久：软标签也是一种正则化

数据只有约 10 万个 token，600 步已经是 6 遍。再训下去会怎样？种子 0 训到 1800 步（18 遍）：

<<< @/public/tinyllm/code/distillation.py#variants

```text
[计时，本机] 43.9 秒
软标签，温度 1（种子 0）    验证损失 4.462
软标签，温度 2       验证损失 4.590
软标签，只留前 8 个    验证损失 6.327
验证集上，真实的下一个字落在老师前 8 个候选里的比例 43%
从头训，1800 步：第 600/1200/1800 步 4.756 4.778 4.613
软标签蒸馏，1800 步：第 600/1200/1800 步 4.553 4.451 4.371
```

先看最后两行。从头训的验证损失在第 1200 步不降反升（4.756 → 4.778，一个种子，只升了 0.02）：同一份数据看了十几遍，学生很可能开始背训练集了，最后的衰减段才把它拉回 4.613。软标签一路下降到 4.371。硬标签让学生把每个位置的真实答案背成概率 1，软标签给的目标本身就是“几分可能”，学生没法把它背成 1，这可能起到了正则化的作用（第 18 章）；老师见过更多数据也是一个原因。同一次 1800 步的训练里，第 600 步两者差 0.20，第 1800 步差 0.24：训得更久，差距没有缩小（一个种子）。

## 5. 温度和“只留前 k 个”

中间三行是两个常见的工程选择：

- **温度 2 不如温度 1**（4.590 对 4.462）。Hinton 等在分类任务上用较高的温度，让老师分布里那些很小的概率显出来；语言模型的老师分布本身就很“软”（下一条：真实的下一个字有一半以上不在老师的前 8 个候选里），再摊平反而让学生学到一个和老师不一样的分布（推理时用的还是温度 1）。
- **只留前 8 个，学生训坏了**（6.327）。离线蒸馏常常只存老师每个位置前 k 个 token 的概率，省得存整张 logits。可本章的老师很不确定：真实的下一个字只有 43% 落在老师的前 8 个候选里。只保留前 8 个、其余当成 0，学生学会了把其余 1016 个 token 的概率压到几乎为 0，真实的字一旦不在前 8 里，损失就极大。实际做法要么取大得多的 k（几十到几百），要么把剩下的概率质量合成一个“其余”类，要么同时加上真实标签的交叉熵。

## 动手实验

1. **混合损失。** 把软标签损失换成 0.5×KL + 0.5×真实标签的交叉熵。600 步时比纯软标签好还是差？“只留前 8 个”加上交叉熵以后能救回来吗？
2. **反向 KL。** 把 `kd_loss` 改成 KL(学生 ‖ 老师)。学生的分布会变得更集中还是更分散？验证损失呢？（提示：反向 KL 只惩罚学生给了概率、老师却觉得不可能的 token。）
3. **更多合成数据。** 让老师写 30 万个 token，和真实数据一样多，再比较序列级蒸馏和从头训。差距来自数据量还是数据质量？
4. **on-policy。** 学生自己从 `<eos>` 采样一批诗，在这些诗上用软标签损失训练（老师在学生写的每个位置上给分布）。和在真实的诗上做软标签比，哪个好？

## 在真实模型里

TRL 的 `DistillationTrainer` 做的是 on-policy 蒸馏：学生先自己写，再在自己写的每个位置上拟合老师的分布；本章的软标签蒸馏在真实的诗上拟合，属于 off-policy，序列级蒸馏则只需要一个能生成文本的老师。下表的链接都指向 Hugging Face trl 的固定版本 `v1.18.2`，精确到行。读代码时可以先跳过缓存、掩码、并行这些工程细节，只看和本章对应的那几行。

| 本章的零件 | 真实代码 | 对照要点 |
| --- | --- | --- |
| 蒸馏训练器 | [`DistillationTrainer`](https://github.com/huggingface/trl/blob/v1.18.2/trl/trainer/distillation_trainer.py#L220-L2086) | 学生生成回答后，老师和学生在同样的位置上各算一遍分布，按 `beta` 选定的散度求损失；要求两者共用同一个词表（本章的老师和学生也共用分词器） |
| 选哪种散度 | [`DistillationConfig`](https://github.com/huggingface/trl/blob/v1.18.2/trl/trainer/distillation_config.py#L22-L424) | `beta=0` 是本章用的前向 KL(老师‖学生)，`beta=1`（默认）是反向 KL，中间是广义 JSD；`temperature` 同时用于采样和算损失 |
| 分块算散度 | [`_chunked_divergence_loss`](https://github.com/huggingface/trl/blob/v1.18.2/trl/trainer/distillation_trainer.py#L105-L217) | 不一次算出整张 logits，而是把老师和学生的隐藏状态分块乘输出层、边算边累加；词表有十几万个 token 时，这比存两份完整的 logits 省得多 |

想在本机看源码，可以先 `pip install trl`，再用 `python -m inspect trl.trainer.distillation_trainer:DistillationTrainer` 这样的命令打印出任意一个类。

## 本章结论：TinyLLM 的选择 {#tinyllm-choice}

TinyLLM 要训一个更小的模型、手上又有一个更大的同词表模型时，用<strong>软标签蒸馏</strong>：在真实数据上，学生每个位置拟合老师的完整分布（前向 KL，温度 1），每一步现算老师的 logits，不截成前 k 个；老师只有 API、拿不到 logits 时，才退回序列级蒸馏，并且要先确认老师写的数据比手头的真实数据好。

为什么：在同样的数据量（约 10 万个 token）和步数下（3 个种子），软标签蒸馏的验证损失 4.471，从头训 4.675，在老师写的诗上训 4.761；训到 1800 步，从头训开始过拟合，软标签一路降到 4.371，差距还略有扩大。温度 2 比温度 1 差（4.590 对 4.462）；只留老师前 8 个概率时学生训坏了（6.327），因为真实的字只有 43% 落在前 8 个里。

实验边界：老师本身很小（验证损失 4.3）、只比学生大三倍，和真实的“几百亿参数教几十亿参数”差得远，序列级蒸馏的结论尤其依赖老师的质量；只在预训练的层面做了蒸馏，没有做指令数据上的蒸馏和 on-policy 蒸馏；变体只跑了一个种子；软标签要每步跑一遍老师，本章没有算这部分额外的计算量。什么情况下要换：老师很强、只能通过 API 调用时，用它写数据（序列级蒸馏）；学生已经训到一定程度、需要在自己会犯错的地方被纠正时，用 on-policy 蒸馏（Qwen3 的第二阶段）；存不下完整的 logits 时，取较大的 k 并保留“其余”的概率质量。

::: warning 常见误区
- **蒸馏就是用大模型生成数据。** 那只是序列级蒸馏；拟合老师的分布（软标签）通常更有效，本章同样的数据下损失低 0.2。
- **老师写的数据一定比真实数据好。** 它受老师的水平限制；本章老师写的诗训出来的学生，比用真实的诗训的还差。
- **温度越高，软标签的信息越多。** 语言模型的分布本来就很软，温度 2 反而变差；而且推理时用的是温度 1。
- **只存老师前几个概率就够了。** 老师不确定时，真实的字常常不在前几个里；本章只留前 8 个，学生直接训坏。
- **蒸馏只是为了省推理成本。** 它也是一种很强的训练信号和正则化：同样的数据，学生学得更快、过拟合得更慢。
:::

## 检查理解

1. 软标签蒸馏为什么要求老师和学生用同一个分词器？如果两者的词表不同，怎么办？

   <details><summary>参考答案</summary>

   软标签损失要在每个位置上比较两个分布，两个分布必须定义在同一组 token 上、位置也要一一对应。词表不同时，同一段文本切出来的 token 数和边界都不一样，没法逐个对齐。这时可以退回序列级蒸馏（只用老师生成的文本，学生用自己的分词器重新切），或者用专门对齐两种词表的方法（比如在字或字节层面对齐概率），后者复杂得多。

   </details>

2. 前向 KL(老师 ‖ 学生) 和反向 KL(学生 ‖ 老师) 对学生的要求有什么不同？当学生太小、学不全老师的分布时，各会得到什么样的学生？

   <details><summary>参考答案</summary>

   前向 KL 按老师的概率加权，老师认为有可能的 token 学生都要给概率，否则惩罚很大，学生会把概率摊开去“覆盖”老师的每一种可能，容量不够时就变得过于分散。反向 KL 按学生自己的概率加权，只惩罚学生给了概率、老师觉得不可能的 token，学生可以只抓住老师的一两种主要模式，变得更集中、更保守。生成任务里常用反向 KL 或两者之间的 JSD（TRL 的 `beta`），避免学生生成老师认为不可能的东西。

   </details>

3. 从头训在第 1200 步的验证损失比第 600 步还高，最后在 1800 步又降到 4.613。用第 17 章的 WSD 和第 18 章的过拟合解释这条曲线。

   <details><summary>参考答案</summary>

   1800 步的 WSD 在前 1440 步保持峰值学习率。数据只有 10 万个 token，到第 1200 步已经看了十几遍，大学习率下学生开始记住训练集的细节，验证损失回升，这是过拟合。最后 20% 的衰减段（第 1440～1800 步）学习率降到 0，损失“下一个台阶”（第 17 章），把验证损失拉回 4.613，但仍不如软标签的 4.371。

   </details>

4. Qwen3 说 on-policy 蒸馏只用了强化学习约十分之一的 GPU 时间，效果还更好。从“每个样本能提供多少信息”的角度解释为什么。

   <details><summary>参考答案</summary>

   强化学习（第 41、43 章）每条回答只得到一个标量奖励，要靠大量采样才能估计出哪些 token 好、哪些不好。on-policy 蒸馏在学生写的每一个位置上都有老师给出的完整分布，相当于每个 token 都有一份详细的“答案”，信息量大得多，需要的样本也少得多。代价是必须有一个更强、而且能拿到 logits 的老师；强化学习不需要老师，所以能超越现有的模型。

   </details>
