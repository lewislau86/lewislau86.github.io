# 第 31 章：KV 显存管理：分页与前缀缓存

[课程总览](./index.md) · [上一章](./batching.md) · [下一章](./inference-optimization.md)

::: info 本章状态：规划中
正文与 notebook 尚未完成。[第 26 章](./inference-efficiency.md)算过 KV cache 要占多少字节，[第 30 章](./batching.md)让很多请求同时进来；两件事撞在一起，显存里的 KV 怎么放就成了瓶颈。预计覆盖：

- **连续分配为什么浪费。** 每个请求按最大长度预留一整块，实际只用到一部分；算一算预分配和实际使用差多少，这就是分页要解决的问题。
- **分页。** 缓存切成固定大小的页，一张块表把逻辑位置映射到物理页；序列增长时只追加新的页，不同请求的页可以放在不连续的位置上，注意力按块表去读。
- **前缀共享。** 两个请求开头一样，就让它们的块表前几项指向同一批页；写时再复制。多轮对话与固定 system prompt 是最常见的两种命中场景，统计命中率。
- **淘汰。** 显存有限，没人再用的页要回收；按最近使用还是按引用计数，淘汰错了会重算，淘汰对了才省。
- **offloading 的边界。** 把冷页搬到内存甚至磁盘，收益取决于“搬回来的代价”和“重算的代价”谁更小，需要和全在显存里的基线比。
:::

## 本章主线选择（待实验验证）

主线先在 CPU 上实现一张<strong>块表</strong>：逻辑位置 → 物理页，页大小取 4 或 8 个 token，注意力按块表把 K、V 拼出来。第一件事是验证正确性：分页后的注意力输出与连续存储逐元素一致（沿用[第 26 章](./inference-efficiency.md)的对照写法）。第二件事是记账：同一份请求流下，比较“按最大长度预分配”和“按页追加”各占多少槽位、真正存了多少 token，报告两者的比值。第三件事是前缀共享：用多轮对话式的请求流，统计有多少页被复用、省下多少次 prefill。

分页是<strong>分配方式</strong>的改变，不改变数学结果；这一点要先用代码证明，再谈收益。指标以“分配槽位 / 实际使用”“页复用次数”这类计数为主，因为它们在 CPU 上就能精确测出；显存峰值和吞吐放在标注了环境的 GPU 实验里。淘汰策略和 offloading 只做小规模模拟，并明确说明是模拟。
