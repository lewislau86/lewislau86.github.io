## 问题：缓存按最大长度预留

[第 32 章](./batching.md)的引擎给每个槽位预留了 64 个位置的 KV cache，也就是模型的上下文上限。可是一个请求最终用到多长，开始时并不知道：它的提示词有多长是知道的，要生成多少个 token 要等写出 `<eos>` 才知道。按上限预留最保险，代价是大部分位置空着。

[第 28 章](./inference-efficiency.md)算过，Llama 3 8B 每个 token 的 KV cache 要 128 KiB，一条 8K 的序列就是 1 GiB；一张 80 GiB 的卡放下权重以后，同时能跑多少请求先受 KV cache 限制。如果每个请求都按 8K 预留，而实际平均只用 2K，四分之三的缓存显存是白占的，能同时跑的请求数也只有本来的四分之一。

这一章把 KV cache 的放法从“每个请求一整段”换成“一块一块按需拿”，再在块上做共享。顺序是：先证明换了放法输出不变；再量省了多少；然后看省下的显存怎么用；最后是共享、淘汰和 offloading。

## 2. 分页：块表把逻辑位置映射到物理块

换一种放法：

- 显存是一个**块池**：每层一份 `[块数, 头, 块大小, 每头维度]` 的张量。块大小取 4、8、16 这样的小数；
- 每个请求有一张**块表**，记第 j 个逻辑块（位置 $j \cdot b$ 到 $(j+1) \cdot b - 1$，$b$ 是块大小）放在哪个物理块里；
- 序列变长时，写满了才再拿一块；请求结束，把块还给池子；
- 注意力按块表把这个请求的块拼回来再算。

这就是 vLLM 的 [PagedAttention](https://arxiv.org/abs/2309.06180)。名字来自操作系统的虚拟内存：块是“页”，块表是“页表”，程序看到的是连续的地址，物理内存可以是零散的。

![同样 3 个请求的两种放法：上面每个请求按上限预留 64 个位置，共 192 个，存着 K、V 的只有 66 个；下面块大小 8，每个请求一张块表，3 个请求一共拿了 10 块、80 个位置，物理块在池子里不连续](/tinyllm/figures/kv-layouts.svg)

怎么读这张图：上半是第 32 章的放法，实心格是已经写了 K、V 的位置，浅色格是这个请求以后还会写到的，灰格是到它结束都用不上的。下半是分页：左边每个请求的块表是一串物理块号，右边的块池里，块按块表散落各处，空闲块随时可以给别的请求。分页后浪费的只有每个请求最后一块里还没写的那几格。

## 3. 预留了多少，用了多少

换到第 32 章的请求流上量显存。请求流完全相同：泊松到达；四分之三是短提示词，生成 8～40 个 token；四分之一是 40 个 token 的长提示词，生成 4～12 个。时间也沿用它的成本模型：一次前向花 $\max(1, N/K)$ 个单位，N 是这次前向的新 token 数，K=16。

<<< @/public/tinyllm/code/kv-memory.py#workload

```text
种子 0：40 个请求，每个请求最终长度（提示词 + 输出）平均 32.3 个 token，最长 51；按上下文上限预留，每个请求 64 个位置
```

平均只用到上限的一半，最长的也没到 64。调度是不分块的连续批，显存由块池管：

- 每一步先管正在生成的请求：每个都要多写一个位置，没有空块时，**抢占**最晚进来的那个请求：还掉它的全部块，放回等待队列（它到得早，排在前面）；下次进来时，把“提示词 + 已经生成的 token”重新 prefill 一遍（**重算**）；
- 然后才放新请求：按到达顺序，块池放得下它的提示词才进来，放不下就停。

先管正在跑的、再放新的，顺序不能反：反过来的话，刚放进来的请求还没跑就可能被抢占，白白多一次 prefill。

抢占会让一些 token 算两遍，但不改变输出，最后用 `assert` 检查。`dry=True` 时不跑模型，直接用基准输出、只记账，第 7 节组合多时用它。每一步记下三个数：分配出去的位置、真正存着 K、V 的位置、在跑的请求以后还会写的位置。

逐行看：

- **块大小 64 只有三分之一存着 K、V。** 另外的三分之二里，19% 是这个请求以后还会写到的（预留得早），47% 是到它结束都用不上的（预留得多）。这一行的 TTFT 和吞吐与第 32 章“重负载 连续批”的 13.7 和 5.64 完全相同，因为块大小等于上下文上限时，块池就是第 32 章的槽位。vLLM 的论文在真实负载上量到的数字也在这个范围：在它比较的几种按请求预留连续空间的做法里，只有 20.4%～38.2% 的 KV cache 显存存着真正的 token（[Kwon 等，2023](https://arxiv.org/abs/2309.06180) 图 2）。
- **块大小 8 时 86% 存着 K、V。** 剩下的 14% 是每个请求最后一块里还没写的格子。一个请求平均浪费约 $(b-1)/2$ 格，同时在跑约 9 个请求时就是 30 格左右，和 230 个位置里的 14% 对得上。块越小，这部分越少，块大小 1 时没有浪费。
- 省下来的显存马上变成了更多同时在跑的请求：块大小 16 及以下，排队几乎消失，TTFT 中位从 13.7 降到 3.0，吞吐从 5.64 涨到约 6.7。

![左：同一份重负载请求流（种子 0），块大小 64 时分配的位置很快顶到 512 的上限，存着 K、V 的只有它的三分之一左右；块大小 8 时分配的位置紧跟实际写入的位置。右：3 份请求流平均，存着 K、V 的比例在块大小 64、16、8、4、1 时是 33%、75%、86%、94%、100%](/tinyllm/figures/kv-waste.svg)

怎么读这张图：左图灰线是块大小 64 时分配出去的位置，从约 13 到约 107 个单位一直贴着 512 的上限，新请求只能排队；蓝线是其中真正存着 K、V 的部分。绿色粗线是块大小 8 时分配的位置，绿色虚线是它存着的，两条线贴得很近。右图把各块大小的平均占用拆开，块大小 64 那一条里黄色是“以后才会写”的部分。

块不是越小越好。本章在 CPU 上把块拼回连续张量，块大小只影响记账；真实的分页内核要按块表一块一块去读，块太小，每次读的数据太碎，块表也更长。vLLM 默认块大小 16，transformers 的连续批默认 256（见章末“在真实模型里”）。块大小还影响下一节的前缀共享：只有写满的块能被共享，块越大，共享的粒度越粗。

## 4. 省下来的显存怎么用

显存省下来了，最直接的用法是放更多请求进来。把到达压到每个单位一个请求（过载），沿用第 32 章的时延目标：TTFT 不超过 20 个单位、TPOT 不超过 1.5 个单位，两个都满足的请求，它的 token 才算进 goodput。比较五种配置：


每格是 3 份请求流的平均，goodput 后面的方括号是范围。

- **第一行就是第 32 章的 B=8。** 显存只够 8 个请求各预留 64 个位置，goodput 1.94，和第 32 章 B=8 那一行相同。
- **分页后，一半显存就够。** 第二行只给 256 个位置，并发同样限制在 8 个，goodput 1.90，几乎没变，偶尔抢占一次。同样的服务质量，KV cache 的显存可以减半。
- **把显存全拿去加并发，goodput 几乎归零。** 第三行不限并发，显存能放多少就放多少，平均同时跑 15.7 个，吞吐最高（7.49）；可是光 decode 就有十五六个 token，再加上新请求的提示词，每次前向常常超过成本模型的拐点，TPOT 中位涨到 2.20，40 个请求里平均只有 1 个达标。第 32 章显存充足的 B=32 也只有 1.10，这里更低，是因为显存满了还要抢占：平均抢占 7.7 次、重算 120 个 token，被抢占的请求停下来等重算，它的 token 间隔被拉得更长。
- **限住并发，goodput 翻倍。** 最多 12 个时 goodput 3.98，3 份请求流里最低的 2.90 也高于第一行最高的 2.27。这份请求流上 12 个请求平均只占 233 个位置，一次也没有抢占（最坏情况下 12 个请求可以占到 600 多个位置，所以这只是这份负载上的观察）；按上限预留的话，12 个并发要 768 个位置。最多 16 个时 TPOT 中位 1.48，贴着目标线，3 份请求流之间从 0.87 到 3.90，很不稳。

所以分页解决的是“显存放不下”，不是“算不过来”。显存不再是上限之后，同时跑多少个请求要由算力和时延目标来定（第 32 章的结论），并发上限要单独设，不能等显存满了再说。本章的调度器很简单，显存一满就靠抢占；真实框架会留一点空闲块作余量（transformers 的 `safety_margin`），空闲低于余量就不再放新的 prefill 进来，抢占少一些，但“并发要按 goodput 定”这一点不变。

## 5. 前缀共享：开头一样的请求共用块

因果注意力里，位置 p 的 K、V 只取决于第 0～p 个 token。两个请求开头的 token 一样，开头那几块的 K、V 就一样，没必要各算一遍、各存一份。做法：

- 只登记**写满的块**。块的键是“前一块的键 + 这一块的 token”的哈希，所以同一个键代表从位置 0 开始的同一段完整前缀，K、V 必然相同；
- 新请求进来时，从第 0 块开始一块一块查，第一块对不上就停。命中的块引用计数加 1，接到它的块表上，这部分不用 prefill；
- 至少留最后一个 token 不命中，因为第一个输出要用它的 logits；
- 引用计数降到 0 的块先不清空，留在 `idle` 里等别人命中；真没有空块了才淘汰，淘汰谁是第 7 节的事。

<<< @/public/tinyllm/code/kv-memory.py#prefix

键用的是 Python 的 `hash`，对整数元组是确定的，64 位，本章的规模下撞车可以忽略；真实系统还要防有人故意构造撞车，让别人的请求命中错误的 K、V：vLLM 曾因为用 Python 内置的 `hash` 做前缀缓存的键收到安全公告（[CVE-2025-25183](https://nvd.nist.gov/vuln/detail/CVE-2025-25183)），公告建议改用 SHA-256 这类不易撞车的哈希；transformers 用的是 blake2b。

注意键是从第 0 块一路链下来的：同一段文字出现在不同位置，前面的内容不同，键就不同，不会命中。这一点也是位置决定的，RoPE 让同一个 token 在不同位置的 K 不一样。所以想让前缀缓存起作用，不变的内容要放在最前面，会变的内容（时间、用户名）放在后面。

两种最常见的命中场景：

- **固定的系统提示词**：每个请求开头都是同一段 24 个 token 的“系统提示词”（这里借一首诗的开头充当），后面接一首诗的第一句；
- **多轮对话**：第 1 轮送诗的第一句，模型写 8 个 token；下一轮的提示词是“上一轮的提示词 + 模型的输出 + 诗的下一句”，共 3 轮。对话的开始时间是泊松过程（平均每 3 个单位一个），每轮结束后用户平均想 10 个单位再发下一轮。

## 6. 写时复制：一个提示词，采好几条

同一个提示词要采 4 条不同的回答（并行采样，或者 beam search 的几条分支），提示词的 K、V 对 4 条都一样。做法是 prefill 一次，然后 `fork` 出另外 3 条：块表照抄，每块的引用计数加 1，不复制任何 K、V。

麻烦在最后一块。提示词 37 个 token，块大小 8，第 5 块只写了 5 格，4 条接下来都要往这块的第 6 格写各自的 token。所以 `grow` 写之前先看这一块的引用计数：大于 1，说明还有别人在用，先复制一块、改自己的块表、把原块的引用减 1，再写。这就是操作系统里 fork 进程时用的**写时复制**（copy-on-write）。每条采样用自己的随机数生成器，和单独采样逐 token 比较：

<<< @/public/tinyllm/code/kv-memory.py#fork

```text
每条各自 prefill：4 条采样 4/4 与单独采样逐 token 相同，块数峰值 28，写时复制 0 次
fork 共用提示词的块：4 条采样 4/4 与单独采样逐 token 相同，块数峰值 16，写时复制 3 次
```

各自 prefill 时，每条最终 52 个位置、7 块，4 条 28 块。fork 后，前 4 个写满的块 4 条一直共用，各自只有后面 3 块：$4 + 4 \times 3 = 16$ 块。复制只发生 3 次而不是 4 次：前 3 条写的时候，那一块的引用计数还大于 1；轮到第 4 条，别人都复制走了，引用计数已经是 1，直接写原块。

![左：两个请求开头是同一段 24 个 token 的系统提示词，3 个写满的块各有一个由前一块的键和本块 token 算出的键，两张块表的前 3 项指向同样的物理块，引用计数 2。右：37 个 token 的提示词 fork 出 4 条，4 个写满的块一直共用，第 5 块只写了 5 格，前 3 条写时引用计数大于 1 要先复制，第 4 条写时引用计数是 1，直接写](/tinyllm/figures/kv-sharing.svg)

怎么读这张图：左右两边是同一个机制的两种来源。左边的共享来自“不同请求碰巧开头相同”，靠哈希找到；右边来自“同一个请求分叉”，fork 时就知道。两边都靠引用计数：写满的块只读，可以放心共享；要往一块里写，先看引用计数，大于 1 就先复制。

## 7. 淘汰：显存不够时留谁

前缀缓存的命中全靠“留着的块”，可是留着的块也占显存。显存紧了，留着的块要让给正在跑的请求，这时清掉谁就是淘汰策略。在多轮对话上比较四种：

- **不保留**：引用计数一到 0 就清空，等于不开前缀缓存；
- **缺块时一次清空**：平时都留着，一缺块就把留着的全部清掉；
- **FIFO**：最早登记的块先清；
- **LRU**：最久没被用到的块先清。`idle` 是一个有序字典，块被还回来时排到队尾，被命中时移出，所以队首就是最久没被用到的。

显存从 256 个位置调到 768 个位置。组合多，这里用 `dry=True` 只记账；调度不改变输出，这一点上一节已经用模型核对过：

<<< @/public/tinyllm/code/kv-memory.py#eviction

```text
显存 256 个位置：不保留  0.0%  一次清空  8.5%  FIFO 12.6%  LRU 12.2%
显存 320 个位置：不保留  0.0%  一次清空 14.2%  FIFO 16.7%  LRU 18.2%
显存 384 个位置：不保留  0.0%  一次清空 16.3%  FIFO 19.5%  LRU 24.4%
显存 448 个位置：不保留  0.0%  一次清空 21.4%  FIFO 24.8%  LRU 29.7%
显存 512 个位置：不保留  0.0%  一次清空 27.8%  FIFO 29.5%  LRU 36.7%
显存 640 个位置：不保留  0.0%  一次清空 45.5%  FIFO 50.3%  LRU 49.9%
显存 768 个位置：不保留  0.0%  一次清空 53.4%  FIFO 53.4%  LRU 53.4%
```

- 显存够大（768）时什么都不用淘汰，三种保留策略都是 53.4%，这是这份请求流命中率的上限。
- 中等显存时策略差得最多。384～512 个位置时 LRU 比 FIFO 高 5～7 个百分点，比一次清空高 8～9 个百分点。两头差得少：显存太紧（256）时什么都留不住，三种保留策略差不到 4 个百分点，FIFO 还略高于 LRU（12.6 对 12.2）；640 时 FIFO 和 LRU 几乎一样（50.3 对 49.9）。
- LRU 赢在多轮对话的访问模式：刚结束的那一轮，它的块马上就会被下一轮用到；FIFO 按登记的先后清，一段还在进行的对话，它最早登记的开头几块反而最先被清掉。
- 一次清空最差，但它最简单，也不用维护顺序。transformers 的连续批就是这样做的（见章末“在真实模型里”），它的取舍是：留着的块只是额外的好处，不能为了它让正在跑的请求分不到块。

还有一个细节：`drop` 从块表的尾部往前还块，所以同一个请求的块里，尾部的先进 `idle` 队首、先被淘汰，开头的块留得更久。开头的块是别人最可能命中的部分（系统提示词、上一轮对话），而且后面块的键链在它上面，开头一清，后面的块即使还在也命中不了。vLLM 的做法相同：请求结束时把块按相反的顺序放进空闲队列的队尾，从队头按 LRU 淘汰，理由是“最后一块哈希了更多 token，更不容易被别人用到”（[vLLM 文档：Automatic Prefix Caching](https://docs.vllm.ai/en/latest/design/prefix_caching.html)）。

## 8. offloading 的边界：搬回来还是重算

显存放不下的 K、V 还有第三条路：搬到内存、甚至 SSD 上，要用时再搬回来（offloading）。第 3 节的抢占走的是另一条路：直接扔掉，要用时重算。哪条路便宜，比的是每个 token：

$$
\text{搬回来} = \frac{\text{每个 token 的 KV 字节数}}{\text{链路带宽}},\qquad
\text{重算} \approx \frac{2N + 2 \cdot \text{层数} \cdot d \cdot n}{\text{算力}}
$$

其中 N 是参数量，$2N$ 近似一个 token 过一遍所有矩阵乘的浮点运算数（嵌入表只查表、不做乘法，算进去会略微高估，对大模型影响很小）；后一项是注意力，前缀长 n 时 $QK^\top$ 和乘 V 两次矩阵乘约 $4 \cdot \text{层数} \cdot d \cdot n$，平均每个 token 只看一半前缀，就是 $2 \cdot \text{层数} \cdot d \cdot n$。

下面是**估算**，不是实测：算力按 H100 SXM 的 BF16 稠密峰值 989 TFLOPS 的一半，链路按 PCIe 5.0 x16 的理论单向带宽 64 GB/s 和一块 NVMe SSD 的约 7 GB/s，前缀长 4096（TinyLLM 取它的上下文 64）。

<<< @/public/tinyllm/code/kv-memory.py#offload

```text
TinyLLM（FP32）          每个 token 的 KV    4.0 KiB │ 重算   0.0054 µs │ 从内存搬回   0.064 µs（重算是它的  0.08 倍）│ 从 SSD 搬回   0.585 µs（ 0.01 倍）
Llama 2 7B（MHA，32 个 KV 头） 每个 token 的 KV  512.0 KiB │ 重算  29.4312 µs │ 从内存搬回   8.192 µs（重算是它的  3.59 倍）│ 从 SSD 搬回  74.898 µs（ 0.39 倍）

```

决定胜负的是“每个 token 的 KV 字节数”和“每个 token 的计算量”之比：

- **TinyLLM 该重算。** 它的 KV 每个 token 4 KiB（FP32），计算量却只有约 2.7 MFLOP，在这组参数下搬回来的时间是重算的十几倍。这也是本章抢占用重算的原因。
- **大模型、GQA 时该搬。** Llama 3 70B 每个 token 的计算量是 8B 的约 9 倍，KV 只多 2.5 倍，从内存搬回比重算快约 58 倍，从 SSD 搬也快 6 倍。
- **MHA 的 KV 太胖，SSD 不划算。** Llama 2 7B 没有 GQA，每个 token 的 KV 是 Llama 3 8B 的 4 倍，从内存搬回仍比重算快 3.6 倍，但从 SSD 搬回反而比重算慢。GQA 不只省显存，也让 offloading 更划算。

这张表只比了“每个 token”的平均代价，还有几件事会改变结论：搬运可以和别的请求的计算重叠，重算会占掉本来可以服务别人的算力，这两点都偏向 offloading；短的 prefill 喂不满 GPU，实际算力远到不了一半峰值，这一点也偏向 offloading；PCIe 实际带宽到不了理论值，搬回来还要等排队，这一点偏向重算。真正部署时要在自己的硬件上实测这两条路。多轮对话、长文档问答这类“同一段前缀隔一阵又要用”的场景，有专门把 KV cache 存在内存和 SSD 里、跨请求复用的系统，比如 Kimi 的 [Mooncake](https://arxiv.org/abs/2407.00079)，思路和这张表的后几行一致：对大模型来说，存下来再搬回来比重算便宜。

| 抢占：搬走或重算 | [`OffloadingManager.offload_requests`](https://github.com/huggingface/transformers/blob/v5.21/src/transformers/generation/continuous_batching/offloading_manager.py#L156-L242) | 先清掉留着的块；还不够，就从分不到块的请求里挑几个抢占（至少留一个在跑）。CPU 上放得下就把它的块拷过去，放不下就“软重置”：扔掉缓存，把已生成的 token 接到提示词后面重新排队，下次从头 prefill，和本章第 3 节的重算一样 |

## 本章结论：TinyLLM 的选择 {#tinyllm-choice}

TinyLLM 的推理服务把 KV cache 放在**块池**里：块大小 16（CPU 实验用 8），每个请求一张块表，按需追加，结束即还；注意力按块表读。打开**前缀缓存**：只登记写满的块，键由前一块的键和本块 token 哈希而成；引用计数到 0 的块留着，缺块时按 LRU 淘汰，请求结束时从尾部往前还。并行采样用 fork 共享写满的块、写时复制最后一块。同时在跑的请求数单独设上限，按目标 SLO 下的 goodput 选，不等显存满了再说；显存不够时抢占最晚进来的请求、用重算恢复。系统提示词等不变的内容放在提示词最前面。

为什么：分页在所有块大小下与连续存储逐 token 相同、logits 差为 0；同一份请求流（3 个种子）上，块大小 64（按上限预留）时分配出去的位置只有 33% 存着 K、V，块大小 8 时 86%；过载时只用一半显存、同样 8 个并发，goodput 不变（1.90 对 1.94），把显存全拿去加并发反而让 goodput 掉到 0.17，并发限在 12 个时 goodput 3.98，3 份请求流都高于按上限预留的最好一份；前缀缓存在系统提示词场景命中 79%、实际 prefill 从 1466 降到 252，多轮对话命中 37%；中等显存时 LRU 的命中率比 FIFO 高 5～7 个百分点、比一次清空高 8～9 个百分点。按公布的硬件参数估算，TinyLLM 这样的小模型重算比从内存搬回快十几倍，所以抢占用重算。

实验边界：时间用的是成本模型，不是 GPU 实测，而且它不收 KV 读取的代价，所以“块大小越小越好”在这里看不到反例；调度器显存一满就抢占，没有留空闲余量；分页的读法是把块拼回连续张量，不是真正的分页内核；每份请求流只有 40 个请求（多轮对话 42 个），请求长度预先定好；系统提示词和多轮对话是用唐诗拼出来的模拟场景，命中率取决于请求流，换一份负载要重新量；第 7 节只比了多轮对话一种访问模式；第 8 节是按峰值和理论带宽的估算。什么情况下要换：模型大、用了 GQA、对话很长而且隔一阵才回来时，给 LRU 淘汰掉的块加一层内存或 SSD 的 offloading；多个服务实例时，把请求路由到已经有它前缀的那一台（第 34 章）。

::: warning 常见误区
- **分页会改变注意力的结果。** 分页只改 K、V 放在哪里，数学结果不变；本章所有块大小下逐 token 相同。真实的分页内核会改变累加顺序，差别在浮点舍入的量级。
- **显存省下来了，并发就该开到显存放满为止。** 显存不再是上限以后，算力和时延目标就是上限；本章不限并发时吞吐最高，goodput 却几乎为 0。
- **前缀缓存能命中任何重复的文本。** 只能命中从位置 0 开始、按整块对齐的相同前缀；同样的文字出现在中间不会命中，最后一块没写满也不会命中。
- **前缀缓存是模型的记忆。** 它只是计算结果的缓存，随时可能被淘汰，淘汰了就重算，输出不变；替用户长期保存事实的记忆见[第 44 章](./llm-agent-interaction.md#external-memory)。
- **offloading 总比重算好。** 取决于每个 token 的 KV 字节数和计算量之比；TinyLLM 这样的小模型、或者 MHA 模型从 SSD 搬，重算更快。
:::

## 检查理解

1. 块大小 16，一个请求最终长 100 个 token，分页时分配多少个位置、浪费多少？如果按 4096 的上下文上限预留呢？

   <details><summary>参考答案</summary>

   分页要 $\lceil 100/16 \rceil = 7$ 块，112 个位置，浪费 12 个（最后一块只写了 4 格）。按上限预留是 4096 个位置，浪费 3996 个，约 97.6%。分页的浪费每个请求最多 $b-1$ 个位置，和请求多长无关。

   </details>

2. 块大小 16，系统提示词 30 个 token，后面接 6 个各自不同的 token。前缀缓存能命中几个 token？系统提示词改成 32 个 token 呢？

   <details><summary>参考答案</summary>

   提示词共 36 个 token，查 $(36-1) // 16 = 2$ 块。第 0 块（第 0～15 个）全是系统提示词，命中；第 1 块（第 16～31 个）里第 30、31 个已经是各自的 token，键不同，不命中。所以只命中 16 个。系统提示词 32 个时，前两块都是系统提示词，命中 32 个。系统提示词的长度最好是块大小的整数倍。

   </details>

3. 为什么前缀匹配至少要留最后一个 token 不命中？如果一个请求的提示词恰好和缓存里的某一段完全相同，会发生什么？

   <details><summary>参考答案</summary>

   第一个输出要用提示词最后一个位置的 logits，而缓存里只有 K、V，没有 logits。所以最后一个 token 必须真的过一遍模型。提示词完全相同时，命中前面的整块，最后一块（或者最后一个 token 所在的那块）重新算；如果最后一个 token 恰好落在一个写满的块里，那一块也要重新算，写进一块新分配的块里。

   </details>

4. 第 6 节 fork 出 4 条后，为什么写时复制只有 3 次？如果提示词正好 40 个 token（5 个写满的块），会复制几次？

   <details><summary>参考答案</summary>

   复制只在“要写的那块引用计数大于 1”时发生。前 3 条写时，那一块还有别人在用；它们各自复制走以后，原块的引用计数降到 1，第 4 条直接写。提示词正好 40 个 token 时，5 块都写满了，下一个 token 写进第 6 块，那是每条各自新拿的块，引用计数是 1，一次也不用复制。

   </details>

5. 按第 8 节的估算，Llama 2 7B 的 KV 存在 SSD 上时，搬回来比重算慢；Llama 3 8B 却快。两个模型参数量差不多，差别从哪里来？

   <details><summary>参考答案</summary>

   每个 token 的计算量两者差不多（约 2 倍参数量），主要差别在每个 token 的 KV 字节数：Llama 2 7B 是 MHA，32 个 KV 头，每个 token 512 KiB；Llama 3 8B 用 GQA，8 个 KV 头，每个 token 128 KiB，只有前者的四分之一。字节数少了 4 倍，搬运时间就少 4 倍；Llama 3 8B 的计算量还略大一些（重算 34.6 对 29.4 µs，主要是词表更大），两个因素一起，比值从 0.39 变成 1.85，从“比重算慢”变成“比重算快”。

   </details>
