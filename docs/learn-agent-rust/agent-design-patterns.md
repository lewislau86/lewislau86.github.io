## 1. 从“会调用接口”走向“会选择结构”

工作区助手已经能读资料、调用工具、检索证据，也能暂停和恢复。现在用户提出：“根据项目当前资料制作升级报告，检查影响，发布前让我确认。”

只有一段模型工具循环时，所有责任都挤在同一段历史里：检查顺序由谁决定？哪些检查可以同时做？发现新的 workspace 成员以后怎么办？草稿缺引用时谁判断需要修复？用户批准以后报告又变了，原批准还有效吗？

设计模式是反复出现的任务组织方法。每种模式都要回答四个问题：**谁决定下一步、每步消费什么状态、失败怎样返回、什么条件下停止。** workflow agents（顺序、并行、循环、条件）和图提供表达手段；模式说明这些手段为什么这样组合。

这部分借鉴 Anthropic 的 [Building effective agents](https://www.anthropic.com/research/building-effective-agents) 与 LangGraph 的 [Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)，再加入本课程的计划、交接与人工介入问题，形成教学顺序。这是课程组织方式，不是声称业界只有这几种正式分类。旧文章中的工具版本不作为本站的 API 依据。

## 2. 先分清三种层次

| 层次 | 回答的问题 | 本课程内容 |
| --- | --- | --- |
| 能力与输入 | 本轮会什么、知道什么、能访问什么？ | Skills 提供方法，RAG 提供当前证据，Memory 提供历史事实；普通工具与 MCP 提供动作入口。 |
| 控制结构 | 先做什么、交给谁、何时回来、何时结束？ | 提示链、路由、并行、规划重规划、协调交接、评估修复与人工介入。 |
| 运行保障 | 退出、重复、冲突或越权时怎样处理？ | 权限、预算、检查点、幂等、任务租约、消息协议和资源回收。 |

因此，“采用 RAG”还没有确定控制结构。检索可以放在单次回答前，也可以放在链中的证据准备节点，或被规划器按需调用。同样，改成 MCP 工具不会自动引入多 Agent；换成 HTTP、CLI 或 SDK 工具也不必改变整张流程图。

MCP 的协议与连接生命周期继续在[外部工具章](./mcp-tools.md)讲解。本部分聚焦动作在流程中的位置与契约；普通工具的实现细节仍沿[工具注册](./tools-and-graph.md)和[权限边界](./permissions.md)学习。

## 3. 先确定控制权，再选模式

首先建立最小基线：资料已齐全，一次生成再校验是否足够？如果足够，就先保留它。如果有多个已知步骤，用明确的工作流组织；如果下一步要根据观察决定，再引入有界自主循环。

这里用“工作流”表示路径主要由程序预先限定，用“自主循环”表示模型能够根据观察提出下一动作。两者可以嵌套：固定升级审查工作流中的一个“补资料”节点，也可以运行受限的工具循环。模型负责提出动作，宿主仍负责验证参数、权限、预算和终止条件。

![从最小基线出发，根据已知步骤、独立子问题、动态计划、控制权、质量反馈与人工输入选择模式。](/learn-agent-rust/figures/agent-pattern-selection.svg)

图为选型示意，不是模型基准结果；多个需求可以组合，各章固定输入的实验已经运行，模型质量另验。

| 任务表现 | 优先考虑 | 要先定义的契约 | 章节 |
| --- | --- | --- | --- |
| 输入齐全，一次变换可验收 | 单次调用基线 | 输出 schema、证据要求、失败返回 | [第 16 章](./pattern-selection.md) |
| 步骤已知，上一结果供下一步使用 | 提示链（Prompt Chaining） | 中间产物与质量门 | [第 17 章](./prompt-chaining-routing.md) |
| 不同输入需要不同处理路径 | 路由（Routing） | 分类枚举、合法目标与兜底 | [第 17 章](./prompt-chaining-routing.md) |
| 子问题独立，汇总规则清楚 | 并行（Parallelization） | 成员清单、版本、失败与归并 | [第 18 章](./parallel-decomposition.md) |
| 执行中新信息会改变剩余步骤 | 规划执行与重规划（Plan–Execute–Replan） | 计划修订、结果账本和触发条件 | [第 19 章](./plan-execute-replan.md) |
| 子任务的数量或内容依输入变化 | 协调者与工作者（Orchestrator–Workers） | 任务规格、委派上限和返回格式 | [第 20 章](./orchestrator-workers-handoffs.md) |
| 后续对话需要另一个角色主导 | 交接（Handoff） | 当前控制者、载荷与权限 | [第 20 章](./orchestrator-workers-handoffs.md) |
| 有明确反馈，可针对缺陷重做 | 评估与修复（Evaluator–Optimizer） | 固定标准、候选版本和修复上限 | [第 21 章](./evaluator-reflection.md) |
| 缺用户信息，需编辑或批准 | 人工介入（Human-in-the-loop） | 等待身份、介入类型与动作修订 | [第 22 章](./human-in-the-loop.md) |
| 一项业务确实需要多种结构 | 模式组合 | 子结构返回值与全局账本 | [第 23 章](./pattern-composition.md) |

所有带章号的本部分链接均指向附独立实验的正文；默认决策采用固定夹具。

## 4. 用同一条升级报告任务理解差别

**提示链与路由。** 先按文件类型选择解析器，再从结构化依赖记录生成检查项，最后写报告。顺序和类别预先已知。每一步都有独立产物；解析失败时，报告节点不能继续消费上一版本的旧记录。

**并行。** 文档、依赖和配置可以在同一资料修订上独立检查。归并器需要确认成员齐全、版本一致，再处理发现之间的冲突。“同时运行三个节点”只解决并发，没有自动解决汇总正确性。

**规划与重规划。** 读到 Cargo workspace 成员后，才知道实际需要检查哪些项目。规划器修订剩余步骤，执行器保存已确认结果。重规划改变未来工作，不能抹掉已经发生的工具效果，也不能重置累计预算。

**协调与交接。** 协调者可以根据实际成员数生成工作者任务，然后等待和汇总。交接则改变后续对话的控制者：例如由技术审查角色移交给许可证审查角色。委派的结果返回后协调者继续；交接以后由接收角色主导，下一轮也由它回答，而且它看不到协调者手里的结果，要靠交接说明。这两种行为需要分别定义。

**评估与修复。** 草稿中的结论没有当前证据时，评估器返回具体断言和缺失项，修复器补证据或收缩结论。反馈必须绑定候选版本；达到上限或没有进展时结束。让模型反复说“再检查一下”不能证明质量提升。

**人工介入。** 补充目标版本属于澄清，修改草稿属于编辑，同意发布属于审批。三者的恢复行为不同：澄清让流程带着新输入重来，审批让挂起的调用从原处继续。批准绑定的是一次具体调用，需求变了，要先撤回还没用掉的批准。

最终组合可以是：并行检查 → 归并 → 生成 → 有限评估修复 → 人工确认。只有遇到新信息才重规划，只有需要专业角色主导才交接。每个任务采用哪些模式，由实际需求决定；组合以后还要验收接缝，第 23 章就遇到了内层循环的“收工”信号让外层流程整个停下。

## 5. 在 ADK-Rust 里用什么搭 {#adk-mapping}

| 模式 | 本部分用的 ADK-Rust 设施 | 章节 |
| --- | --- | --- |
| 单次调用、固定工作流、自主循环 | `LlmAgent`、`SequentialAgent`、带工具的 `LlmAgent`（`max_iterations`） | 第 16 章 |
| 提示链、路由 | `SequentialAgent`、`LlmConditionalAgent`、`ConditionalAgent`、`DecisionAgent`、`output_schema` | 第 17 章 |
| 并行与归并 | `ParallelAgent` + 归并用的 `CustomAgent` | 第 18 章 |
| 规划、执行与重规划 | `LoopAgent`（规划者 + 执行者）；adk-harness 计划模式（`exit_plan_mode`，Beta） | 第 19 章 |
| 协调者—工作者、交接 | `TeamSpec` / `CompiledTeam`：委派降为 `AgentTool`，交接走 `transfer_to_agent`；执行回执 | 第 20 章 |
| 评估与修复 | `LoopAgent`（写作者 + 评估者）；adk-retry-reflect 处理工具失败 | 第 21 章 |
| 人工介入 | 工具策略挂起调用、审批记录（SQLite）、工作流从挂起处恢复 | 第 22 章 |
| 组合 | workflow agents 嵌套、接缝适配、`RunBudget`、`OpenAIClient::compatible` | 第 23 章 |

**workflow agents 还是 adk-graph？** 本部分全部用 workflow agents：子 Agent 组成一棵树，顺序、并行、循环、条件是现成的组合子，状态放在会话里，escalate 让所在的工作流停下，挂起的调用让工作流从那一步恢复。结构能写成“几个 Agent 按某种顺序跑”时，它最直接。

第 5–7 章的 adk-graph 适合另一类需求：要显式的状态通道和归并规则（覆盖、追加、计数），要按步保存检查点、从任意一步恢复，要在节点里暂停、用 schema 校验人的答复，要条件边、运行时按数据扇出、带通道检查的子图，或者要用递归上限约束整张图的步数。两套 API 可以一起用：图的节点里可以运行一个 workflow agent，`GraphAgent` 也能作为 workflow 的一个子 Agent。选择的依据是“状态和恢复要多精细”，不是哪套更高级。

## 6. 两个容易混淆的研究术语

[ReAct](https://arxiv.org/abs/2210.03629)讨论任务推理与行动交替。本课程在工具循环中借鉴“动作 → 环境观察 → 下一决策”的组织方式，记录调用、结果、状态与公开决策摘要；不把模型私有思维过程作为必须暴露的接口，也不把现有脚本循环称为论文完整复现。

[Reflexion](https://arxiv.org/abs/2303.11366)还涉及将语言反馈保存在情节记忆中，用于后续尝试。第 21 章先设计单次任务内的评估修复，跨任务反思经验的写入与召回另列边界。[受控演进专题](./agent-rsi.md)讨论策略候选与发布验证，不能由一次报告修复推导为已实现 RSI。

ADK-Rust 提供 workflow agents、团队、审批记录、预算与会话这些执行基础。计划内容的检查、交接说明、评估规则、接缝合同与跨运行的总花费仍是应用契约。LangGraph 的模式示例帮助提出设计问题；不能从其 `Send`、`Command` 或检查点接口直接推定 ADK-Rust 有同等行为，以各章固定版本的实验为准。

## 8. 怎样复验本部分

各章沿问题 → 先运行 → 机制 → 故障场景 → 框架做了什么展开。在网站仓库根目录取一次 ADK-Rust 源码（`python3 scripts/fetch-adk-rust.py .cache/adk-rust`）后运行 `python3 scripts/verify-agent-patterns-adk.py --check`：把八章分别打包、在临时目录解压，跑格式、Clippy、32 项 Rust 测试和 66 个场景（每个场景连跑两次必须逐字节相同），并核对结果表与下载包。D07 另用独立进程逐条运行审批命令，D08 另用本地 fixture 跑 `live`，并运行 36 项模式对照驱动器自检。

上述默认检查使用固定决策，不调用真实模型。[第 23 章模型比较](./pattern-composition.md#model-comparison)冻结四题公开诊断集、请求预算与判分口径，配置服务后记录成功率、调用量、usage、耗时和失败样本；费用未知时保留 null。流程合同通过与真实模型的质量提升分别报告。

::: warning 常见误区
- Skills、RAG、Memory 与 MCP 可以用于多种模式，不能与控制结构混为同一组选项。
- 计划清单、固定 FanOut、子图封装分别只是机制基础，不能直接代表动态重规划、协调者或角色交接已经实现。
- 多角色、并行与反思都会引入额外开销；增加结构需要对照同一基线验收。
- 局部成功不等于组合成功；版本、预算、权限和终态都要在接缝处复核。
:::

## 本部分结论

先从任务结构确定控制权，再选择模式，并为每次分支、循环、委派和等待定义状态与停止条件。前面的图编排讲机制，本部分用 workflow agents 讲结构选择，后面的长任务与可靠性章节继续处理运行边界。

## 检查理解

1. 检索到资料再回答，一定需要自主 Agent 吗？

   <details><summary>参考答案</summary>

   不一定。固定检索加单次生成可能已满足需求；要看是否需要根据观察继续选择动作。

   </details>

2. 固定三个检查者与按输入生成工作者，差别在哪里？

   <details><summary>参考答案</summary>

   前者可以预先确定分支和归并成员；后者还需要生成任务规格、限制委派规模、校验动态返回并管理生命周期。

   </details>

3. 子 Agent 调用返回与 handoff 是同一种控制转移吗？

   <details><summary>参考答案</summary>

   不是。委派（子 Agent 当工具调用）完成后由父级继续；交接改变后续对话的主导角色，下一轮也由接手者回答。第 20 章的团队里接手者不能再交回，它需要的信息要靠交接说明。

   </details>

4. 修复后规则通过，能否断言真实模型质量提升？

   <details><summary>参考答案</summary>

   只能说明该规则在当前产物上通过。真实质量需要固定评估集、独立判分和与修复前基线的比较。

   </details>

5. 报告修改后，为什么不能直接复用修改前的批准？

   <details><summary>参考答案</summary>

   批准绑定的是一次具体调用（工具和参数）。内容变了，就是另一次调用，要重新批准；而还没用掉的旧批准，还可能在下一次运行里放行旧内容，需求变化时要先撤回（第 22 章）。

   </details>
