# 全书审查与学习方法

[课程总览](./index.md) · [技术跟踪](./technology-radar.md) · [Agent RSI](./agent-rsi.md)

**审查日期：2026-11-08。范围：Learn Agent by Rust 的 主线第 0–24 章、专题 1–6（实验标识 R00–R20、G01–G03、K01、P01–P06），以及总览、环境、架构、学习路径、配图与片段引用。** 本页聚焦教学叙事、证据口径、版本一致性和学习迁移。它不是逐行安全审计，也不把其他课程纳入“全书”。

这本书最有价值的主线，是把模型提出的动作放到可检查的运行边界中：消息是否配对、批准是否对应原动作、取消后执行者是否退出、恢复时效果是否重复。图和代码应帮助读者解释这些问题，最后能在新场景中作判断。

本次审查逐章检查了导入、目标、章节位置、图文入口、常见误区、结论、折叠答案与参考资料，阅读各章的问题、机制、实验边界和结论，并针对容易被误读的接缝补充迁移题。资源存在性由站点检查和构建验证。既有章节的运行记录用于定位其宣称范围；**本次没有重新运行全书所有历史实验，也没有把材料齐备等同于运行全部通过。** 新增 P06 独立重跑源码与最终下载包。

| 高 | 总览中的能力状态不断追加，仍保留“恢复待验证”等早期结论 | 混淆模块恢复、最小集成、真实模型与生产准入。 | 总览改为阅读与证据入口，更新恢复状态，明确各项结论的适用层。 |

| 中 | 缺少集中记录一手来源、查阅日期和迁移要求的位置 | 新论文或新协议容易变成无日期的“最新技术”。 | 新增[技术跟踪](./technology-radar.md)，区分规范、工程经验、论文报告与本地实验。 |

“高”表示容易造成能力或协议判断错误，不是已确认的安全漏洞等级。修订完成也不意味着右侧列出的待验收事项已完成。

## 2. 读者应当能沿图回答什么？

![先预测，再运行与构造反例，最后界定边界并把判断迁移到新问题。](/learn-agent-rust/figures/review-learning-chain.svg)

顺着图完成一章：先写出预期行为；运行后找能支持预期的轨迹与产物；再只破坏一个条件，解释结果为什么变化。最后才问换到另一个业务场景时还需要什么。

例如 R16 不能只记住 approve 消息类型。把它放到退款流程：批准是否绑定订单、金额、版本和审批者？旧批准被延迟投递，会不会批准新的退款？只有能解释这种反例，关联身份才成为可迁移的知识。

全书配图分三种阅读方式：架构图找调用与状态归属，时间线找动作顺序与故障窗口，结果图找数据来源、分母和实验条件。图下阅读提示与代码、输出互相对应。保留的参考站图继续原样使用，Python/Claude 语境、原编号和来源不改写成 Rust 实验结果。

**有图不等于讲清楚。** 下表统计资源覆盖，不能自动评判图意是否准确、文字是否有启发。新增七张图已纳入脚本生成；P06 结果图从实际输出证据读取，概念图明确为示意。

## 3. 成功要对应哪一层证据？ {#evidence-layers}

![受控输入、真实边界、恢复、跨机制集成与真实模型生产各需要独立证据。](/learn-agent-rust/figures/review-evidence-layers.svg)

图中向下意味着新增验证责任，不是成熟度打分。脚本模型可以连接真实文件、线程、MCP 子进程或数据库；它能验证运行合同，却无法给真实模型质量作保证。

| 看到的证据 | 可以据此判断 | 继续追问 |
| --- | --- | --- |
| 确定性消息与故障夹具 | 该输入下的状态机、权限和预算行为。 | 实际边界是否被跨越，效果是什么？ |
| 真实文件、线程、进程、数据库 | 本次环境下确实执行了对应 I/O。 | 超时或重启发生在哪一步？ |
| 退出点与恢复重放 | 指定窗口下的恢复、去重与拒写行为。 | 有没有未测的崩溃或外部副作用？ |
| R20 最小集成 | 选定合同在同一任务链中正确衔接。 | 哪些章节能力还没有接入这条链？ |
| P03 本地 HTTP | 客户端和宿主对受控返回的处理、独立产物验收。 | 真实 provider 的决策、时延和费用表现如何？ |
| 真实服务与准入演练 | 指定模型、任务、额度与故障条件下的观察。 | 是否覆盖目标业务、长期流量和事故恢复终点？ |

因此“模块都通过”不能直接加总为“生产系统通过”；重复运行确定性夹具不能当作多个独立模型样本。P06 的小题集与两个候选顺序同样遵守这个口径。

### 四条可以带出本书的判断原则

| 原则 | 贯穿章节 | 换个场景怎样问 |
| --- | --- | --- |
| 知识、建议与执行权分别管理 | R03、R07、R10 | 客服知识库说“可以退款”，它是否有权批准这一订单的退款？ |
| 声明、运行状态与实际效果分别记录 | R05、R16、P05 | 队友回复完成时，产物是否存在；取消返回时，写入者是否已退出？ |
| 身份按所证明的关系设计 | R01、R16、P02、P06 | 一次 RPC 的 call_id 能否代表跨重试的业务意图；候选是否基于当前父修订？ |
| 时间、额度与提交共同决定能否继续 | R11、R17、P01 | worker 重启后额度是否仍累计，租约过期后资源端是否仍拒绝旧代次？ |

这些原则的教育意义在于训练判断责任的能力。读者不必把某个框架当作答案，而应能说明：哪条信息支持哪个决定，谁对这个决定负责，哪个反例会推翻当前结论。把它们带到运维、客服或财务自动化中，仍然可以设计可检查的合同。

## 5. 下一轮最值得补的证据

| 尚未解决的事项 | 应怎样验证 | 对应章节 |
| --- | --- | --- |
| 真实模型的决策与任务质量 | 固定任务、真实 provider、独立判分，保存实际模型标识、轨迹、用量与不确定性。 | P03；本次没有调用付费模型。 |
| MCP 新规范迁移 | 新旧对照、能力与结果解析、断连重发、实际效果与回收，再运行集成链。 | R19、R20、技术跟踪页。 |
| 各可靠性模块共同上线 | 把检查点、业务幂等、租约、目标验收串成同一链，沿接缝注入故障。 | R20、P01、P02、P04、P05。 |
| 元改进真实收益 | 冻结独立评估、等预算、留出新任务，比较改进器的有效候选产出与总成本。 | P06；当前有限候选搜索未实现此项。 |
| 教学效果 | 请读者先预测、运行、解释新反例，收集误判与卡点，按证据改写文字和图。 | 全书；资源覆盖不能代替实际学习反馈。 |

技术维护按[技术跟踪页](./technology-radar.md#maintenance)的迁移流程进行。任何“已完成”应能回到一份具体结果与清楚的环境；任何“有效”应能指出相对于哪种基线、在哪种任务上有效。

## 6. 如何复查本次修订

在网站仓库根目录执行：

```sh
python3 scripts/review-learn-agent-rust.py --check
python3 scripts/sync-learn-agent-rust-course.py --check
python3 scripts/verify-agent-rsi.py --check
python3 scripts/generate-learn-agent-rust-figures.py --lesson P06
npm run docs:build
```

覆盖脚本检查章结构、迁移题与当前生成表；站点构建检查引用、资源跟踪和死链。P06 验证器实际执行 Rust 测试、Clippy、九次运行、两个拒绝路径，以及最终下载包的独立解压复验。构建或结构检查通过，不等于重新运行了历史章节的全部运行时测试。
