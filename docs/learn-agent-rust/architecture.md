## 1. 从读取 README 的任务出发

用户说：“告诉我这个项目如何运行。”模型可以提出读取 `README.md` 的请求。框架检查这次调用能不能执行，调用文件工具，再把结果与原调用 ID 一起交回模型。模型看到文件内容后，生成回答或继续请求工具。

这段往返由框架运行，规则由应用给出：工具的名称与参数、什么能做什么要批准、最多跑几轮、花多少预算、任务算不算完成，都要有明确的契约。后续加入审批、任务和团队时，仍围绕这条主链扩展。

![参考课程的模型循环在工具请求、工具执行与结果回传之间往返，直到模型结束本轮。](/learn-agent-rust/figures/upstream/r01-agent-loop.svg)

这张是参考站原图，保留其 Claude 消息和 `stop_reason` 语境。先沿“调用模型 → 判断是否需要工具 → 执行并回传 → 再调用”读一遍；在 ADK-Rust 里，这个循环由 `LlmAgent` 运行，第 1 章从事件和请求记录里把每一步看清楚。[原始章节](https://learn.shareai.run/zh/s01/) · [来源与许可](#reference-assets)。

## 2. ADK-Rust 的各部分怎样配合

![应用的策略与验收在最外层；Runner 管理会话并装入策略和预算；LlmAgent 与图运行模型和工具的循环；Llm trait 连接模型提供方，FunctionTool 操作限定工作区，会话与账本由 adk-session 保存。](/learn-agent-rust/figures/runtime-architecture.svg)

蓝色区域是一个 Rust 进程。向右是可选的外部模型服务和存储，向下是工作区。箭头表达职责和数据流，具体执行顺序由各章的实际轨迹验证。

| 部分 | 负责什么 | 课程中的位置 |
| --- | --- | --- |
| 应用 | 入口、策略规则（`ToolPolicy` / `DeclarativePolicy`）、预算取值、审批人、任务是否完成的判断。 | 每章的 `main.rs`；第 3 章写策略。 |
| `Runner`（adk-runner） | 加载会话、把策略与预算装进这次运行、逐条保存事件、恢复挂起或中断的调用。 | 第 0 章起每章都用。 |
| `LlmAgent`（adk-agent） | “调用模型 → 执行工具 → 结果写回 → 再调用”的循环；在行动前检查循环上限、预算、策略与审批。 | 第 1 章看清循环，第 4 章挂回调。 |
| 图（adk-graph） | 把 Agent 和普通业务步骤组织成节点，负责状态、路由、暂停恢复、并行与子图。 | 第 2 章入门，第 5–7 章展开。 |
| `Llm` trait（adk-core / adk-model） | 模型的边界：给一个 `LlmRequest`，返回回复。实验用 `ScriptedLlm` 或自写规则模型；接真实服务换适配器。 | 第 1 章写一个规则模型。 |
| `FunctionTool`（adk-tool） | 工具的描述、参数 schema 与处理函数；执行前按 schema 校验，声明副作用（只读 / 幂等 / 非幂等）。 | 第 2 章。 |
| 会话与账本（adk-session） | 会话事件、审批记录、动作账本、检查点，有内存、SQLite、PostgreSQL 等实现。 | 第 3 章审批记录，专题 1–2 的持久化。 |
| 工具与外部系统 | 在明确范围内读取工作区或执行业务动作。 | 从只读工具开始，逐步扩展。 |

框架接手了循环和大量检查，判断仍要分清归属：每章都有一节“框架替你做了什么、没做什么”，列出哪些行为由框架保证、哪些仍是应用的合同。

### 进程和协议边界

| 调用 | 边界 |
| --- | --- |
| `LlmAgent` 调用模型 trait 或工具 | 同一 Rust 进程中的方法调用。 |
| 脚本模型返回固定结果 | 进程内的确定性实验；不请求真实服务。 |
| 适配器请求真实模型 | 外部 HTTP；具体服务与工具协议需要独立验收。 |
| 文件工具读取练习目录 | 操作系统文件访问；需要路径、大小与权限限制。 |
| 会话、审批记录或账本保存到 SQLite / PostgreSQL | 本地文件或独立数据库进程；保存成功后才有对应的持久记录。 |
| MCP 工具调用 | 依具体传输跨越进程或网络；连接生命周期单独管理。 |

## 3. 方法、知识与外部连接放在哪里

在模型请求准备阶段，[Skills](./skill-loading.md)按需提供工作方法，[RAG](./retrieval-augmented-generation.md)选择当前可访问的证据，[Memory](./memory.md)召回历史确认的事实；系统提示词组装记录来源，压缩管理输入预算。在动作执行阶段，[MCP](./mcp-tools.md)由客户端连接外部服务器，宿主继续负责权限与生命周期。

详细区别与升级报告示例见[概念导读](./knowledge-and-capabilities.md)。这里描述职责位置，各章的独立实现与 R20 的组合分别验收。

## 4. 各类机制挂在哪里

控制结构单独在[第五部分 · 常见 Agent 设计模式](./agent-design-patterns.md)组织：从提示链、路由与并行，走向规划重规划、协调交接、评估修复、人工介入和模式组合。图编排章节解释节点与状态怎样运行，设计模式部分解释面对任务为什么选择这些结构。

| 模块域 | 典型机制 | 生效位置 |
| --- | --- | --- |
| 工具与执行 | 注册、schema 校验、策略、审批、回调、结果回传。 | 模型返回之后，工具执行前后。 |
| 规划与控制 | 计划、提示词、错误、循环上限和预算。 | 准备模型请求及判断是否继续时。 |
| 方法与知识 | 按需技能、资料检索与引用依据。 | 选择方法、构造证据与检查回答时。 |
| 记忆管理 | 历史压缩、事实提取与长期召回。 | 构造上下文前后。 |
| 并发与调度 | 后台执行、通知、定时触发与取消。 | 受控执行者及其通知入口。 |
| 多 Agent 平台 | 独立上下文、交接、任务领取与工作区。 | 各会话与共享任务系统之间。 |

## 5. 消息、会话与任务分别保存什么

| 概念 | 保存内容 | 生命周期与责任 |
| --- | --- | --- |
| 对话历史 | 一次运行里 `LlmAgent` 在内存中维护的用户、模型与工具结果，带调用 ID。 | 运行开始时从会话取出，运行中自己追加；下一次运行重新从会话读取。 |
| 会话事件 | `Runner` 逐条保存的事件，包括调用、结果、停止说明。 | 由选用的会话服务决定能否跨进程；内存会话随进程结束。 |
| 审批记录 | 等待中的请求与按指纹记录的决定。 | 决定取走即用掉；持久实现可跨进程。 |
| 动作账本 | 非幂等调用的开始与结果。 | 用于崩溃后恢复时不重复执行；必须持久才有意义。 |
| 图状态与检查点 | 图的通道值、当前位置、版本。 | 由检查点存储决定能否恢复。 |
| 待办清单 | 当前计划、步骤与进度。 | 从会话内展示开始，便于用户与模型检查。 |
| 持久化业务任务 | 依赖、所有者、状态与执行记录。 | 由独立任务存储管理，后续验证领取与接管。 |
| 长期记忆 | 有来源、可修订、可召回的事实。 | 跨会话保存，有独立版本与留存规则。 |

图节点是一个运行步骤，业务任务是一项要完成的工作，一次运行是 `Runner` 处理一条输入的过程，Tokio task 是异步执行单元。一项业务任务可以经历多次运行和多个图节点。

## 6. 恢复要对应具体保存点

工具成功后，如果结果没来得及保存，恢复时可能重复执行。调用 ID 用于配对；涉及业务副作用时，还需要操作身份、幂等或对账。ADK-Rust 的动作账本能让同一次调用在恢复时不再执行，但模型在新一轮里重发就是新的调用，去重仍要靠稳定的业务身份。[P01](./postgres-checkpoints.md)与[P02](./side-effect-reliability.md)分别验证这些故障窗口；与完整 Agent 的生产接线仍需分别验收。

::: warning 常见误区
- 图路由表达运行规则；模型的工具选择仍需真实模型或脚本模型结果驱动。
- 会话保存、操作幂等和自动接管各自需要证据，不能用一项通过推断其余能力。
- 模型正常返回答案，表示本轮按协议结束；任务是否完成仍需固定断言或后续目标评估。
- 框架接手了循环，不等于接手了判断：策略规则、预算取值、任务验收仍归应用。
:::

## 检查理解

1. `LlmAgent` 调用模型，需要 HTTP 吗？

   <details><summary>参考答案</summary>

   `LlmAgent` 和模型 trait 之间是同进程方法调用。使用真实服务时，由具体的模型适配器向外部服务发送 HTTP；脚本模型则在进程内返回结果。

   </details>

2. 待办清单和持久化任务系统各解决什么问题？

   <details><summary>参考答案</summary>

   待办清单让当前计划与进度可见；持久化任务系统还需要定义任务身份、依赖、状态迁移、所有权和恢复。后者需要独立的存储与运行验收。

   </details>

3. 模型说“完成”，是否足以标记整个业务任务成功？

   <details><summary>参考答案</summary>

   它可以是一次合法的最终模型响应，但业务完成需要任务断言或评估证据。例如要求读取文件，就检查真实工具调用与返回内容，而不只看模型的自述。

   </details>
