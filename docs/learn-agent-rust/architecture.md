## 1. 从读取 README 的任务出发

用户说：“告诉我这个项目如何运行。”模型可以提出读取 `README.md` 的请求。程序检查路径与参数，调用文件工具，再把结果与原调用 ID 一起交回模型。模型看到文件内容后，生成回答或继续请求工具。

这段往返由应用驱动。工具名称、参数、权限、轮次上限和错误处理都需要明确的契约；后续加入审批、任务和团队时，仍围绕这条主链扩展。

![参考课程的模型循环在工具请求、工具执行与结果回传之间往返，直到模型结束本轮。](/learn-agent-rust/figures/upstream/r01-agent-loop.svg)

这张是参考站原图，保留其 Claude 消息和 `stop_reason` 语境。先沿“调用模型 → 判断是否需要工具 → 执行并回传 → 再调用”读一遍；Rust 主线将使用结构化 `tool_calls` 与调用 ID 实现对应过程。[原始章节](https://learn.shareai.run/zh/s01/) · [来源与许可](#reference-assets)。

## 2. 两个框架与应用层如何配合

![入口与应用策略经图执行器推进应用节点，节点调用模型接口和工具，检查点由会话存储保存。](/learn-agent-rust/figures/runtime-architecture.svg)

蓝色区域是一个 Rust 进程中的目标模块。向右是可选外部模型服务，向下是工作区与存储边界。箭头表达职责和数据流，后续章节会用实际 trace 验证具体执行顺序。

| 部分 | 负责什么 | 课程中的位置 |
| --- | --- | --- |
| 入口与应用策略 | 接收请求、选择能力、授权、预算、停止原因与输出。 | CLI 入口及运行策略。 |
| `graph-flow` | 图节点、路由、会话身份、推进位置与存储接口。 | 把一轮模型调用和工具执行拆成可观察的步骤。 |
| 应用适配 | 消息历史、待执行调用、工具注册、参数校验和结果回传。 | `ModelTurn`、`ExecuteTools` 等计划节点。 |
| `langchain-rust` | 模型接口、消息类型、结构化结果和客户端适配。 | 以保留工具字段的调用路径连接模型。 |
| 工具与外部系统 | 在明确范围内读取工作区或执行业务动作。 | 从确定性只读工具开始，逐步扩展。 |
| 会话与任务存储 | 保存可重建状态，提供相应的版本和恢复契约。 | 初版内存；后续按章节引入持久化。 |

两库通过应用自己编写的节点连接。R01 先展示显式循环；R02 再把同一行为映射到图。`AgentExecutor` 留作后续对照，主线由图节点掌握循环边界。

### 进程和协议边界

| 调用 | 边界 |
| --- | --- |
| 图节点调用模型 trait 或工具注册表 | 同一 Rust 进程中的方法调用。 |
| 脚本模型返回固定结果 | 进程内的确定性实验；不请求真实服务。 |
| 客户端请求真实模型 | 外部 HTTP；具体服务与工具协议需要独立验收。 |
| 文件工具读取练习目录 | 操作系统文件访问；需要路径、大小与权限限制。 |
| 保存到 PostgreSQL | 独立数据库进程；成功保存后才有对应持久化检查点。 |
| 后续 MCP 工具调用 | 依具体传输跨越进程或网络；连接生命周期单独管理。 |

## 3. 五类机制挂在哪里

参考课程按工具、规划、记忆、并发和协作组织机制。本站用这些关注点定位每章新增内容，同时沿前文的实际调用链解释数据如何移动。

| 模块域 | 典型机制 | 生效位置 |
| --- | --- | --- |
| 工具与执行 | 注册、权限、审批、Hooks、结果回传。 | 模型返回之后，工具动作前后。 |
| 规划与控制 | 计划、技能、提示词、错误和预算。 | 准备模型请求及判断是否继续时。 |
| 记忆管理 | 历史压缩、事实提取与长期召回。 | 构造上下文前后。 |
| 并发与调度 | 后台执行、通知、定时触发与取消。 | 受控执行者及其通知入口。 |
| 多 Agent 平台 | 独立上下文、邮箱、任务领取与工作区。 | 各会话与共享任务系统之间。 |

## 4. 消息、会话与任务分别保存什么

| 概念 | 保存内容 | 生命周期与责任 |
| --- | --- | --- |
| 模型消息历史 | 有序的用户、assistant 与工具结果，包含调用关联。 | 属于单个 Agent 会话；跨进程时需显式保存。 |
| 应用运行状态 | 消息、待执行调用、工具游标、预算和停止原因。 | 应用持有；图版本将可序列化内容写入 Context。 |
| 图会话 Session | 图身份、当前位置、Context 与存储版本。 | 持久性由选用的 Storage 决定。 |
| 待办清单 | 当前计划、步骤与进度。 | 从会话内展示开始，便于用户与模型检查。 |
| 持久化业务任务 | 依赖、所有者、状态与执行记录。 | 由独立任务存储管理，后续验证领取与接管。 |
| 长期记忆 | 有来源、可修订、可召回的事实。 | 跨会话保存，有独立版本与留存规则。 |

图节点是一个运行步骤，业务任务是一项要完成的工作，Tokio task 是异步执行单元。一项业务任务可以经历多个图节点和多次模型请求。

## 5. 恢复要对应具体保存点

初版先顺序执行同轮工具，之后再研究逐工具恢复。整批工具放在一个节点中时，不能直接推断每个内部动作都有独立检查点。

工具成功后，如果会话保存失败，再次恢复可能重复执行。调用 ID 用于消息关联；涉及业务副作用时，还需要操作身份、幂等或对账。P01–P02 会在具体故障窗口中验证这些边界。

::: warning 常见误区
- 图路由表达运行规则；模型的工具选择仍需真实模型或脚本模型结果驱动。
- 会话保存、操作幂等和自动接管各自需要证据，不能用一项通过推断其余能力。
- 模型正常返回答案，表示本轮按协议结束；任务是否完成仍需固定断言或后续目标评估。
:::

## 6. 本课程的主线选择

先用显式代码理解消息往返，再用图节点展示执行边界；先用脚本模型固定控制流，再验证客户端协议和真实模型；先把正常与失败路径跑清楚，再扩大到持久化、后台执行和团队。

已有筹备实验采用 `graph-flow 0.8.1` 和 `langchain-rust 8.0.0` 的固定源码。课程工程将在独立目录验证依赖、保留锁文件后确定运行命令。当前目录与原图可阅读，课程学习包仍待实现。

## 检查理解

1. 图节点调用模型客户端，两个库之间需要 HTTP 吗？

   <details><summary>参考答案</summary>

   两库之间是同进程方法调用。使用真实服务时，由具体模型客户端向外部服务发送 HTTP；脚本模型则在进程内返回结果。

   </details>

2. 待办清单和持久化任务系统各解决什么问题？

   <details><summary>参考答案</summary>

   待办清单让当前计划与进度可见；持久化任务系统还需要定义任务身份、依赖、状态迁移、所有权和恢复。后者需要独立的存储与运行验收。

   </details>

3. 模型说“完成”，是否足以标记整个业务任务成功？

   <details><summary>参考答案</summary>

   它可以是一次合法的最终模型响应，但业务完成需要任务断言或评估证据。例如要求读取文件，就检查真实工具调用与返回内容，而不只看模型的自述。

   </details>
