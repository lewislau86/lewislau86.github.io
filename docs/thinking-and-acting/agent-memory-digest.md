## 引子：向后理解，向前生活

文章从克尔凯郭尔的一句话开头：人生只能向后理解，却必须向前去过。作者说，给 AI Agent 设计记忆时，他们碰到的正是同一种两难。

人一边生活一边不停地形成记忆。海马体负责在当下快速捕获经历，让它马上可用；但只有一部分经历会被巩固成长期知识。这种巩固很多发生在大脑“离线”的时候：睡眠和安静休息时，海马体会回放近期经历，逐步提炼它们，并整合进新皮层——我们通常称为“知识”的东西，大多存在那里。

Agent 的记忆也可以这样分工。Agent 做事时，大量过程本来就被记录在日志或对话记录（transcript）里。Letta 与 UC Berkeley 的研究者提出过 [sleep-time compute](https://arxiv.org/abs/2504.13171)：让模型利用两次交互之间的空闲时间重新组织已有上下文。同样的思路可以用来整理记忆——回看日志，修正错误，产出新的笔记和表征。这个过程常被称为**做梦**（dreaming）。

作者说，做梦已经成为他们帮 Claude 建立有效记忆的有用工具。全文介绍他们如何看待 Agent 记忆，并通过几组评测说明包括做梦在内的各个组成部分分别起什么作用。

## 记忆笔记

先界定范围。文中的“Agent 记忆”，指 Claude 从经验中获得、能跨会话保留、并以日后可读取的上下文形式保存下来的知识；经验既包括与用户的交互，也包括被分配的任务。它**不包括**模型学习或管理上下文的其他方式：权重的改变（训练时设定的内部参数）、[上下文学习](https://www.anthropic.com/research/in-context-learning-and-induction-heads)（只在单次对话内获得的知识），以及 [compaction](https://platform.claude.com/docs/en/build-with-claude/compaction)（Claude 写摘要替换较早的轮次，以便在新的上下文窗口里继续工作）。

人脑中，在经历之前、之中或之后释放的化学信号，可以把一段记忆标记为“重要”；被标记的记忆在离线时期被回放得更频繁，这种**回放**有助于把它们稳定并整合进长期记忆。

Claude 也可以在会话日志里随时给显著事件打标签，方便以后查找；或者把它们[写进一个记忆存储](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)，比如一个存放记忆笔记的文件夹。问题随之而来：还不知道后面会发生什么，Claude 怎么在当下判断什么是显著的？

## 记忆有时是对未来需要什么的预测

记忆有时就是一种预测。写下一条规则，等于预测它描述的模式还会再次用到；写下一条已验证的事实，等于预测未来某次会话会想直接依赖它，而不必重新核对。作者说，Claude 做这类预测的能力已经明显提高。

例子来自 [Continual Learning Bench（CL-Bench）1.0](https://continual-learning-bench.com/news/cl-bench-1-0/)，这是一个衡量 Agent 能否借助记忆完成长程任务的基准。其中一个任务要求 Claude 通过查数据库回答一系列问题；每答完一题，它会被告知正确答案，并可以写一条记忆帮助后面的题目。

这里记忆可以支撑一个**学习闭环**：答错时，记录失败，提出“哪里出错”的假设，检验这些假设，再把结论写成以后作答的规则。

他们用 [Claude Managed Agents](https://platform.claude.com/docs/en/managed-agents/overview) 运行这个任务。每道题都在一个全新会话里开始，唯一的例外是：Claude 可以读取一个跨会话持久保存的[记忆目录](https://platform.claude.com/docs/en/managed-agents/memory)。

不同模型把这个闭环走到了不同的程度：

- **Claude Sonnet 4.6** 走到“提出理论解释为什么答错”为止。它的记忆目录里散落着若干文件，每个都列着几条没有检验过的猜测。
- **Claude Opus 4.7** 把笔记合并成一份参考文档，并开始标注哪些事实已核对、哪些尚未确认。
- **Claude Sonnet 5** 在判分确认后把答案标为“已确认”，答错时写下更正。
- **Claude Opus 5** 是这些模型中第一个**闭合循环**的：它的大多数条目包含一条规则（以及它如何知道这条规则成立）、早先题目的答案，以及对途中发现的陷阱的明确警告。
- **Claude Opus 5.5 与 Claude Sonnet 5.5** 也闭合了循环，用记忆保存经过验证的作答规则。有记忆时两者得分与 Opus 5 大致相同，但没有记忆时的基线略高。

## Claude 学会了判断显著性

第二组观察来自 Claude 玩《精灵宝可梦 红》（[Pokémon Red](https://www.youtube.com/watch?v=CXhYDOvgpuU)）。这款游戏要求完成复杂的长程任务，正好用来检验 Claude 判断“什么值得存进记忆”的能力。每次运行开始时，模型都会拿到一个可读写的记忆文件夹。

作者比较了 Claude Sonnet 3.7 和 Claude Fable 5 各一次运行、在大约第 10,000 步时的记忆文件夹。关键差别在于各自认为什么值得记：

- **Sonnet 3.7** 假定什么都可能有用，不加选择地写入。它的文件夹像一座遭遇档案馆：每场战斗、每件拾到的道具、每个遇到的 NPC 往往各占一个文件。最终它写了 **413 个文件、分布在 225 个文件夹里**，拿到 **1 枚徽章**（徽章标志玩家在游戏中的进度）。
- **Fable 5** 只在两个文件夹里写了 9 个文件，外加一个顶层的 `global.md`，拿到 **4 枚徽章**。

![Pokémon 中两个模型的记忆目录对比](/thinking-and-acting/figures/agent-memory-pokemon.svg)

*图 3：同一比例尺下两个模型的记忆目录（依原文图 4 的数字重绘）。原文树图标注：Sonnet 3.7 共 413 个文件、977,930 个字符；Fable 5 共 10 个文件、43,406 个字符。*

Sonnet 3.7 的做法之所以成问题，主要是因为宝可梦的游戏状态一直在变，它那份详尽的记录不断过时。随着游戏推进，它花在翻检记忆上的时间和资源越来越多，花在玩游戏上的越来越少。例如在第 10,000 步左右，它开始建立第四个存放“master”记忆文件的文件夹；接下来的 17 步里，它新建了 6 个文件、删掉了 9 个，游戏里却一个动作都没做。

Fable 5 则把记忆用在**游戏没有明说的东西**上。Sonnet 3.7 记下的一些信息——比如玩家有多少钱、人在地图哪里——每一轮都能直接从屏幕上读出来，存下来是多余的。相反，策略、计划和验证过的规则只有 Claude 自己推出来才会存在，不写下来就会消失。

Fable 5 的组织方式也与此对应。`global.md` 像一块仪表盘，放着当前目标、预先写好的打道馆计划（道馆是赢取徽章的挑战），以及模型自己定下的记忆使用规则；`locations` 文件夹存特定路线的导航计划；`gameplay` 文件夹存它对游戏机制的理解所形成的策略。例如，连续 7 个精灵球都没能抓住鲤鱼王（最容易抓的宝可梦之一）之后，Claude 写下：如果连续 3 次以上失败，就改变节奏，在菜单步骤之间插入额外的“等待”——刚这样做就抓住了。

记忆文件夹小得多的 Fable 5，在游戏里走得比 Sonnet 3.7 远得多。Opus 5.5 采取类似做法：只保留一小份记录当前目标和下一步的笔记，边玩边改写，最终通关。

## 引导 Claude 写记忆

作者发现，**告诉 Claude 记忆是做什么用的，而不是规定怎么用**，效果更好。在 CL-Bench 上，他们只是告诉 Claude 有一个记忆文件夹可用。这样笼统的指引已足以让 Opus 4.7 和 Opus 5 有效地使用记忆，两者的成绩都明显提升（见图 2）。

他们也试过给模型规定具体的写入规则，每次测试一条规则，比较每个模型在有、无该规则时从记忆中获得的增益。当规则是“**只记录失败**”时，Opus 5 和 Opus 4.7 都失去了记忆带来的大部分提升。对较强的模型来说，让它自己判断显著性，比事先定死规则更有效，定死的规则反而可能削弱表现。

![引导记忆写法的两个实验](/thinking-and-acting/figures/agent-memory-steering.svg)

*图 4：左为 Sonnet 4.6 在有无引导指令下的成绩；右为规定“只记录失败”后记忆增益的变化（原文图 5 的数字；右图红条由本站结合图 2 推算）。*

引导对较老的模型帮助最大。例如 Sonnet 4.6 经常不去读记忆目录里的文件，也没有检验自己关于答错原因的理论。提示它在作答前先读记忆文件、并明确检验自己的理论之后，它的基准分数几乎翻了一倍（0.330 → 0.641）。Sonnet 5 则会自发这样做：不加提示时，它在 10 次中有 9 次会先读记忆再作答；Sonnet 4.6 做到这一点的比例不到一半。

对前沿 Claude 模型，他们通常只给出简单的指引：当用户要求、或某件事明显值得记住时，就创建记忆笔记——具体判断交给 Claude。

## 做梦可以纠正记忆

由于 Claude 是按会话中自认为显著的东西写记忆的，一条一开始就错、或随环境变化而失效的笔记，会在之后的会话里被读到并被信任。

做梦让 Claude 有机会拿笔记去对照原始对话记录。正面的例子同样来自宝可梦：Claude 通过 Managed Agents 运行，记忆放在一个挂载的目录里。

游戏中，玩家必须穿过 Mt. Moon（月见山），这是一个入口在地图西侧、出口在东侧的洞穴系统。入口附近有个陷阱：一道单向台阶，跳下去会落回来时的那条路线，而且没有明显的办法爬回去。Claude 把山脚的 PokéCenter（宝可梦中心）当作地标，所以它会不会走下台阶，取决于它认为 PokéCenter 在山的哪一侧。

有一次，Claude（错误地）记下 PokéCenter 在东侧。走出 PokéCenter 时，它宣布“Mt Moon is behind me”，并把笔记更新为“Mt Moon DONE”。可月见山并不在它身后。几步之后，Claude 走下台阶，落回了来时的路线。它的导航工具没有显示这道落差，于是 Claude 得出结论“I overshot far west”（我往西走过头了），认定自己一直在正确的一侧——其实并没有。

![Mt. Moon 案例：错误笔记与做梦纠错](/thinking-and-acting/figures/agent-memory-mt-moon.svg)

*图 5：一条被纠正的笔记改变了结局（依原文图 7、图 8 的描述重绘）。用未纠正的笔记，Claude 说“Mt Moon is behind me”，朝下一座城市走，结果回到来时的路线；用做梦纠正后的笔记，它说“现在我需要找到 Mt Moon 的洞口重新进去”，然后回到了洞里。*

接着他们测试做梦能否帮 Claude 避开这个陷阱：对含有错误 PokéCenter 位置的记忆文件夹运行做梦。Claude 把笔记与会话记录对照，发现错误并改写了它——对话记录提供了验证记忆的事实依据。带着纠正后的笔记，Claude 直接回到月见山里，最终到达 Cerulean City（华蓝市）。

在使用未纠正笔记的那次运行里，Claude 三次掉回那条路线。第三次失败后它似乎放弃了，写道：“I'm going to stop rather than keep looping.” 实验装置的自动回复让它继续，于是它一路退回了山前的城镇 Pewter City（深灰市），打算在那里治疗和补给。这次运行直到结束都没有到达华蓝市；没有记忆的那次运行同样没有过山。在 3,000 次累计动作的对比里，记忆 + 做梦的运行在第 1,935 次动作时抵达华蓝市。

## 做梦可以构建新的记忆表征

借助做梦，Claude 可以构建帮助检索记忆的**表征**。其中一种叫 [wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)：由 Claude 编写和维护的一组页面，每页汇集它对某个主题的了解，并链接到其他笔记。这些链接相当于一张地图，让 Claude 在需要时能在记忆中快速筛选、定位。

wiki 这类表征能帮助 Claude 在不断增长的知识库中穿行。为了检验它的价值，他们使用了 Stainless（Anthropic 于 5 月收购的一家软件公司）的内部文档语料：约 **35 万个文件、约 4.2 亿 token**。他们针对这批语料编了 **25 道评测题**，给 Claude 一个搜索工具来探索语料，同时让它通过做梦基于这些文件构建 wiki：在 **128 次会话**中，让 Opus 5 Agent 探索文件、编写或修正互相链接的 wiki 页面、合并重复内容，并把论断与原始资料核对。

每次会话都在前面会话的进度上继续，通过一份共享日志协调工作。当做梦从 2 次会话扩展到 128 次时，25 道题上满足的评分点比例从 **13% 升到 48%**。

Claude 是增量地建 wiki 的：先建出初版，再在后续几轮做梦中补充、修改或修剪。早期 Claude 的知识像新员工，只靠 wiki 回答问题的能力有限；做梦越多，它的知识地图越丰富，就像一位资深员工。测试发现，**wiki 与搜索工具同时可用时帮助最大**：两者并用时，总分随 wiki 增长从 54% 升到 61%；只有搜索工具时为 53%；只用 wiki 时的最好成绩是 48%。同时使用搜索和 wiki，每道题还能省下约 **2 万 token**。

![wiki 随做梦次数增长的效果](/thinking-and-acting/figures/agent-memory-wiki-scaling.svg)

*图 6：随着做梦会话增加，wiki 的效果与规模（原文图 10 的数字）。原文网络图显示 2 次会话后 wiki 有 103 页、766 条链接，128 次后有 222 页、12,893 条链接。*

他们还想知道哪类任务能从 wiki 中受益，于是用了 [Harvey LAB](https://github.com/harveyai/harvey-labs) 基准和一组关于某次并购的文档。LAB 给 Claude 一批文档，要求据此写一份法律简报，再按评分清单打分。作者调侃说，这比玩宝可梦少了点趣味，但提供了多样的文档集合来建 wiki。

他们让 Claude 先从文档建 wiki，再让它分别借助 wiki 和直接文件搜索来回答并购问题、撰写法律简报。其中一项测试有 **24 道并购问题**，过半需要跨多份文档找信息，很多还需要判断或计算。在这些题目上，Claude 查阅 wiki 时得分 **87%**，只用搜索时为 **73%**。

但在别的情形下 wiki 没那么有用。在一个 LAB 任务中，简报的评分点大多能从单一文档里用文本搜索直接找到，wiki 相对搜索没有明显增益。在另一个 LAB 任务中，wiki 长得比原始文档还大：10 份文档共 115 KB，wiki 却有 68 页、255 条链接、203 KB，是原文的 1.77 倍，还有些页面没有任何链接。作者借用博尔赫斯的短篇《论科学的精确性》：那里的制图师画出了与帝国一样大的地图——Claude 也做出了一份极其详尽、却什么都没有抽象出来的 wiki。

## 做梦可以把笔记提升到记忆层级的顶端

做梦还能把笔记“浮”到记忆层级的最上层，再由 Agent harness 在每次会话开始时预先加载进 Claude 的上下文。这样 Claude 不必去搜索这些内容，甚至不需要知道有东西可搜。

把记忆提升进新会话（一种上下文注入）必须谨慎。注入的记忆占用宝贵的 token；一条错误的笔记会被带进每一次会话；而且加载了也不保证 Claude 会照做——[Claude Code 的文档](https://code.claude.com/docs/en/memory)就提醒过，指令文件越长，遵循度越低。所以记忆层级的顶层必须保持相对小，做梦在这里的大量工作就是维持这一点：把部分细节移到下层，只在原处留下链接。

Claude Code 的 auto memory 用同样的办法保持注入层精简，由 Claude 在会话中维护。它不会把全部 auto memory 都加载进每次会话，只加载 `MEMORY.md` 的前 **200 行或 25 KB**。这段开头充当索引，告诉 Claude 自己知道什么、去哪里找。

## 做梦可以让记忆服务于特定目标

做梦还能塑造记忆的生长方向。像 [Claude Duet](https://support.claude.com/en/articles/17631495-get-started-with-claude-duet) 这样的助手，往往受益于围绕它所帮助的那个人组织起来的记忆；做梦可以调整为服务某个特定目标来构建记忆。

指导记忆如何生长的指令因任务而异，它告诉 Claude 哪些信息真正重要。例如，LAB 中有一个任务模拟一次公司收购并提供一组合同，简报的评分标准是能否准确描述合同条款。

他们起初只给了基础的建 wiki 指令，没有说明 wiki 将如何使用。这个任务高度依赖合同条款；而在建 wiki 的过程中，几个 Agent 同时往一张共享的合同条款表里写入。结果 wiki 缺了关键事实：用这份 wiki 生成的简报只覆盖了 57 个事实中的 41 个（72%）。排查发现，共享表格对条款概括得很差、甚至漏掉一些，因为 Agent 们互相覆盖了彼此的工作。

合同条款是 wiki 最重要的部分，但指令里没这么说。为了找到更好的指令，他们跑了一个循环：Claude 反思失败，提出对指令的修改，再重建 wiki。通过这个循环，Claude 发现了忠实保留合同条款的重要性，并据此改写了建 wiki 的指令：每份合同单独一页，由一个 Agent 负责，逐字引用条款而不是汇总进共享表格。用改进后的 wiki 生成的简报，**全部评分点都能满足**，从 72% 升到 100%。

## 做梦可以补上单次会话留下的缺口

Claude 写记忆笔记时，只看得到当前会话的上下文；做梦则可以跨多次会话搜索，找出共同规律或纠正共同错误。

为 LAB 基准建 wiki 时，Claude 有时会链接到尚未创建的页面，第二轮做梦补上了其中很多缺口。在一个任务中，做梦发现有 9 条链接指向一个不存在的页面，便把它们改指向同一文档已有的页面；它还新增了 3 页，其中包括一个索引页。

## 向后思考，向前看

关于如何为 Agent 设计记忆系统，还有很多悬而未决的问题。

其一是**什么时候创建记忆**。Claude 在工作中可以写入记忆存储（文件夹、文件或数据库），在源头捕获显著性，让重要细节马上可供后续轮次或会话使用；但当场记笔记难免分散它对主任务的注意力。做梦可以把记忆创建推到后台，但做梦的产出未必能立刻被 Claude 用上。

其二是**如何让记忆可靠地保持更新**。Claude 可能做出错误预测，或写下一开始就错的规则；记忆也会随环境变化而漂移、失去相关性。做梦是修正这些错误的一种方式，但它需要算力，让 Claude 持续复查全部记忆未必现实。更可行的或许是让做梦集中在可能变化的信息上，或者精心调节做梦的频率（例如按记忆被访问的频繁程度）。

此外，把**对话记录搜索**当作 Claude 记忆的基础也是合理的选择。把表征（如 wiki）与搜索结合，有时会很有效；但 Claude 需要花算力维护这些表征，确保它们不会积累错误或幻觉。

尽管 Claude 对显著性的判断已经进步，任何模型都无法真正预知未来的轮次会发生什么。做梦给了 Claude 一个向后看的机会：用算力整理记忆、纠正错误、维护表征，让未来的会话更容易用上记忆。作者最后说，记忆系统会随 Claude 能力的提升而演进，关于如何设计 Claude 的记忆系统，他们还有很多要学。
