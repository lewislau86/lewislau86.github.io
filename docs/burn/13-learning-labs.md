# 第 13 章：实验路线与后续计划

[学习总览](./index.md) · [上一章：源码阅读地图](./12-source-reading.md) · [下一章：PyTorch 对照学习](./14-pytorch-comparison.md)

原理要靠小实验建立联系。这份路线先让每个结果都能手算，再逐步增加训练、设备迁移和性能分析。不要从“大模型能不能跑”开始，否则一旦出错，很难判断是数据、模型、依赖还是后端的问题。

## 当前已验证的内容

验证日期为 **2026-10-23**，环境是 **Windows、Rust 1.98.1、Cargo 1.98.1、Burn 0.22.1、Flex CPU**。程序在开发构建模式执行，目的是核对基础正确性，不是性能测试。学习包使用锁文件；Burn 本体声明最低 Rust 1.95，较旧工具链未在本次验证。

下载[完整 CPU 学习包](/burn/first-inference.zip)，解压后在项目目录运行下面四项。每项都包含断言，错误时会报错退出。

## 第一阶段：每一步都能手算

读完第 0～4 章后做 A、B。先写下每个张量的形状，再运行代码；每次只改一个输入或一个参数。

建议做两项练习，尚未作为独立实验程序提供：

1. 把偏置改为 `[0, -3]`，预期输出 `[5, 0]`，解释负数在哪一步变成零。
2. 先恢复默认偏置 `[0, 1]`，用两行输入 `[[1, 2], [0, 1]]`，预期输出 `[[5, 2], [2, 2]]`，解释同一组参数怎样服务多个样本。

本阶段验收标准：可以在不运行代码时算出结果；能够指出输入、参数、算子和模型各在哪里；知道 `Tensor<2>` 与形状 `[1, 2]` 不是同一件事。

## 第二阶段：知道梯度为什么是这个数

先运行实验 C，手算 `2x+1`。读到第 11 章后运行实验 D：向量输入 `[-2, 0, 3]` 配合求和目标，梯度为 `[-3, 1, 7]`；再乘上常量上游梯度 `[2,-1,0.5]`，得到 `[-6,-1,3.5]`。

下一步实现有限差分检查，分别观察 ε 过大和过小会怎样影响误差。这里的目标是理解梯度检查，不是选择“永远正确”的固定 ε。

然后运行 E/F，把标量导数推广到主线矩阵的 X/W/b 梯度，再观察一次手动更新怎样使损失从 16 降到约 0.64。能解释这个例子后，再进入完整训练循环。

本阶段验收标准：能区分设备允许自动微分、源输入保留梯度、执行 backward 和优化器更新；知道 clone 句柄不能用来恢复已经消耗的反向步骤。

## 第三阶段：完成一个训练与保存闭环

这是后续优先补充的完整实验，当前第 7 章先给流程。

| 步骤 | 要做什么 | 验收标准 |
| --- | --- | --- |
| 构造数据 | 选择可控的小型回归数据与目标 | 输入、目标形状和数值范围可解释 |
| 训练 | 自定义循环完成前向、损失、反向、更新 | 梯度有限，固定小批次 loss 明显降低 |
| 验证 | 使用 `valid()`，在独立数据上评估 | 能区分拟合训练集和泛化 |
| 保存 | 保存模型结构配置与参数 | 能说明文件分别保存什么 |
| 恢复 | 在新模型实例中加载参数 | 固定输入的输出在容差内保持一致 |
| 训练恢复 | 增加优化器等状态 | 恢复步骤和状态可检查，不只“程序能跑” |

应先完成原生 Burn 模型的保存加载，再加入外部模型格式。这样更容易把“文件往返”与“框架之间语义转换”分开排错。

## 第四阶段：比较 CPU 和 GPU

完成第 8～9 章后，再给学习包增加可选的 WGPU 等后端。开始时使用同样的固定小数据比较正确性；性能测试则需要扩大矩阵并记录规模。

计划按下面顺序验证：先确认设备能初始化，再验证输出形状和数值，然后区分冷启动、稳态前向、上传与读回，最后观察融合开关是否改变耗时。每次比较都保留版本、features、设备、shape、dtype、同步位置和误差记录。

本阶段验收标准：能够解释小模型在 GPU 上可能更慢的原因；不会把异步请求提交时间当作完整推理时间；不会在没有测量时宣称某条公式一定融合为一个 kernel。

## 第五阶段：导入与扩展

读完第 11 章，先完成已经提供的实验 D，解释 trait、具体 impl、宏路由和公共 Tensor 函数各自做什么。再分别选择一个外部模型和一个专用内核继续实验。

| 计划实验 | 首个合适对象 | 应检查什么 |
| --- | --- | --- |
| 权重导入 | 结构已知的小型线性网络 | 参数键名、权重方向、预处理、逐层误差 |
| ONNX 导入 | 只使用已支持算子的简单网络 | 算子支持、生成代码、动态维度与输出一致性 |
| 后端扩展的下一步 | 在已验证的 `y=x²+x` 上增加随机输入、更多布局和有限差分 | 对照组合参考的前向与梯度 |
| Fusion 接入 | 同一个公式，先明确采用哪一种方法注解 | 元数据与真实结果一致，普通返回字段可提前确定 |
| 专用 kernel | 与组合算子相同的公式 | 边界、布局、dtype、误差、耗时 |
| 浏览器部署 | 先选足够小的模型 | 目标编译、资源加载、异步接口、可用设备 |

这些是实验计划，首版没有提供已经验证完成的导入产物或 GPU 内核。自定义算子应先有可信的组合参考实现，再写底层优化。

## 读源码时留下什么记录

每次只追一个问题，例如“Linear 的偏置在哪里加”。记录入口函数、下一层调用、张量形状、涉及的设备与上下文，最后用两三句话解释职责。不要只抄一长串文件名。

建议采用以下笔记格式：

```text
问题：
版本 / 提交：
最小算例与预期：
源码入口与调用路径：
我现在能解释的行为：
仍未验证的假设：
实际运行结果与环境：
```

## 后续内容的补充顺序

先将训练、保存加载和梯度检查做成独立可运行实验；再补 CPU/GPU 对照和融合测量；随后完成一个小模型导入与一个自定义 kernel；最后扩展到 Transformer 推理、量化、内存规划和服务调度。

这些扩展会沿用本书的方法：先定义数学和输入输出，再检查实现与误差，最后讨论性能。遇到不懂的源码名词，回到它为哪一个具体计算问题服务，就更容易找到阅读方向。
