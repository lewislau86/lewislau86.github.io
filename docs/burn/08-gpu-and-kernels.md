# 第 8 章：GPU 与计算内核

[学习总览](./index.md) · [上一章：从训练到推理](./07-training-to-inference.md) · [下一章：框架怎样执行一次计算](./09-how-execution-works.md)

> 首版导读，实验状态见[实验路线](./14-learning-labs.md)。本章依据 Burn **v0.22.1**，固定提交 `907ab111a02c2dea47bc41633754f095c6b2220e`；示意图与伪代码帮助理解执行过程，不代表本机已完成 GPU 验证。

本章只解决一个问题：当你写下 `Y = relu(XW + b)`，到底是谁在读数据、做乘加、保存结果？读完后，你应能解释 CPU 与 GPU 的分工，以及为什么“Rust 函数返回了”可能还不等于“GPU 算完了”。

前两章已经完成“同一份数据向前计算、梯度向后计算”的数学路线。这一章只换观察角度：无论前向还是反向，其中的张量运算最终都需要处理器读取数值并执行。先学工作怎样分配与依赖怎样保证，再学 CubeCL 和 JIT 的名字。

## 先在纸上算一次

取一个样本的两个特征，输出两个数。这次把主线偏置的第一个值改为 -6，以便观察 ReLU 把负数变成零；其余输入和权重保持主线取值：

```text
X = [[1, 2]]       shape = [1, 2]
W = [[ 1, -1],
     [ 2,  1]]     shape = [2, 2]
b = [[-6, 1]]      shape = [1, 2]
```

`shape` 是每个维度的长度。这里使用二维张量；`XW` 表示矩阵乘法，不是对应位置相乘。

1. 第一个输出：`1 × 1 + 2 × 2 = 5`。
2. 第二个输出：`1 × (-1) + 2 × 1 = 1`。
3. 加偏置：`[5, 1] + [-6, 1] = [-1, 2]`。
4. `ReLU(t) = max(t, 0)`，所以 `Y = [[0, 2]]`。

CPU 或 GPU 运行时都必须遵守这套数学规则。差别在于如何分配工作、如何取数，以及使用什么精度计算。

## CPU、GPU、host、device 分别是什么

| 词语 | 本章中的含义 | 在这个例子里做什么 |
| --- | --- | --- |
| CPU | 擅长控制流程和通用任务的处理器 | 运行 Rust 程序、准备输入、发出计算请求 |
| GPU | 适合同时处理大量相似计算的处理器 | 并行处理许多输出元素或矩阵小块 |
| host（主机侧） | 发起和管理任务的一侧，通常指 CPU 程序及其内存 | 持有待上传的输入、处理最终结果 |
| device（设备侧） | 执行张量计算的目标；也可以选择 CPU 设备 | 持有张量并运行选定运行时的计算 |
| buffer（缓冲区） | 保存一段数据的存储区域 | 存放 `X`、`W`、中间结果或 `Y` 的数值 |
| kernel（计算内核） | 在设备上执行的一段计算程序 | 计算矩阵乘法，或逐元素执行加法与 ReLU |

host/device 是角色称呼，不能简单理解成两台机器。集成 GPU 可能共享物理内存；运行时仍需管理数据可见性、缓冲区与任务依赖。

GPU 也不是“核心越多，小模型就必然越快”。安排任务、启动内核、搬运数据都需要时间；只有几个数字时，这些开销可能超过计算本身。

## 张量数值放在哪里，为什么要搬运

先用常见的独立 GPU 想象：Rust 的 `[[1.0,2.0]]` 最初在主机侧，设备算子需要可访问的设备缓冲区。框架创建张量时安排上传，计算完成后，只有当应用需要打印或处理具体数值时，才需要相应读回。集成 GPU 的物理共享内存会改变搬运细节，但不会免除访问和同步规则。

```text
主机数据 → 上传 X、W、b → 设备缓冲区 → 连续执行多个算子 → 输出缓冲区
                                                               ↓ 按需读回
                                                           主机可读取的数值
```

因此，一个请求里反复“读回中间结果 → 在 CPU 改一点 → 再上传”，可能让 GPU 不断等待。常见做法是让连续的张量操作留在同一设备，模型权重在初始化或加载后复用，输入按请求准备，最后只读回需要的结果。这样做是否更快仍要按第 10 章测量。

还要区分三种存储范围：

| 范围 | 初学时怎样理解 | 与矩阵乘法的关系 |
| --- | --- | --- |
| 全局设备内存 | 大多数张量数值所在的位置，容量较大 | 保存完整的 X、W 和输出 |
| 工作组共享存储 | 同一组工作项可以协作使用的较小区域 | 暂存一块输入，让组内多次使用 |
| 寄存器等局部计算状态 | 某个工作项计算时保留的小量值 | 保存累加中的输出或索引 |

这是典型 GPU 的教学划分，具体容量、可用机制与成本取决于硬件和运行时。不能因 Rust 里变量很小就断言它必然在寄存器，也不能把所有中间值都无条件塞进共享存储。

## 从模型表达式走到设备

先把整个过程看成一条路线：

```text
主机侧 Rust 程序
  → 创建 Device，准备 X、W、b
  → 创建目标设备上的张量
  → Tensor 操作经过 Bridge、Dispatch 路由到底层 backend
  → 运行时准备 buffer、内核及启动参数
  → 提交设备任务
  → 设备读取输入并写入输出
  → 等待完成，按需把结果读回主机
```

**backend（后端）**负责实现张量操作；**runtime（运行时）**负责面向具体设备管理内存、编译与执行等事务。`Dispatch` 是根据张量所属设备选择实现的路由层。初学时先把它们理解成“选择谁来算”和“安排它怎样算”。

Burn v0.22.1 的应用层使用 `Tensor<D>` 和 `Device`。`D` 是维数，例如这里的 `Tensor<2>`；底层实现仍使用 `Backend` 等 trait。旧资料里的 `Tensor<B, D>` 不能直接当作当前公共 API。

下面是公式对应的应用层核心片段；参数必须已经位于兼容设备，完整依赖与实验步骤见[实验路线](./14-learning-labs.md)。本章未独立编译此片段。

```rust
use burn::tensor::{Tensor, activation};

fn layer(x: Tensor<2>, w: Tensor<2>, b: Tensor<2>) -> Tensor<2> {
    activation::relu(x.matmul(w) + b)
}
```

这段代码表达“要算什么”，没有指定一个 GPU 线程负责哪一格，也没有承诺它只启动一个内核。源码中，公共 `matmul` 会检查形状，再下沉到实现层；CubeCL 后端的 `float_matmul` 会调用矩阵乘法实现。[公共矩阵乘法源码](https://github.com/tracel-ai/burn/blob/v0.22.1/crates/burn-tensor/src/tensor/api/numeric.rs)、[CubeCL 操作实现](https://github.com/tracel-ai/burn/blob/v0.22.1/crates/burn-cubecl/src/ops/tensor.rs)。

## 并行时，谁负责哪个元素

把输出放大成 `[M, N]`，其中 `M` 是样本行数，`N` 是输出特征数，输入特征数记作 `K`。共享偏置保存为 `[1, N]`，每一行都读取同一行偏置：

```text
Y[row, col] = max(0, sum(k=0..K-1, X[row,k] × W[k,col]) + b[0,col])
```

一个容易理解的教学方案，是让一个逻辑线程计算一个输出位置：线程 `(0, 0)` 算左上角，线程 `(0, 1)` 算同一行的下一格。**线程**是参与执行的一份工作；**线程组**把若干线程组织成一组，便于协作与调度。

假设有 `3 × 5 = 15` 个输出，每组安排 8 个逻辑位置，就需要向上取整为 2 组，共安排 16 个位置。最后一个位置没有有效元素，必须检查索引边界并退出，不能随意读写缓冲区。

把“一个工作项负责一个输出”写成索引关系：

$$
\text{total}=\left\lceil\frac{M\cdot N}{B}\right\rceil\cdot B,\qquad
\text{index}=\text{group}\cdot B+\text{lane}
$$

若 `index >= M*N` 就退出；否则 `row = index / N`、`col = index % N`。这里的 $B$ 是一组的工作项数。取整会让最后一组多出空位，所以边界检查不是可选项。

这只是教学分工。高性能矩阵乘法常使用 **tiling（分块）**：一组线程合作处理一个小矩阵块，让已读取的输入被多次利用；一个线程也可能负责多个元素。不要把“一线程一元素”当作所有 GPU 内核的规律。

### 分块为什么可能节省读取

设一组工作项合作算输出的一个 `2×2` 小块。在某个输入位置 k，需要一列 X 中的两个数、一行 W 中的两个数。这四个输入可以组成四次乘法，分别贡献给小块的四个输出；不必让四个输出各自独立读取全部需要的输入。

```text
从 X 取 [a,b]，从 W 取 [c,d]
对输出小块累计：[[a*c, a*d],
               [b*c, b*d]]
接着处理下一个 k，继续加到这些输出上
```

真正的分块内核通常把更大块数据协作加载到快速存储，并重复使用。它还要处理不足一个块的边界、对齐和工作组资源限制。协作读取时，需要保证读者开始使用前数据已准备好；这种组内同步与“CPU 等待整块 GPU 完成”是不同范围的同步。

GPU 工作项也不是给每个元素创建一个操作系统线程。工作项和工作组描述内核的逻辑分工，运行时与硬件把它们调度到执行资源上；模型作者通常不需要自己管理每个工作项。

Burn 的[官方教学内核](https://github.com/tracel-ai/burn/blob/v0.22.1/examples/custom-cubecl-kernel/src/kernel.rs)使用输出行列位置做乘加，并包含边界检查；它适合解释原理，官方书也明确提醒生产矩阵乘法需要更复杂的分块与硬件优化。

## CubeCL、WGPU 与编译：不要混在一起

**CubeCL** 提供编写和编译可移植计算内核的能力。Burn 的 `burn-cubecl` 把张量操作实现为 CubeCL 内核；同一个 `CubeBackend` 可以服务多个运行时，设备决定具体使用哪个运行时。

**wgpu** 提供跨图形 API 的设备计算接口。Burn 的 `burn-wgpu` 是 CubeCL 的一个运行时入口，可通过相关平台 API 执行计算；CubeCL 还支持其他运行时。因此，两者不是互相替代的两个模型框架。[CubeCL 后端说明](https://github.com/tracel-ai/burn/blob/v0.22.1/crates/burn-cubecl/src/lib.rs)、[WGPU 运行时说明](https://github.com/tracel-ai/burn/blob/v0.22.1/crates/burn-wgpu/src/lib.rs)。

这里还有两次不同层次的“编译”：

| 编译 | 什么时候 | 主要产物 |
| --- | --- | --- |
| Cargo / Rust 编译 | 构建 Rust 项目时 | 应用程序与依赖的主机侧代码 |
| JIT（即时编译） | 程序运行、需要特定设备内核时 | 适合当前运行时和计算配置的设备内核 |

JIT 的英文是 Just-In-Time。它并不是每次推理都重新执行 `cargo build`；内核缓存等机制可以复用已准备的结果。首次运行还可能包含设备初始化与 **autotune（自动调优）**，即测量候选内核并选择实现，所以首次耗时不代表稳定推理耗时。

## 提交、同步与读回是三件事

**submit（提交）**表示把任务交给执行队列，队列是一串等待设备执行的工作；**sync（同步）**表示等待待执行工作完成。提交函数返回时，GPU 可能仍在计算。

`Device::flush` 用来推动缓冲的工作进入执行过程，不等待完成；`Device::sync` 用来等待，返回 `Result` 以供处理错误。要查看数值，还需要读取输出，例如使用 `try_into_data` 并访问数据；主机读回可能引入等待与数据传输。[设备接口](https://github.com/tracel-ai/burn/blob/v0.22.1/crates/burn-tensor/src/device.rs)、[读回接口](https://github.com/tracel-ai/burn/blob/v0.22.1/crates/burn-tensor/src/tensor/api/base.rs)。

同步成功也不能替代输出正确性检查。在 CubeCL 实现中，某些启动失败会关联到输出缓冲区并在读取时报告；调试时应实际读取并验证结果，而非只观察程序有没有走过 `sync`。[CubeCL 同步实现](https://github.com/tracel-ai/burn/blob/v0.22.1/crates/burn-cubecl/src/backend.rs)。

### 后一个算子会不会读到前一个尚未算好的结果

异步不等于乱序使用数据。`matmul → add → relu` 里，add 依赖矩乘结果，relu 依赖加法结果；框架与运行时必须保留这些依赖，排队或在适当位置同步。CPU 可以先拿到输出句柄并继续描述下一步，GPU 则在依赖满足后执行。

```text
CPU：提交 matmul → 提交 add → 提交 relu → 等待 / 做其他主机工作
GPU：       执行 matmul → 执行 add → 执行 relu → 输出可供读取
```

这是单条依赖链的示意，不代表所有操作都能互相并行。两个无依赖的任务是否重叠，受运行时队列、硬件和资源约束；初学时使用框架正常接口即可，不要为了“并行”跳过数据依赖。

## 与 PyTorch 对照：CUDA 调用也有同样的时间边界

在 PyTorch 里，把张量放到 CUDA 后，张量运算通常同样是异步排队；要从主机观察完成时间，需要处理同步。`torch.cuda.synchronize()` 对应“主机等设备完成”的概念，不能类比成“下载输出数组”。CUDA event 还能用于设备时间测量，它与整段请求的主机耗时各有边界。[PyTorch CUDA 执行与计时说明](https://docs.pytorch.org/docs/2.14/notes/cuda.html#asynchronous-execution)。

可以用 PyTorch 的 GPU 教学理解上传、队列、内核与读回，但看到 `CUDA stream`、`torch.cuda` 等 API 时，应先认清它限定的运行时。Burn 的统一 Device 可以连接其他执行路径，具体接口和队列模型需要查相应实现，不能把 CUDA 写法直接替换几个名字就搬过来。

## 遇到问题时先检查这些

| 现象 | 首先检查 |
| --- | --- |
| 设备初始化失败 | Cargo feature、运行时选择、驱动与设备支持是否匹配 |
| 结果形状不对 | `X[M,K] × W[K,N]` 的 `K` 是否一致，偏置的广播规则是否符合预期 |
| 第一次明显更慢 | 是否把初始化、JIT、自动调优算进了推理时间 |
| 刚调用时没报错，读结果才失败 | 异步执行错误可能在等待或读回位置显现 |
| GPU 比 CPU 慢 | 数据规模、传输次数、启动次数和计时方法，而非只看计算表达式 |

## 本章实验

`gpu_probe` 用 CPU 线程模拟“把一个数组切成多个工作项”，对比单线程与四线程的元素级加法：

```sh
cargo run --locked --bin gpu_probe
```

预期看到 `single-thread`、`multi-thread` 与一个接近 4 的加速比。它演示的是工作划分，不是 GPU 基准；真正的 GPU 还要考虑启动、内存带宽和同步。没有 GPU 也可以完成本实验。

## 自测与答案

1. 上面的小例子，ReLU 前后分别是什么？**答案：**`[[-1, 2]]` 和 `[[0, 2]]`。
2. GPU 调用返回，能立刻说设备完成了吗？**答案：**不能；需按运行时接口等待，读取结果时也可能发生等待。
3. 15 个输出启动 16 个位置，最后一个怎么办？**答案：**先检查边界，越界位置不参与读写。
4. Cargo 构建完成，为什么首次运行仍可能慢？**答案：**设备初始化、JIT 和自动调优发生在运行阶段。
