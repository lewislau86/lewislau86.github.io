# 第 12 章：一次计算怎样执行

[课程总览](./index.md) · [上一章](./training-to-inference.md) · [下一章](./fusion-and-performance.md) · [资料与版本](./references.md)

::: tip 本章学习目标
把调用、排队、执行、同步与读回放在同一条时间线上。

**实践方式：** execution_trace：CPU 提交与读回观察。历史验证范围统一见[实验索引](./learning-labs.md)。
:::

第 5 章把工作分给 GPU 上的许多执行项，这一章把镜头拉回一次完整的调用：从 `x.matmul(w)` 进入框架，到结果重新变成可读张量，中间谁在排队、谁在等待、什么时候才算真正算完。理解这条时间线，才能解释“为什么提交很快、读回很慢”和“为什么小模型在 GPU 上可能更慢”。

## 一次调用经过哪些层 {#_9-1-一次调用经过哪些层}

同一个 `matmul` 在框架里要经过几层职责。下面是一条典型路径；不同后端会合并或省略某些步骤，但职责边界基本不变。

| 层 | 主要做什么 | 不该误认为 |
| --- | --- | --- |
| 公共 API | 检查形状、dtype、设备等用户层约束，表达数学意图 | 不是直接循环计算元素 |
| primitive / Bridge | 把公共张量转成后端能处理的底层表示 | 不是把数据下载到主机 |
| Dispatch | 根据张量和执行上下文选择实现 | 不是每次都比较所有显卡 |
| Backend / 装饰器 | 执行、记录求导或融合，或把工作转交运行时 | 不是所有装饰器都立即计算 |
| Runtime / 设备队列 | 提交 kernel、管理流与依赖 | 不是提交完就已经算完 |
| 同步与读回 | 等待完成，把结果变成主机可读数据 | 不是每次运算都会自动发生 |

公共张量 `Tensor<2>` 表示“二维浮点张量”，但不保证数据已经在 CPU，也不保证计算已经结束。形状、设备、dtype 和完成状态是不同维度的事实。

## 提交、执行与等待 {#_9-2-提交、执行与等待}

一次计算可以拆成三个时间点：

1. **提交（submit）**：主机把操作和参数放入运行时队列，通常很快；
2. **执行（execute）**：设备按队列顺序（或依赖关系）运行 kernel；
3. **读回（readback）**：主机等待完成并复制结果，可能引入同步。

![一次计算从提交到读回的时间线](/burn/execution-timeline.svg)

在 GPU 上，提交和执行是异步的：主机可以继续提交下一步，设备在后台排队。只有显式同步、读取数值、打印张量或进入下一步依赖时才需要等待。CPU 后端的实现可能同步执行，因此时间线会被压扁；但 API 的边界仍然存在。

可以用三个量描述这段过程：

$$
T_{\text{wall}} = T_{\text{submit}} + T_{\text{queue}} + T_{\text{kernel}} + T_{\text{readback}}
$$

$$
\text{吞吐} = \frac{\text{一次处理的样本数}}{T_{\text{wall}}}, \qquad
\text{加速比} = \frac{T_{\text{CPU}}}{T_{\text{设备}}}
$$

这里的 $T_{\text{wall}}$ 是主机看到的墙钟时间，不等于 kernel 自己报告的执行时间。只测提交时间，会得到“几乎没有耗时”的假象；只测一次冷启动，又会把编译、初始化和首次分配算进去。

## 提交、同步与读回是三件事 {#提交、同步与读回是三件事}

**submit（提交）**表示把任务交给执行队列，队列是一串等待设备执行的工作；**sync（同步）**表示等待待执行工作完成。提交函数返回时，GPU 可能仍在计算。

`Device::flush` 用来推动缓冲的工作进入执行过程，不等待完成；`Device::sync` 用来等待，返回 `Result` 以供处理错误。要查看数值，还需要读取输出，例如使用 `try_into_data` 并访问数据；主机读回可能引入等待与数据传输。[设备接口](https://github.com/tracel-ai/burn/blob/v0.22.1/crates/burn-tensor/src/device.rs)、[读回接口](https://github.com/tracel-ai/burn/blob/v0.22.1/crates/burn-tensor/src/tensor/api/base.rs)。

同步成功也不能替代输出正确性检查。在 CubeCL 实现中，某些启动失败会关联到输出缓冲区并在读取时报告；调试时应实际读取并验证结果，而非只观察程序有没有走过 `sync`。[CubeCL 同步实现](https://github.com/tracel-ai/burn/blob/v0.22.1/crates/burn-cubecl/src/backend.rs)。

### 后一个算子会不会读到前一个尚未算好的结果 {#后一个算子会不会读到前一个尚未算好的结果}

异步不等于乱序使用数据。`matmul → add → relu` 里，add 依赖矩乘结果，relu 依赖加法结果；框架与运行时必须保留这些依赖，排队或在适当位置同步。CPU 可以先拿到输出句柄并继续描述下一步，GPU 则在依赖满足后执行。

```text
CPU：提交 matmul → 提交 add → 提交 relu → 等待 / 做其他主机工作
GPU：       执行 matmul → 执行 add → 执行 relu → 输出可供读取
```

这是单条依赖链的示意，不代表所有操作都能互相并行。两个无依赖的任务是否重叠，受运行时队列、硬件和资源约束；初学时使用框架正常接口即可，不要为了“并行”跳过数据依赖。

## 什么时候必须同步 {#_9-4-什么时候必须同步}

以下操作通常需要或触发同步：

- 把张量读成主机数组、打印具体数值、做依赖主机值的条件判断；
- 在不同设备之间复制数据；
- 某些错误检查、调试工具或性能计时；
- 运行时显式要求 `sync` / `synchronize`。

仅仅“构造一个张量”或“提交一次矩阵乘法”通常不需要。把同步点放在循环里，会让主机和设备轮流等待，吞吐显著下降。反过来，完全不等就读取计时结果，又可能只测到提交时间。

## 与 PyTorch 对照：CUDA 调用也有同样的时间边界 {#与-pytorch-对照-cuda-调用也有同样的时间边界}

在 PyTorch 里，把张量放到 CUDA 后，张量运算通常同样是异步排队；要从主机观察完成时间，需要处理同步。`torch.cuda.synchronize()` 对应“主机等设备完成”的概念，不能类比成“下载输出数组”。CUDA event 还能用于设备时间测量，它与整段请求的主机耗时各有边界。[PyTorch CUDA 执行与计时说明](https://docs.pytorch.org/docs/2.14/notes/cuda.html#asynchronous-execution)。

可以用 PyTorch 的 GPU 教学理解上传、队列、内核与读回，但看到 `CUDA stream`、`torch.cuda` 等 API 时，应先认清它限定的运行时。Burn 的统一 Device 可以连接其他执行路径，具体接口和队列模型需要查相应实现，不能把 CUDA 写法直接替换几个名字就搬过来。

## 为什么小模型在 GPU 上可能更慢 {#_9-3-为什么小模型在-gpu-上可能更慢}

GPU 擅长“大量相同工作并行执行”，但每次启动 kernel、搬运数据和同步都有固定成本。判断是否值得，需要同时看计算量和数据量。一个常用的粗指标是算术强度：

$$
\text{算术强度} = \frac{\text{浮点运算次数}}{\text{搬运字节数}}
$$

若计算量相对搬运量太小，时间主要花在搬运和启动上，增加并行度也救不回来。反过来，矩阵乘法这类操作有较多可复用数据，更容易从并行中获益。实际判断仍要测量，不能只看参数量或显卡型号。

批处理也会改变结论：增大 batch 通常提高设备利用率与吞吐，但增加单次请求的延迟和内存占用。服务系统要在吞吐、延迟和显存之间取舍，而不是简单“越大越好”。

## 融合、图捕获与编译 {#_9-5-融合、图捕获与编译}

框架可以在执行前做两类优化：

- **算子融合**：把相邻的逐元素操作合并，减少临时张量和 kernel 启动；第 13 章会讨论。
- **图捕获 / 编译**：记录一段固定的启动序列，之后整体重放，减少逐次分派开销；是否支持取决于后端与版本。

它们都不会改变数学公式，但会改变时间花在哪里。阅读性能数字时，要同时记录是否启用融合、是否捕获图、是否包含首次编译，以及同步点在哪里。

## P2P：两张 GPU、两个进程怎样共享数据 {#p2p}

单设备的“提交、等待、读回”还不足以解释 [10_p2p](https://github.com/gau-nernst/learn-cuda/tree/afcb20b1bd89065c31a1575c276aba686fc4dfce/10_p2p)。该例有两个 Python 子进程，各自选择一张 GPU，用 gloo 交换 IPC handle，再由 kernel 直接访问对端显存。

### 指针、句柄和通信通道

| 对象 | 所属范围 | 职责 |
| --- | --- | --- |
| 本地设备指针 | 当前进程的地址空间 | 定位当前进程可访问的设备内存 |
| CUDA IPC handle | 可通过进程通信传递的句柄 | 让另一个进程打开同一设备分配 |
| 打开的 remote pointer | 接收进程的映射 | 在该进程的 kernel 中访问对端 |
| gloo process group | 进程间通信 | 交换 handle、协调实验阶段，不代替 GPU 内存协议 |
| arena / heap | 每张 GPU 的大块分配 | 子对象用基址加偏移定位，减少重复交换 |

原始指针的数值不能直接跨进程使用。上游 main.py 用 spawn 创建进程，先设置设备，再由 p2p.cu 调用 cudaIpcGetMemHandle / cudaIpcOpenMemHandle。所有设备各分配一块相同用途的 heap；子对象使用同样偏移，远程地址按下式翻译：

```text
offset = local_object_pointer - local_heap_base
remote_object_pointer = remote_heap_base + offset
```

这就是示例中 symmetric heap 的核心约定。它依赖对端对象确实位于同一偏移，不是共享了一次基址就能随意在两边独立分配。

### P2P 能访问，不代表已经同步

先用 cudaDeviceCanAccessPeer 检查“当前设备能否访问 peer”，再在当前设备启用该访问方向；反向也要单独处理。并非任意两张 GPU 都支持，也不因支持 P2P 就推断存在 NVLink。API 语义见 [CUDA Peer Device Memory Access](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__PEER.html)。

示例 enable_p2p 直接尝试启用，未先调用 can-access 查询。复现前应补能力检查，失败时明确结束，不把单卡、不可达拓扑或权限问题当成 kernel 错误。

主程序的两个阶段分别为：

1. 每张卡把本地数组填成 -1，等待本地写入完成，再做进程 barrier。远端写入测试后再次等待与 barrier，期望各进程读到 `[0,1]`。
2. 每张卡填入自身 rank，完成初始化并协调后，读取各 peer 的数据到本地数组，期望仍为 `[0,1]`。

这里**先完成设备工作，再协调进程阶段**。单独调用 dist.barrier 并不自动使任意 CUDA 流中的先前写入全部完成；内存 ordering/coherence 需要实际同步协议。上游靠阶段性同步展示读写，没有实现并发生产消费或通用集合通信。

### 资源怎样结束

正确生命周期是：分配 heap → 导出/交换 handle → 打开映射 → 执行并等待所有访问 → 关闭打开的 IPC 映射 → 最后释放原分配。示例没有显式提供 close_ipc_handle 包装，进程退出会结束这次演示；长期运行程序应补 cudaIpcCloseMemHandle、异常清理与明确所有者。

还要检查每个子进程的退出码。上游父进程只 join，没有把失败子进程状态汇总为严格验收，因此“父进程正常退出”不等于两个 rank 都成功。该例每卡申请约 1 GiB heap，容量也应预先记录。

### 与 Burn 的关系

Burn Tensor 知道自己所属的设备，但两个 Device 句柄不会自动建立 IPC、对称堆或跨卡同步。接入此类机制需要额外设计内存所有权、设备与进程拓扑、流和事件、异常路径及后端接口。这里的 P2P 内容用于理解执行边界，不声称 Burn 主线已具备这份示例的多进程能力。


## 本章实验：观察提交与读回 {#_9-6-本章实验-观察提交与读回}

学习包中的 `execution_trace` 用 CPU Flex 后端做一次可复现的对照：先预热，再分别计时“只提交矩阵乘法”和“提交后读回结果”。CPU 后端可能同步执行，所以两组数字接近是正常的；这个实验的目的是让你分清 API 边界，而不是制造 CPU/GPU 排名。

在解压后的学习包目录运行：

```sh
cargo run --locked --bin execution_trace
```

程序会：

1. 创建两个 `256 × 256` 的 `f32` 张量；
2. 预热 3 次，避免首次分配和编译影响；
3. 计时 20 次矩阵乘法，不读取结果；
4. 计时 20 次矩阵乘法，并在每次后把结果读回主机求和；
5. 打印形状、两次耗时和近似 GFLOPS。

预期输出形状为 `[256, 256]`，并包含两行 `submit` / `readback` 时间。具体毫秒数随机器变化，不构成性能基准。若你使用支持异步的后端，可以观察两组时间的差距；若使用 CPU，重点看“读回”这一步是否改变了调用顺序。

### 自己改一改 {#自己改一改}

- 把矩阵从 `256` 改为 `64` 和 `1024`，观察提交与读回的比例怎样变化；
- 去掉读回，只保留循环，看看程序是否真的完成了计算（提示：结果可能被优化掉，需要保留输出）；
- 在循环里加入 `println!` 或 `into_data()`，观察同步点如何插入；
- 若有 WGPU/CUDA 设备，改用对应 `Device`，并记录是否首次初始化。

## 自测 {#_9-7-自测}

1. 提交一次矩阵乘法后，主机能否立刻读到结果？**不一定。** 读回或同步时才保证完成。
2. 为什么只测一次 `matmul` 可能得到错误结论？**冷启动、首次分配和编译会混入计时。**
3. 小模型在 GPU 上更慢，可能有哪些原因？**启动、搬运、同步、利用率低，或计算量太小。**
4. 融合会改变数学结果吗？**不会改变公式，但会改变执行次数、临时内存和时间分布。**
5. 吞吐高是否等于单次延迟低？**不一定。** 批处理可以提高吞吐，同时增加单次延迟。
